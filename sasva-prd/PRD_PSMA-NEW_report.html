Wrap-Text Toggle for Markdown Inline Code Blocks

Add a client-side "Toggle code wrap" button next to the copy button on every rendered Markdown code block, so long lines can be wrapped instead of horizontally scrolled.

Issue: PSMA-NEW (source: go-gitea/gitea#35314)  |  Generated: 2025  |  Prior art: Draft PR go-gitea/gitea#35529 (unmerged)

1. Executive Summary

Gitea renders fenced/indented code blocks inside Markdown (issue bodies, PR descriptions, comments, wiki pages, READMEs) with a "copy code" button (web_src/js/markup/codecopy.ts) but no way for the reader to toggle line wrapping. Long lines currently either overflow with a horizontal scrollbar (code-overflow-scroll, the default emitted by the Go renderers) or, in a couple of dev-test-only surfaces, wrap (code-overflow-wrap) — but there is no interactive way to switch between the two from the rendered page.

This feature adds a "Toggle code wrap" button next to the existing copy button on every rendered Markdown code block, letting users flip between horizontal-scroll and wrapped-text display on demand. The preference is remembered client-side (per browser) so it persists across page loads.

2. Problem Statement

Long lines in fenced code blocks (long log lines, long URLs, long JSON, minified code pasted into an issue) force horizontal scrolling, which is awkward on narrow viewports and mobile, and requires extra interaction to read the full line. Conversely, some users prefer wrapped text as the default and scroll-mode as the exception. Gitea's markup CSS (web_src/css/markup/content.css lines 377–392) already defines both .code-block-container.code-overflow-wrap and .code-block-container.code-overflow-scroll rule sets, and they are exercised in the internal templates/devtest/markup-render.tmpl page, but no production UI surface lets an end user choose between them — the two Go renderers (modules/markup/markdown/markdown.go:91 for Chroma-highlighted fences, modules/markup/markdown/goldmark.go:132 for indented code blocks) both hardcode code-overflow-scroll unconditionally.

GitHub, Codeberg and other forges offer an inline wrap toggle on rendered code blocks; its absence is a recurring, low-friction usability gap reported directly by a Gitea PR reviewer (silverwind) in issue #35314.

3. Goals & Objectives

Business goals

  • Close a well-known usability gap relative to competitor forges (GitHub) at low engineering cost, reusing already-shipped CSS.
  • Keep the change additive/non-breaking — no change to default rendering behavior unless the user opts in.

User goals

  • Let any reader of rendered Markdown switch a code block between scroll-on-overflow and wrap-long-lines display with a single click.
  • Remember the last-chosen mode across page navigations without requiring login or a server round-trip.

Measurable outcomes

  • Wrap toggle button renders on 100% of fenced/indented code blocks inside .markup content (issues, PRs, comments, wiki, README, release notes).
  • No regression in existing "copy code" button placement/behavior or in Mermaid/KaTeX/math code block rendering.
  • Preference persists across a full page reload in the same browser.

4. Scope

In scope

  • New wrap-toggle button rendered alongside the existing copy-code button on every .markup .code-block-container.
  • Client-side persistence of the wrap preference (single global toggle) using localUserSettings (web_src/js/modules/user-settings.ts), not raw localStorage.
  • New locale string (code_toggle_wrap) surfaced through templates/base/head_script.tmpl → window.config.i18n.
  • New SVG icon asset for the wrap toggle, registered in web_src/js/svg.ts.
  • Refactor of web_src/js/markup/codecopy.ts into a shared "code block buttons" module (as prototyped in PR #35529's codeblocks.ts).
  • Update web_src/js/markup/mermaid.ts to consume the shared button-row helper.

Out of scope (this iteration)

  • The repository file/blame code view (web_src/js/modules/codeeditor/) already has its own unrelated line-wrap affordance — whether it should share a preference with the Markdown toggle is deferred as an open question.
  • The package registry container digest block (templates/package/content/container.tmpl:20) is not wired to the toggle in this iteration.
  • Per-code-block (vs. global/page-wide) wrap memory is out of scope.
  • Backend renderer changes to emit a different default wrap mode are out of scope — default remains code-overflow-scroll server-side.

7. User Stories / Use Cases

  1. As a reader viewing a long log dump in an issue comment, I want to click a "wrap" button on the code block so long lines wrap instead of requiring horizontal scrolling.
  2. As a reader who has already toggled wrap mode on one code block, I expect the same wrap preference to apply automatically to other code blocks I encounter later in my session/browser, without needing to log in.
  3. As a mobile user, I want wrapped code by default/via one tap, since horizontal scrolling is harder on touch screens.
  4. As a maintainer reviewing a PR, when a diff/patch or Mermaid diagram is rendered inside a Markdown body, I want the same consistent copy/wrap button row so the UI feels uniform across code block types.
  5. As a translator, I want the new toggle's tooltip/label (code_toggle_wrap) to be a translatable locale string, not hardcoded English text.

9. Non-Functional Requirements

  • Coding convention compliance: must not introduce a direct localStorage call — ESLint restricted-globals forbids this repo-wide (per docs/22-contributing-development/frontend-coding-conventions.md); PR #35529's raw localStorage usage would need adaptation to pass CI.
  • Performance: no additional network requests; pure DOM class toggle plus one synchronous localStorage read/write.
  • Accessibility: button must have an accessible label via the new locale string and be keyboard-operable (native <button>, per makeCodeCopyButton's pattern).
  • i18n: string added only to locale_en-US.json; other locales flow through Crowdin.
  • Browser compatibility: vanilla DOM APIs, no framework dependency.
  • No visual regression: existing hover/reveal behavior for auto-hide-control must continue to apply.
  • Backward compatibility: templates/devtest/markup-render.tmpl must continue to render correctly after the module rename.

11. Data Requirements

Client-side only. No new database tables, migrations, or REST API endpoints. The only "data" persisted is a boolean/string preference key (e.g. wrap-markup-code) stored via localUserSettings, which prefixes keys with gitea:setting: in localStorage — no server round-trip, no per-user server-side setting.

Input: user click on the toggle button. Output: DOM class mutation (code-overflow-wrap ⇄ code-overflow-scroll) applied to all .code-block-container elements currently on the page, plus a localStorage write for persistence.

13. Dependencies & Assumptions

  • Depends on existing CSS rules already shipped in web_src/css/markup/content.css — no new selectors needed, only a new trigger mechanism.
  • Depends on the existing svg() icon-registration pattern in web_src/js/svg.ts.
  • Depends on localUserSettings being the sanctioned localStorage wrapper (per ESLint rule).
  • Assumption: a single global (not per-code-block) toggle is acceptable UX, matching PR #35529.
  • Assumption: this feature does not need to touch the diff/blame code viewer (web_src/js/modules/codeeditor/).
  • PR #35529 is draft/unmerged prior art — treated as a design reference, not shipped functionality.

15. Acceptance Criteria

  • Wrap-toggle button appears on every rendered Markdown code block inside .markup content without displacing the copy button.
  • Clicking the button toggles wrap/scroll display immediately, with no page reload.
  • Chosen mode persists after a full reload (validated via localUserSettings, key visible under gitea:setting: prefix).
  • Toggle button has a translatable, accessible label from code_toggle_wrap.
  • No raw localStorage calls introduced (ESLint passes).
  • Mermaid-rendered code fences continue to render zoom/reset controls correctly using the shared helper.
  • templates/devtest/markup-render.tmpl still renders both static wrap states correctly.
  • Server-rendered HTML from the Go renderers is unchanged (confirmed via markdown_test.go:611).

16. Success Metrics (KPIs)

  • Zero regressions in copy-button or Mermaid/KaTeX rendering.
  • CI health: passes markdown_test.go, new frontend tests, and ESLint.

18. Open Questions

  1. Should the Markdown wrap preference share state with the unrelated code/file view wrap control (web_src/js/modules/codeeditor/main.ts)? Treated as separate for now — needs maintainer sign-off.
  2. Should the implementation use localUserSettings instead of PR #35529's raw localStorage? Recommended for convention compliance — confirm with eventual PR author/reviewers.
  3. Is mixing icon families (Octicon copy + Material wrap-text) acceptable, or should an alternate icon be sourced?
  4. Should the wrap preference be global/site-wide (assumed here) or per-code-block?
  5. Should templates/package/content/container.tmpl's hardcoded scroll block eventually get the same toggle?
