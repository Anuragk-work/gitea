<h1>Authentication & Session Security</h1>
<h1 id="authentication-session-security">Authentication &amp; Session Security</h1>
<p>Gitea accepts credentials through an unusually wide number of front doors: browser sessions,
HTTP Basic, personal access tokens (PATs), OAuth2 bearer tokens, LDAP/PAM/SMTP-backed password
login, SSPI/Kerberos, reverse-proxy header trust, and HTTP-signature auth for ActivityPub
federation. All of it funnels through one small interface and a small number of ordered
"auth chains" per surface. This page maps that entire authentication and session-security
surface — what verifies identity, how sessions/tokens are minted and protected, how 2FA and
replay protection work, and where a scanner operator (Trivy/opengrep) should focus attention.</p>
<p>This page synthesizes <code>docs/08-services/auth-providers.md</code>, <code>docs/11-authentication/README.md</code>,
<code>docs/02-architecture/request-lifecycle.md</code>, <code>docs/06-web-routers/web-routes.md</code>, and
<code>docs/07-rest-api/api-conventions-and-swagger.md</code>.</p>
<h2 id="the-core-abstraction-authmethod">The Core Abstraction: <code>auth.Method</code><a href="#the-core-abstraction-authmethod" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Every authentication mechanism in Gitea implements one interface, described in
<a href="../../docs/08-services/auth-providers.html">Authentication &amp; Authorization</a>:</p>
<pre class="highlight"><code class="language-go">// Method represents an authentication method (plugin) for HTTP requests.
type Method interface {
    Verify(http *http.Request, w http.ResponseWriter, store DataStore, sess SessionStore) (*user_model.User, error)
    Name() string
}</code></pre>
<p>Contract semantics matter for security review:</p>
<ul>
<li><strong><code>(nil, nil)</code></strong> — this method doesn't apply to the request (no matching header/cookie); the
  chain tries the next method.</li>
<li><strong><code>(nil, err)</code></strong> — the method recognized its credential format but verification <em>failed</em>
  (bad password, expired/replayed token). This is a hard failure, but other methods further
  down the chain may still succeed and override it.</li>
<li><strong><code>(user, nil)</code></strong> — success.</li>
</ul>
<p>Two optional extension interfaces sit on top of a login <strong><code>Source</code></strong> (the admin-configured
credential backend, distinct from a <code>Method</code>):</p>
<pre class="highlight"><code class="language-go">type PasswordAuthenticator interface {
    Authenticate(ctx context.Context, user *user_model.User, login, password string) (*user_model.User, error)
}
type SynchronizableSource interface {
    Sync(ctx context.Context, updateExisting bool) error
}</code></pre>
<blockquote>
<p><strong>Method vs. Source, don't conflate them when triaging a finding.</strong> An <code>auth.Method</code>
verifies an <em>HTTP request</em> (session cookie, bearer token, header, signature). An
<code>auth.Source</code> is an admin-configured <em>credential backend</em> (LDAP server, SMTP server, OAuth2
app, PAM service, SSPI domain). <code>Basic</code>/<code>Session</code> call into the active <code>Source</code>s via
<code>UserSignIn</code>; OAuth2/SSPI use their <code>Source</code> purely for configuration.</p>
</blockquote>

<p>Every one of these is a distinct attack surface with a different credential format, which
means a single SAST pass (opengrep) or dependency scan (Trivy) won't cover them uniformly —
see <a href="#scanning-guidance-for-trivy--opengrep">Scanning Guidance</a> below.</p>
<h2 id="per-surface-auth-chains">Per-Surface Auth Chains<a href="#per-surface-auth-chains" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The <strong>order of methods in a chain matters</strong> — some methods (reverse proxy, SSPI) create a new
session or short-circuit the chain, so ordering bugs are a realistic authentication-bypass
class to look for when reviewing chain-construction code.</p>
<h3 id="web-ui-chain-routerswebwebgo-newwebauthmiddleware">Web UI chain (<code>routers/web/web.go</code> → <code>newWebAuthMiddleware</code>)<a href="#web-ui-chain-routerswebwebgo-newwebauthmiddleware" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code class="language-go">group := auth_service.NewGroup()
if allowOAuth2 {
    group.Add(&amp;auth_service.OAuth2{})
}
if allowBasic {
    group.Add(&amp;auth_service.Basic{})
}
if setting.Service.EnableReverseProxyAuth {
    // reverse-proxy should be before Session, otherwise the header
    // will be ignored if the user has already logged in
    group.Add(&amp;auth_service.ReverseProxy{CreateSession: !isSessionless})
}
group.Add(&amp;auth_service.Session{})
if enableSSPI {
    // it MUST be the last, see the comment of SSPI
    group.Add(&amp;auth_service.SSPI{CreateSession: !isSessionless})
}</code></pre>
<h3 id="rest-api-chain-routersapiv1apigo-buildauthgroup">REST API chain (<code>routers/api/v1/api.go</code> → <code>buildAuthGroup</code>)<a href="#rest-api-chain-routersapiv1apigo-buildauthgroup" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code class="language-go">func buildAuthGroup() *auth.Group {
    group := auth.NewGroup(
        &amp;auth.OAuth2{},
        &amp;auth.HTTPSign{},
        &amp;auth.Basic{}, // FIXME: should be removed once basic auth in API isn't allowed
    )
    if setting.Service.EnableReverseProxyAuthAPI {
        group.Add(&amp;auth.ReverseProxy{})
    }
    return group
}</code></pre>
<blockquote>
<p>The <code>FIXME</code> comment in the upstream source itself flags Basic Auth on the API as a
known-undesirable legacy allowance — worth tracking as a standing hardening item rather than
a "new" finding if a scanner surfaces it.</p>
</blockquote>
<h3 id="package-registry-api-chain-routersapipackagesapigo">Package registry API chain (<code>routers/api/packages/api.go</code>)<a href="#package-registry-api-chain-routersapipackagesapigo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Each package registry endpoint calls <code>verifyAuth(r, []auth.Method{...}, opts)</code> with a
registry-specific method list (e.g. NuGet's own API-key <code>Method</code> wrapping
<code>Basic.VerifyAuthToken</code>), and <code>ReverseProxy</code> is appended automatically when
<code>EnableReverseProxyAuth</code> is set.</p>
<pre class="mermaid">flowchart TD

<p><code>common.AuthShared</code> (<code>routers/common/auth.go</code>) is the shared glue: it calls
<code>authMethod.Verify(...)</code>, stores <code>ctx.Doer</code>/<code>ctx.IsSigned</code>/<code>ctx.IsBasicAuth</code>, and refreshes the
request locale to the signed-in user's language, per
<a href="../../docs/02-architecture/request-lifecycle.html">Request Lifecycle</a>.</p>
<h2 id="session-establishment-fixation-protection">Session Establishment &amp; Fixation Protection<a href="#session-establishment-fixation-protection" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>Session</code> (<code>services/auth/session.go</code>) is deliberately simple: it reads a <code>uid</code> key from the
session store (backed by <code>modules/session</code>, provider selectable via <code>[session] PROVIDER</code> —
<code>memory</code>/<code>file</code>/<code>db</code>/<code>redis</code>) and loads the <code>User</code> by ID. It returns <code>(nil, nil)</code> when there's
no session, letting later/earlier methods take over.</p>
<p>The session-writing side lives in <code>handleSignIn</code> (<code>services/auth/auth.go</code>), which — per
<a href="../../docs/08-services/auth-providers.html">Auth Providers</a> — <strong>regenerates the session ID on
sign-in</strong> (classic session-fixation mitigation), clears stale two-factor/OpenID keys, and
stores <code>uid</code>/<code>uname</code>.</p>
<p>Per <a href="../../docs/02-architecture/request-lifecycle.html">Request Lifecycle</a>, the session
middleware (<code>common.MustInitSessioner()</code>) is installed globally, ahead of the auth-method
group, so every request — even unauthenticated ones — carries a session-capable context.
Routes that must remain sessionless (git-over-HTTP clone/push, RSS feeds, attachment
downloads) explicitly opt out via <code>webAuth.AllowBasic</code>/<code>webAuth.AllowOAuth2</code> pre-middlewares
so the <code>Session</code> method doesn't force a cookie to be created for non-browser clients.</p>
<h3 id="cross-origin-csrf-protection">Cross-Origin / CSRF Protection<a href="#cross-origin-csrf-protection" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Rather than the classic CSRF-token-in-every-form pattern, Gitea's <code>verifyAuthWithOptions</code>
(<code>routers/web/web.go</code>) calls Go's standard-library <strong>Fetch Metadata</strong> check:</p>
<pre class="highlight"><code class="language-go">http.NewCrossOriginProtection().Check(ctx.Req)</code></pre>
<p>This inspects the <code>Sec-Fetch-Site</code> header to reject cross-site browser navigations, per
<a href="../../docs/02-architecture/request-lifecycle.html#5-authorization--csrf--feature-checks">Request Lifecycle</a>.
It is skipped when <code>SignOutRequired</code> or <code>DisableCrossOriginProtection</code> is set, and explicitly
disabled for routes that must accept legitimately cross-origin, non-browser traffic — e.g. Git
Smart HTTP (<code>optSignInFromAnyOrigin</code>), because <code>git clone</code>/<code>push</code> traffic never sends a
<code>Sec-Fetch-Site</code> header and isn't a CSRF risk by construction (per
<a href="../../docs/06-web-routers/web-routes.html">Web Router &amp; Server-Rendered UI</a>).</p>
<blockquote>
<p><strong>Review angle</strong>: any new route added with <code>optSignInFromAnyOrigin</code> (or an equivalent
CSRF-disabling option) that <em>does</em> accept browser-originated state-changing requests would
reintroduce a CSRF gap — this is a good opengrep custom-rule target (flag any use of
<code>DisableCrossOriginProtection</code> / <code>optSignInFromAnyOrigin</code> for manual review).</p>
</blockquote>
<h2 id="basic-auth-the-multi-credential-fallback-path">Basic Auth: the Multi-Credential Fallback Path<a href="#basic-auth-the-multi-credential-fallback-path" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>Basic.VerifyAuthToken</code> (<code>services/auth/basic.go</code>) is more than "HTTP Basic" — it's the shared
verification routine reused by other integrations (e.g. NuGet's <code>X-NuGet-ApiKey</code>). It tries,
in order:</p>
<ol>
<li><strong>OAuth2 access token</strong> — parses a JWT-shaped token and resolves the <code>OAuth2Grant</code>.</li>
<li><strong>Personal Access Token</strong> — looks up a PAT by its last-eight-chars index, then verifies the
   full token via a constant-time hash comparison.</li>
<li><strong>Actions task token</strong> — used by CI runners.</li>
<li><strong>Username/password fallback</strong> — only if <code>setting.Service.EnableBasicAuth</code> is true; calls
   <code>UserSignIn</code>, then enforces 2FA: <strong>WebAuthn-enrolled accounts are rejected outright</strong> for
   Basic auth (<code>"basic authorization is not allowed while WebAuthn enrolled"</code>), and
   TOTP-enrolled accounts must supply a valid <code>X-Gitea-OTP</code> header, verified via atomic
   single-use consumption to prevent replay.</li>
</ol>
<p>This layering means "Basic Auth is disabled" (<code>ENABLE_BASIC_AUTHENTICATION=false</code>) does <em>not</em>
disable PAT or OAuth2-bearer-via-Basic-header usage — only the raw username/password fallback
step 4. Scanners and reviewers checking "is password-over-Basic-Auth possible" need to check
this specific branch, not just whether the <code>Basic</code> method is registered in the chain.</p>
<h2 id="personal-access-tokens-oauth2-scopes">Personal Access Tokens &amp; OAuth2 Scopes<a href="#personal-access-tokens-oauth2-scopes" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Modeled by <code>AccessToken</code> (<code>models/auth/access_token.go</code>), per
<a href="../../docs/08-services/auth-providers.html">Auth Providers</a>:</p>
<pre class="highlight"><code class="language-go">type AccessToken struct {
    ID             int64 `xorm:"pk autoincr"`
    UID            int64 `xorm:"INDEX"`
    Name           string
    Token          string `xorm:"-"`          // only available at creation time
    TokenHash      string `xorm:"UNIQUE"`      // sha256+salt of token, persisted
    TokenSalt      string
    TokenLastEight string `xorm:"INDEX token_last_eight"` // fast index lookup
    Scope          AccessTokenScope
    ...
}</code></pre>
<p>Tokens are <strong>never stored in plaintext</strong>: <code>NewAccessToken</code> generates a random token and stores
only a salted hash plus a <code>TokenLastEight</code> index shortcut; <code>GetAccessTokenBySHA</code> looks up
candidates by the index and does a <strong>constant-time</strong> comparison (<code>crypto/subtle</code>), with an
optional LRU cache to skip repeated hash work for hot tokens.</p>

<h2 id="remember-me-cookies-auth-tokens-distinct-from-sessions-and-pats">Remember-Me Cookies (Auth Tokens) — Distinct from Sessions and PATs<a href="#remember-me-cookies-auth-tokens-distinct-from-sessions-and-pats" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Persistent "remember me" login cookies use a <strong>separate mechanism</strong> from both sessions and
PATs: <code>models/auth/auth_token.go</code> + <code>services/auth/auth_token.go</code>, modeled after
<a href="https://paragonie.com/blog/2015/04/secure-authentication-php-with-long-term-persistence">Paragon Initiative's secure remember-me design</a>,
per <a href="../../docs/08-services/auth-providers.html">Auth Providers</a>. Each cookie value is <code>id:token</code>;
the server stores only <code>TokenHash = sha256(token)</code> keyed by <code>id</code>.</p>
<ul>
<li><code>CheckAuthToken</code> verifies the hash in <strong>constant time</strong> on every use.</li>
<li><code>RegenerateAuthToken</code> <strong>rotates the hash on every login</strong>, keeping the same <code>id</code>.</li>
<li>If an attacker replays a stolen (already-used) token, the hash mismatch triggers
  <code>DeleteAuthTokenByID</code> — the device's remember-me token is immediately revoked, forcing
  re-authentication. This is a <strong>theft-detection</strong> property, not just theft-prevention.</li>
</ul>
<h2 id="two-factor-authentication">Two-Factor Authentication<a href="#two-factor-authentication" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea supports two independent 2FA mechanisms; a user may enroll in either or both, per
<a href="../../docs/08-services/auth-providers.html">Auth Providers</a>:</p>
<h3 id="totp">TOTP<a href="#totp" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Modeled by <code>TwoFactor</code> (<code>models/auth/twofactor.go</code>). The shared secret is <strong>AES-encrypted at
rest</strong> (key derived from <code>setting.SecretKey</code> via MD5) and Base64-encoded in the <code>Secret</code>
column. Validation uses <code>github.com/pquerna/otp/totp</code>, and — critically — passcodes are
<strong>single-use</strong>: <code>ValidateAndConsumeTOTP</code> performs a conditional <code>UPDATE</code> (<code>last_used_passcode
&lt;&gt; ?</code> or <code>IS NULL</code>) so a captured OTP cannot be replayed within its validity window even under
concurrent requests (the <code>UPDATE</code>'s row lock serializes racing attempts). A scratch/recovery
token (ambiguity-free Base32 alphabet) is available as a backup.</p>
<blockquote>
<p><strong>MD5-derived key note</strong>: the source docs explicitly describe the TOTP secret's
AES-encryption key as "derived from <code>setting.SecretKey</code> via MD5". MD5-as-a-KDF is a
reasonable target for an opengrep custom rule or manual crypto review — even though it's not
used for signature/hash verification here (just symmetric-key derivation), it's the kind of
primitive-choice a SAST tool tuned for weak-crypto detection should surface for
confirmation, not automatic assumption of exploitability.</p>
</blockquote>
<h3 id="webauthn-passkeys">WebAuthn / Passkeys<a href="#webauthn-passkeys" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Modeled by <code>WebAuthnCredential</code> (<code>models/auth/webauthn.go</code>), backed by
<code>github.com/go-webauthn/webauthn</code>, initialized once at startup with <code>RPDisplayName</code>, <code>RPID</code>
(<code>setting.Domain</code>), and <code>RPOrigins</code>. As noted above, <strong>WebAuthn-enrolled accounts cannot use
Basic Auth at all</strong> — WebAuthn's challenge-response ceremony can't be satisfied by a
header-only credential, so such users must use session login, OAuth2, or an <code>X-Gitea-OTP</code>
(TOTP) path if also enrolled in TOTP.</p>
<h2 id="credential-backend-source-details">Credential-Backend (Source) Details<a href="#credential-backend-source-details" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="ldap-servicesauthsourceldap">LDAP (<code>services/auth/source/ldap</code>)<a href="#ldap-servicesauthsourceldap" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Two flavors — <code>LDAP</code> (bind-DN search+bind) and <code>DLDAP</code> (direct/simple bind) — built on
<code>github.com/go-ldap/ldap</code>. Security-relevant fields: <code>BindDN</code>/<code>BindPassword</code> are <strong>encrypted
at rest</strong> via <code>secret.EncryptSecret</code> when the source config is persisted (<code>ToDB</code>).
<code>source_authenticate.go</code> implements <code>PasswordAuthenticator.Authenticate</code>; <code>source_sync.go</code>
implements periodic external-user sync (create/update/deactivate local users from LDAP search
results).</p>
<h3 id="pam-servicesauthsourcepam">PAM (<code>services/auth/source/pam</code>)<a href="#pam-servicesauthsourcepam" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Delegates username/password validation to the host's PAM stack. Config is just <code>ServiceName</code>
and <code>EmailDomain</code> (used to synthesize an email for auto-created users, since PAM carries no
email attribute).</p>
<h3 id="smtp-servicesauthsourcesmtp">SMTP (<code>services/auth/source/smtp</code>)<a href="#smtp-servicesauthsourcesmtp" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Authenticates by opening an SMTP connection and performing SMTP AUTH (PLAIN/LOGIN/CRAM-MD5).
Supports <code>AllowedDomains</code> restriction and <code>ForceSMTPS</code>/<code>SkipVerify</code> TLS controls — the latter
is a direct, reviewable TLS-downgrade knob if misconfigured in <code>app.ini</code>.</p>
<h3 id="oauth2-login-source-servicesauthsourceoauth2">OAuth2 login source (<code>services/auth/source/oauth2</code>)<a href="#oauth2-login-source-servicesauthsourceoauth2" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Configures an external OAuth2/OIDC identity provider via <code>github.com/markbates/goth</code>.
<code>source_callout.go</code> performs the redirect to the provider's authorization endpoint;
<code>routers/web/auth/oauth.go</code> handles the callback, token exchange, and user
creation/linking/admin-or-restricted-group derivation from claims. <code>source_sync.go</code> refreshes
stored OAuth2 refresh tokens and disables users whose upstream grant has been revoked
(<code>invalid_grant</code>).</p>
<h3 id="sspi-servicesauthsspigo">SSPI (<code>services/auth/sspi.go</code>)<a href="#sspi-servicesauthsspigo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Implements Windows Integrated Authentication (SPNEGO/Kerberos). Only activates for
<code>POST /user/login?auth_with_sspi=1</code>, so it can't interfere with any other route, and — because
a failed negotiation returns <code>401</code> immediately — <strong>must be the last method in the chain</strong>, or
it would short-circuit before Session/Basic/OAuth2 get a chance to run.</p>
<h3 id="httpsign-servicesauthhttpsigngo">HTTPSign (<code>services/auth/httpsign.go</code>)<a href="#httpsign-servicesauthhttpsigngo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Implements HTTP Signatures for ActivityPub federation, where the caller signs the request with
an SSH key pair. Two verification paths: <code>VerifyPubKey</code> (registered <code>PublicKey</code> by fingerprint)
and <code>VerifyCert</code> (SSH certificate signed by a trusted CA, matched against <code>TrustedUserCAKeys</code>).</p>
<h2 id="group-sync-external-groups-teams">Group Sync — External Groups → Teams<a href="#group-sync-external-groups-teams" class="heading-anchor" aria-label="Link">#</a></h2>
<p>When users authenticate via LDAP or OAuth2/OIDC, Gitea can auto-manage Organization/Team
membership from group claims/attributes, implemented centrally in
<code>services/auth/source/source_group_sync.go</code>. Configuration shape is a JSON mapping
(<code>GroupTeamMap</code>): <code>{"&lt;external-group&gt;": {"&lt;gitea-org&gt;": ["&lt;team1&gt;", "&lt;team2&gt;"]}}</code>.</p>
<p>Security-relevant behaviors:</p>
<ul>
<li><code>GroupTeamMapRemoval</code> controls whether membership is <strong>revoked</strong> when the user is no longer
  in the source group — if unset, membership only ever grows, which can be a slow privilege
  creep if group membership on the IdP side isn't audited.</li>
<li>For OAuth2, <code>AdminGroup</code>/<code>RestrictedGroup</code> claims can <strong>promote a user to admin or restrict
  them</strong>, based purely on trusting the identity provider's claims — misconfiguration of these
  claim names, or a compromised/misconfigured IdP, is a direct path to privilege escalation.</li>
<li><strong>Organizations and teams are never auto-created</strong> by group sync — if the mapped org/team
  doesn't exist, the mapping entry is silently skipped with a log warning, which limits blast
  radius but also means silent policy drift is possible if an admin renames a team.</li>
</ul>
<pre class="mermaid">sequenceDiagram
    participant IdP as LDAP/OAuth2 Provider
    participant Src as auth.Source (LDAP/OAuth2)
    participant Sync as source.SyncGroupsToTeams(Cached)
    participant Org as organization.Team

    IdP->>Src: returns user's groups (LDAP attr / OIDC claim)
    Src->>Sync: sourceUserGroups, GroupTeamMap, GroupTeamMapRemoval
    Sync->>Sync: resolveMappedMemberships() -> add-set / remove-set
    alt performRemoval
        Sync->>Org: RemoveTeamMember for mapped teams user no longer belongs to
    end
    Sync->>Org: AddTeamMember for mapped teams user now belongs to
    Org-->>Sync: membership updated</pre>
<h2 id="password-credential-login-flow-usersignin">Password / Credential Login Flow (<code>UserSignIn</code>)<a href="#password-credential-login-flow-usersignin" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>services/auth/signin.go</code> implements the shared username/password validation path used by
both <code>Basic.Verify</code> and the <code>/user/login</code> web form, per
<a href="../../docs/08-services/auth-providers.html">Auth Providers</a>:</p>
<pre class="mermaid">flowchart TD
    A["UserSignIn(ctx, username, password)"] --> B{Contains '@'?}
    B -->|yes| C[Look up EmailAddress; must be activated]
    B -->|no| D[Look up User by lower-cased name]
    C --> E{User found?}
    D --> E
    E -->|yes, has LoginSource| F["source.Cfg.(PasswordAuthenticator).Authenticate()"]
    F -->|success + not ProhibitLogin| G[Return user, source]
    F -->|fail| H[ErrUserNotExist / auth error]
    E -->|no exact match| I[Iterate ALL active sources]
    I --> J["authenticator.Authenticate(ctx, nil, username, password)"]
    J -->|success| G
    J -->|fail for all sources| H</pre>
<blockquote>
<p><strong>Timing-side-channel consideration for reviewers</strong>: branch <code>E --&gt;|no exact match| I</code> means
that when no user record matches, Gitea iterates <em>every</em> active source attempting
authentication anyway (rather than failing fast). This is a defensible mitigation against
username-enumeration-via-timing, and should not be "fixed" into an early return without
considering that trade-off if it ever surfaces in a diff under review.</p>
</blockquote>
<h2 id="authentication-authorization-handoff">Authentication → Authorization Handoff<a href="#authentication-authorization-handoff" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Authentication only establishes <strong>who</strong> is making the request (<code>ctx.Doer</code>). <strong>What</strong> they can
do is a wholly separate authorization step built on <code>AccessMode</code>/<code>Access</code>/<code>Permission</code> — see
<a href="authorization-permission-model.html">Authorization &amp; Permission Model</a> for the full mechanics
of that handoff, including the diagram of how <code>ctx.Doer</code> becomes a concrete allow/deny decision
per repository unit.</p>
