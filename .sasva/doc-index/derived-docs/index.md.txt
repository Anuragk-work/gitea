# Security Issues: Trivy & Opengrep Scanning Guide for Gitea

This documentation set is a **derived, focused reorganization** of Gitea's existing Markdown
documentation, built specifically to help a security engineer or scanner operator run **security
scanning tools** — such as **[Trivy](https://github.com/aquasecurity/trivy)** (dependency /
container / vulnerability scanning) and **[opengrep](https://github.com/opengrep/opengrep)**-class
static analysis tools (SAST / secret-detection / CI-config linting) — against this codebase, and to
understand what Gitea already does for security before layering more tooling on top.

> **Source material note:** no literal `security-issues/` documentation directory exists in this
> workspace. Every page in this set is instead synthesized from Gitea's general Markdown
> documentation tree — primarily root-level `SECURITY.md`, `CONTRIBUTING.md`, `WORKSPACE_ANALYSIS.md`,
> and the structured `docs/**/*.md` tree (architecture, services, database models, core modules,
> configuration, and build/CI/CD docs). See [`STYLE_GUIDE.md`](STYLE_GUIDE.md) for the full
> source-provenance table and the authoring conventions used throughout this set.

## Quick Start for Scanner Operators

If you just want to point Trivy/opengrep at this repository right now and know what to expect:

1. Read the [Security Posture Overview](01-overview/security-posture-overview.md) for the
   threat-model summary and the "what's covered vs. what's not" gap table.
2. Skim [Existing Security Tooling in CI](02-ci-security-tooling/existing-security-tooling-in-ci.md)
   so new scanning is **additive**, not duplicative, of `govulncheck`, `zizmor`, `actionlint`,
   `golangci-lint`/`depguard`, license scanning, and Renovate.
3. Go straight to [Running Trivy and Opengrep](06-scanning-playbook/running-trivy-and-opengrep.md)
   for concrete integration points in the existing pipeline and a consolidated opengrep
   rule-target backlog (with source-code pointers, not fabricated examples).
4. If a scan turns up something real and exploitable, route it through the
   [Vulnerability Disclosure Process](07-vulnerability-disclosure/reporting-process.md) instead of a
   public issue.

## Threat Model, at a Glance

This table is synthesized from the "Threat Model at a Glance" and "Where Trivy/Opengrep Fit" tables
in the [Security Posture Overview](01-overview/security-posture-overview.md) — read that page for
full detail, caveats, and citations.

| Threat Actor | Representative Risk | Primary Existing Mitigation | Deep-Dive Page |
|---|---|---|---|
| Unauthenticated external attacker | Auth-chain ordering bugs, session fixation, CSRF on state-changing routes | Ordered `auth.Method` chains, session-ID regeneration on sign-in, Fetch Metadata CSRF check | [Authentication & Sessions](03-attack-surface/authentication-and-sessions.md) |
| Authenticated low-privilege user | Privilege escalation via a missing/incorrect permission check on a new route | Three-layer `AccessMode`/`Access`/`Permission` model; `"owner"` intentionally excluded from string parsing | [Authorization / Permission Model](03-attack-surface/authorization-permission-model.md) |
| Malicious repository contributor | Stored XSS via a crafted README/wiki/issue/PR body or an overly permissive custom renderer | `bluemonday`-based sanitizer wired into the shared rendering pipeline (opt-out, not opt-in) | [Input Handling & XSS Defense](03-attack-surface/input-handling-and-xss-defense.md) |
| Repo/org admin (or attacker who compromises one) | SSRF via a webhook URL, migration source, or OAuth2 client pointed at internal/loopback/cloud-metadata hosts | `ALLOWED_HOST_LIST`, webhook HMAC signing, LFS JWT auth | [SSRF, Webhooks & Outbound Requests](03-attack-surface/ssrf-webhooks-and-outbound-requests.md) |
| Anyone with read access to config/deployment artifacts | Leaked `SECRET_KEY`, `INTERNAL_TOKEN`, DB/SMTP/LDAP credentials in plaintext | `*_FILE`/`*_URI` secret indirection, `ClearEnvConfigKeys()` env scrubbing | [Security-Relevant Settings](04-configuration-hardening/security-relevant-settings.md) |
| Supply-chain attacker | Poisoned dependency, tampered release artifact, unpinned build tool | Cosign + GPG dual-signing, Renovate pinning, `depguard` import denylist, license scanning | [Build, Release & Container Posture](05-supply-chain-and-container-security/build-release-and-container-posture.md) |
| Anyone relying on CI to catch known-vulnerable dependencies | A known Go CVE reaching `main` because `security-check` (`govulncheck`) is non-fatal | Partial — `govulncheck` runs but doesn't block merge | [Existing Security Tooling in CI](02-ci-security-tooling/existing-security-tooling-in-ci.md) |

## What This Set Covers, Section by Section

1. **[Security Posture Overview](01-overview/security-posture-overview.md)** — a threat-model-at-a-
   glance summary and an annotated architecture diagram showing where security controls sit in
   Gitea's layered-monolith backend (`routers/` → `services/` → `models/` → `xorm`, plus a shared
   `modules/` layer, and a Vue 3/TypeScript frontend). Also includes a "what Trivy/opengrep would add
   vs. what's already covered" gap table and suggested reading paths.
2. **[Existing Security Tooling in CI](02-ci-security-tooling/existing-security-tooling-in-ci.md)** —
   what's already automated (`govulncheck`, `zizmor`, `actionlint`, `golangci-lint`/`depguard`,
   license scanning via `go-licenses`/`rolldown-license-plugin`, Renovate) so new scans don't
   duplicate coverage, and explicitly flags the `govulncheck` non-fatal gap.
3. **Attack surface**, in four pages:
   - **[Authentication & Session Security](03-attack-surface/authentication-and-sessions.md)** —
     the auth chain, session/token handling, 2FA, LDAP secret encryption.
   - **[Authorization / Permission Model](03-attack-surface/authorization-permission-model.md)** —
     `AccessMode`/`Access`/`Permission`, org/team roles, restricted users.
   - **[Input Handling & XSS Defense](03-attack-surface/input-handling-and-xss-defense.md)** — HTML
     sanitization (`bluemonday`), URL scheme blocklist, iframe sandboxing.
   - **[SSRF, Webhooks & Outbound Requests](03-attack-surface/ssrf-webhooks-and-outbound-requests.md)**
     — `ALLOWED_HOST_LIST`, webhook signing, LFS JWT auth.
4. **[Security-Relevant Settings](04-configuration-hardening/security-relevant-settings.md)** — the
   `[security]`/`[cors]` settings catalog and other security-relevant `app.ini` configuration,
   including secret-supply mechanics and HTTP security headers.
5. **[Build, Release & Container Posture](05-supply-chain-and-container-security/build-release-and-container-posture.md)**
   — release signing, Docker/rootless container posture, dependency pinning, and license compliance.
6. **[Running Trivy and Opengrep](06-scanning-playbook/running-trivy-and-opengrep.md)** — concrete
   guidance for slotting Trivy and opengrep into this repository's existing pipeline, and mapping
   findings back to the attack-surface pages above, plus a consolidated rule-target backlog.
7. **[Vulnerability Disclosure Process](07-vulnerability-disclosure/reporting-process.md)** — the
   official process (per `SECURITY.md`) for routing any real, exploitable finding responsibly
   instead of filing a public issue.
