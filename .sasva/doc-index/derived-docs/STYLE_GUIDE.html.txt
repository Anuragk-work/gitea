<h1>Documentation Style & Conventions (Internal Reference)</h1>
<h1 id="documentation-style-conventions-internal-reference">Documentation Style &amp; Conventions (Internal Reference)</h1>
<blockquote>
<p>This page is an internal authoring reference for the <code>security-issues</code> derived documentation set.
It is not part of the primary navigation flow, but it is kept in the tree so the conventions used
across every page in <code>derived-docs/</code> are traceable and consistent. Later phases should follow these
rules exactly; do not introduce new formatting conventions mid-way through the set.</p>
</blockquote>
<h2 id="purpose-of-this-documentation-set">Purpose of This Documentation Set<a href="#purpose-of-this-documentation-set" class="heading-anchor" aria-label="Link">#</a></h2>
<p>This derived wiki reorganizes Gitea's existing Markdown documentation (root-level <code>SECURITY.md</code>,
<code>CONTRIBUTING.md</code>, <code>WORKSPACE_ANALYSIS.md</code>, and the <code>docs/**/*.md</code> tree) around a single focus:
<strong>finding and reasoning about security issues using tools like Trivy (SCA / dependency / container
vulnerability scanning) and opengrep (Semgrep-class SAST / secret-detection / CI-config linting)</strong>.</p>
<p>No new facts are invented. Every claim in every page must trace back to something actually stated in
the source <code>.md</code> files. Where the source is silent or ambiguous, pages say so explicitly rather than
guessing.</p>

<p>Every deliverable page must cite the specific source file(s) it draws from, using the format described
below, so a reader can verify claims against the original documentation.</p>
<h2 id="writing-conventions">Writing Conventions<a href="#writing-conventions" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="heading-levels">Heading Levels<a href="#heading-levels" class="heading-anchor" aria-label="Link">#</a></h3>
<ul>
<li><code>#</code> (H1): exactly one per page, matching the page title. No page has more than one H1.</li>
<li><code>##</code> (H2): major sections of the page (e.g., "Threat Model", "Configuration Reference").</li>
<li><code>###</code> (H3): sub-topics within a section (e.g., specific settings, specific auth providers).</li>
<li>Avoid H4+ except in rare cases (e.g., deeply nested reference tables); prefer restructuring instead.</li>
</ul>
<h3 id="citations">Citations<a href="#citations" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Cite source documentation inline, in prose, the first time a fact from that source is introduced on a
page, using this pattern:</p>
<blockquote>
<p>As described in the <a href="../08-services/auth-providers.html">Auth Providers docs</a>...</p>
</blockquote>
<p>Because these derived pages live under <code>derived-docs/</code>, not under the original <code>docs/</code> tree, citation
links should point back to the <em>original</em> source path relative to the repository root when the source
lives outside <code>derived-docs/</code> (e.g. <code>../../docs/08-services/auth-providers.md</code> from a page two levels
deep, or plain prose citation with the filename in backticks — e.g. <code>`docs/08-services/auth-providers.md`</code>
— when a working relative link cannot be guaranteed). Prefer the backtick-filename citation style for
robustness across the final directory layout; use relative Markdown links for cross-references <em>within</em>
<code>derived-docs/</code> itself, since those paths are fully controlled by this plan.</p>
<h3 id="cross-links-within-this-wiki">Cross-Links Within This Wiki<a href="#cross-links-within-this-wiki" class="heading-anchor" aria-label="Link">#</a></h3>
<ul>
<li>Same directory: <code>[Other Page](other-page.md)</code></li>
<li>Parent directory: <code>[Home](../index.md)</code></li>
<li>Sibling directory: <code>[Attack Surface](../03-attack-surface/authentication-and-sessions.md)</code></li>
<li>Always use relative paths, never absolute paths starting with <code>/</code>.</li>
</ul>
<h3 id="mermaid-diagrams">Mermaid Diagrams<a href="#mermaid-diagrams" class="heading-anchor" aria-label="Link">#</a></h3>
<ul>
<li>Use fenced <code>```mermaid</code> blocks.</li>
<li>Raw <code>&lt;</code>/<code>&gt;</code> characters only — never HTML-entity-escape inside a mermaid block.</li>
<li>Generics/parameterized labels: use <code>~T~</code> or quote the whole label (e.g. <code>A["List&lt;T&gt;"]</code>).</li>
<li>Line breaks inside a node label: use <code>&lt;br/&gt;</code> inside a quoted label.</li>
<li>Keep diagrams to 5–15 nodes; prefer several small focused diagrams over one large one.</li>
<li>Every diagram must be traceable to something described in the source docs (e.g., the layered-monolith
  diagram in <code>WORKSPACE_ANALYSIS.md</code> is the base for the annotated security-control diagram in the
  overview page) — diagrams may add structure/callouts not spelled out verbatim in prose, but must not
  invent components that don't exist in the source material.</li>
</ul>
<h3 id="tables">Tables<a href="#tables" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Use pipe tables for:
- Settings/config references (name, purpose, default, security implication)
- Tool comparisons (e.g., existing CI tool vs. Trivy vs. opengrep — what each covers)
- Threat-model summaries (threat actor → relevant page → existing mitigation)</p>
<h3 id="code-blocks">Code Blocks<a href="#code-blocks" class="heading-anchor" aria-label="Link">#</a></h3>
<ul>
<li>Preserve real snippets (Makefile targets, <code>app.ini</code> keys, YAML workflow fragments, Go type/field
  names as described in prose) exactly as named in the source docs.</li>
<li>Never fabricate example code that isn't grounded in something the source docs actually describe.</li>
<li>Use language tags: <code>ini</code> for <code>app.ini</code> fragments, <code>yaml</code> for workflow snippets, <code>makefile</code> for Make
  targets, <code>go</code> only when quoting a type/field name exactly as named in source prose (not real Go
  source, which was never read directly).</li>
</ul>
<h3 id="tone-framing">Tone &amp; Framing<a href="#tone-framing" class="heading-anchor" aria-label="Link">#</a></h3>
<ul>
<li>Written for a security engineer or scanner operator who needs to (a) understand what Gitea already
  does for security, and (b) know where to point Trivy/opengrep and what to do with results.</li>
<li>Explicitly call out gaps/hardening opportunities noted in source docs (e.g., <code>govulncheck</code> currently
  being non-fatal in CI) rather than glossing over them.</li>
<li>Use <code>&gt;</code> blockquotes for caveats, gaps, and "verify before relying on this" notes — especially where
  the source material itself flags something as unverified.</li>
</ul>
