<h1>Security-Relevant Configuration & Secrets Management</h1>
<h1 id="security-relevant-configuration-secrets-management">Security-Relevant Configuration &amp; Secrets Management</h1>
<p>Gitea's entire configuration surface is a single INI file (conventionally <code>custom/conf/app.ini</code>),
loaded and typed by <code>modules/setting/*.go</code>. Most of it is operational tuning, but a specific subset
of sections and keys directly control the instance's security posture: encryption/signing secrets,
password policy, HTTP security headers, reverse-proxy trust, outbound-request allowlisting, and
session/cookie behavior. This page catalogs that subset, explains how secrets are supplied and
protected in the loading pipeline itself, and flags what a scanner operator (Trivy for
dependencies/containers, opengrep for source/secret patterns) should specifically look for in this
repository's configuration files and templates.</p>
<p>This page synthesizes <code>docs/04-configuration/settings-catalog.md</code>, <code>docs/03-getting-started/configuration-app-ini.md</code>,
<code>docs/08-services/auth-providers.md</code>, and <code>docs/09-core-modules/notify-mailer-webhook.md</code>.</p>
<h2 id="how-configuration-reaches-the-process-and-why-it-matters-for-secrets">How Configuration Reaches the Process (and Why It Matters for Secrets)<a href="#how-configuration-reaches-the-process-and-why-it-matters-for-secrets" class="heading-anchor" aria-label="Link">#</a></h2>
<p>As described in the <a href="../../docs/04-configuration/settings-catalog.html">Settings Catalog</a>, Gitea's
config subsystem loads <code>app.ini</code> through <code>gopkg.in/ini.v1</code>, then layers environment variable
overrides on top, before handing typed values to package-level Go variables:</p>
<pre class="mermaid">flowchart LR
    A["custom/conf/app.ini"] --> B["ini.File"]
    E["GITEA__SECTION__KEY env vars"] --> C["EnvironmentToConfig()"]
    C --> B
    B --> D["ConfigProvider"]
    D --> F["loadSecurityFrom(cfg)<br/>security.go"]
    F --> G["setting.SecretKey<br/>setting.InternalToken"]
    H["GITEA__SECURITY__SECRET_KEY__FILE"] -.->|"reads file contents"| C</pre>
<p>Two mechanics are directly relevant to secret hygiene and to what a secret-scanner (opengrep-class
tooling) should be configured to recognize:</p>
<ol>
<li><strong><code>GITEA__SECTION__KEY=value</code></strong> — any <code>app.ini</code> key can be overridden or supplied purely via
   environment variable. <code>SECTION</code>/<code>KEY</code> are joined with a double underscore, and non-<code>[A-Z0-9_]</code>
   characters (dots, dashes in sub-section names like <code>[log.console]</code>) are hex-escaped as
   <code>_0x2E_</code>/<code>_0x2D_</code>.</li>
<li><strong><code>GITEA__SECTION__KEY__FILE=/path</code></strong> — the standard pattern for injecting secrets from
   Docker/Kubernetes secret mounts <em>without</em> putting the literal secret value in the environment
   or in <code>app.ini</code> at all. <code>EnvironmentToConfig</code> reads the file's contents (trimming a trailing
   newline) and uses that as the value. Gitea itself uses this pattern for the two most sensitive
   settings:</li>
</ol>
<pre class="highlight"><code class="language-bash">GITEA__SECURITY__SECRET_KEY__FILE=/run/secrets/gitea_secret_key
GITEA__MAILER__PASSWD__FILE=/run/secrets/smtp_password</code></pre>
<p>Both <code>SECRET_KEY</code> and <code>INTERNAL_TOKEN</code> also support an equivalent <code>*_URI</code> form directly in
   <code>app.ini</code> (<code>SECRET_KEY_URI = file:/etc/gitea/secret_key</code>), mutually exclusive with setting the
   plaintext value inline.</p>
<blockquote>
<p><strong>Scanner takeaway:</strong> when secret-scanning this repository or a deployed configuration bundle,
treat literal, non-empty values for <code>SECRET_KEY</code>, <code>INTERNAL_TOKEN</code>, <code>[database] PASSWD</code>,
<code>[mailer] PASSWD</code>, and any LDAP <code>BindPassword</code>/OAuth2 client secret written directly into an
<code>app.ini</code> or Kubernetes <code>ConfigMap</code> (as opposed to a <code>Secret</code> or a <code>*_FILE</code>/<code>*_URI</code> reference) as
a finding. The <code>__FILE</code>/<code>_URI</code> indirection pattern is the "correct" answer these scanners should
not flag; a literal secret string is the anti-pattern they should.</p>
</blockquote>
<p><code>ClearEnvConfigKeys()</code> additionally unsets every <code>GITEA__*</code> variable from the process environment
once installation completes, specifically so that environment-supplied secrets are not inherited by
subprocesses Gitea spawns (e.g. git hooks) unless intentionally passed through — worth knowing when
reasoning about whether a secret leaked via <code>GITEA__...</code> env vars could leak further into subprocess
environments.</p>
<h2 id="the-security-section-core-secrets-and-policy">The <code>[security]</code> Section — Core Secrets and Policy<a href="#the-security-section-core-secrets-and-policy" class="heading-anchor" aria-label="Link">#</a></h2>
<p>As documented in <a href="../../docs/03-getting-started/configuration-app-ini.html">Configuration (<code>app.ini</code>)</a>
and the <a href="../../docs/04-configuration/settings-catalog.html">Settings Catalog</a> (<code>security.go</code>), this is
the single most security-dense section in the entire configuration surface.</p>
<table>
<thead>
<tr>
<th>Key</th>
<th>Purpose</th>
<th>Security implication</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>SECRET_KEY</code> (or <code>SECRET_KEY_URI</code>)</td>
<td>Symmetric key used to encrypt data at rest — e.g. TOTP 2FA shared secrets (via an MD5-derived key, see below), LDAP bind passwords</td>
<td><strong>Losing it means losing that encrypted data.</strong> Leaking it means an attacker who also has DB access can decrypt those secrets. Auto-generated by the install wizard; back it up, never commit it.</td>
</tr>
<tr>
<td><code>INTERNAL_TOKEN</code> (or <code>INTERNAL_TOKEN_URI</code>)</td>
<td>Secret used to authenticate internal/loopback API calls, e.g. from git hooks calling back into the <code>gitea web</code> process</td>
<td>Also auto-generated at install; a leaked <code>INTERNAL_TOKEN</code> could let a local process impersonate Gitea's own hook-callback path.</td>
</tr>
<tr>
<td><code>INSTALL_LOCK</code></td>
<td><code>false</code> by default; set <code>true</code> to permanently disable the install wizard</td>
<td>Leaving this <code>false</code> in a running production instance re-exposes the install wizard endpoint.</td>
</tr>
<tr>
<td><code>LOGIN_REMEMBER_DAYS</code></td>
<td>Lifetime of "remember me" persistent login cookies (default 31)</td>

</tr>
<tr>
<td><code>MIN_PASSWORD_LENGTH</code></td>
<td>Minimum password length (default 8)</td>
<td>Low defaults should be raised for hardened deployments.</td>
</tr>
<tr>
<td><code>PASSWORD_HASH_ALGO</code></td>
<td><code>argon2</code>, <code>pbkdf2</code> (default), <code>scrypt</code>, or <code>bcrypt</code></td>
<td><code>argon2</code>/<code>bcrypt</code>/<code>scrypt</code> are generally preferred over <code>pbkdf2</code> for modern password-hashing guidance; worth confirming the deployment's chosen algorithm against current recommendations.</td>
</tr>
<tr>
<td><code>PASSWORD_CHECK_PWN</code></td>
<td><code>false</code> by default; checks new passwords against haveibeenpwned.com</td>
<td>Off by default — a hardening opportunity worth calling out explicitly, per this documentation set's convention of not glossing over gaps.</td>
</tr>
<tr>
<td><code>TWO_FACTOR_AUTH</code></td>
<td>Set to <code>"enforced"</code> to require 2FA for all users</td>
<td>Not enforced by default.</td>
</tr>
<tr>
<td><code>DISABLE_GIT_HOOKS</code></td>
<td><code>true</code> by default</td>
<td>Governs whether users with hook privileges may install custom Git hooks — a powerful, potentially dangerous capability if flipped to <code>false</code>; treat any deployment with this <code>false</code> as higher-risk / needing extra review.</td>
</tr>
<tr>
<td><code>DISABLE_WEBHOOKS</code>, <code>IMPORT_LOCAL_PATHS</code></td>
<td>Feature toggles</td>
<td>Both carry security implications per the source docs (webhook SSRF surface, local-filesystem-path import capability) — see <a href="../03-attack-surface/ssrf-webhooks-and-outbound-requests.html">SSRF, Webhooks &amp; Outbound Requests</a>.</td>
</tr>
<tr>
<td><code>REVERSE_PROXY_AUTHENTICATION_USER</code> / <code>..._EMAIL</code> / <code>..._FULL_NAME</code></td>
<td>Header names trusted for reverse-proxy SSO</td>
<td><strong>Only safe if the reverse proxy is guaranteed to strip these headers from untrusted client input.</strong> A misconfigured proxy that passes through a client-supplied version of the trusted header is a full authentication bypass.</td>
</tr>
<tr>
<td><code>REVERSE_PROXY_TRUSTED_PROXIES</code>, <code>REVERSE_PROXY_LIMIT</code></td>
<td>Which upstream hops are trusted to set those headers</td>
<td>Misconfiguration here is the concrete control that prevents the bypass above.</td>
</tr>
<tr>
<td><code>X_FRAME_OPTIONS</code>, <code>X_CONTENT_TYPE_OPTIONS</code>, <code>CONTENT_SECURITY_POLICY_GENERAL</code></td>
<td>HTTP security response headers</td>
<td>See <a href="#http-security-headers">HTTP Security Headers</a> below.</td>
</tr>
<tr>
<td><code>ALLOWED_HOST_LIST</code></td>
<td>Restricts which hosts webhook/OAuth2 clients are allowed to call: <code>loopback</code>, <code>private</code>, <code>external</code>, <code>*</code>, CIDRs, or wildcard hostnames</td>
<td>This is Gitea's primary <strong>SSRF control</strong> for outbound webhook/OAuth2/migration requests — see <a href="../03-attack-surface/ssrf-webhooks-and-outbound-requests.html">SSRF, Webhooks &amp; Outbound Requests</a> for the enforcement path.</td>
</tr>
</tbody>
</table>
<pre class="highlight"><code class="language-ini">[security]
INSTALL_LOCK = false        ; set true to disable the install wizard entirely
SECRET_KEY =                ; VERY IMPORTANT: encrypts things like 2FA secrets — losing it means losing that data
;SECRET_KEY_URI = file:/etc/gitea/secret_key   ; mutually exclusive with SECRET_KEY
INTERNAL_TOKEN =            ; secret used for internal (loopback) API calls, e.g. from git hooks
;INTERNAL_TOKEN_URI = file:/etc/gitea/internal_token
LOGIN_REMEMBER_DAYS = 31
MIN_PASSWORD_LENGTH = 8
PASSWORD_HASH_ALGO = pbkdf2 ; argon2, pbkdf2, scrypt, or bcrypt
PASSWORD_CHECK_PWN = false  ; check against haveibeenpwned.com
TWO_FACTOR_AUTH =           ; set to "enforced" to require 2FA for all users</code></pre>
<blockquote>
<p>As noted in <a href="../../docs/03-getting-started/configuration-app-ini.html">Configuration (<code>app.ini</code>)</a>:
<code>SECRET_KEY</code> and <code>INTERNAL_TOKEN</code> are auto-generated the first time the install wizard runs
(<code>modules/generate</code>, <code>routers/install/install.go</code>) — operators rarely set them by hand, but <strong>must
back them up</strong>. A regenerated <code>SECRET_KEY</code> on an existing database instantly makes any data it had
encrypted (2FA secrets, certain source credentials) unrecoverable.</p>
</blockquote>
<h3 id="where-secret_key-is-actually-used-to-encrypt-data">Where <code>SECRET_KEY</code> Is Actually Used to Encrypt Data<a href="#where-secret_key-is-actually-used-to-encrypt-data" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Per <a href="../../docs/08-services/auth-providers.html">Auth Providers</a>, <code>setting.SecretKey</code> is not just a
theoretical value — it is the concrete key material behind at least two at-rest encryption
mechanisms:</p>
<ul>
<li><strong>TOTP 2FA shared secrets</strong> (<code>models/auth/twofactor.go</code>): AES-encrypted at rest, with the AES key
  <em>derived from <code>setting.SecretKey</code> via MD5</em> (<code>getEncryptionKey</code>), then Base64-encoded into the
  <code>Secret</code> column.</li>
<li><strong>LDAP <code>BindDN</code>/<code>BindPassword</code></strong> (<code>services/auth/source/ldap/source.go</code>): encrypted at rest via
  <code>secret.EncryptSecret</code> in the source's <code>ToDB</code> method before being persisted to the login-source
  table.</li>
</ul>
<blockquote>
<p><strong>Note on the MD5-derived key:</strong> the source documentation explicitly calls out that the TOTP
encryption key is derived from <code>SecretKey</code> "via MD5." MD5 is a broken hash for collision
resistance, but here it is used purely as a key-derivation step, not for integrity/collision
purposes — still, this is exactly the kind of <code>crypto/md5</code> usage that an opengrep SAST rule
tuned for "weak cryptographic primitive" will flag in this codebase, and it is worth triaging
against this documented, intentional design rather than assuming it is an oversight. See the
<a href="../06-scanning-playbook/running-trivy-and-opengrep.html">Scanning Playbook</a> for how to route this
kind of finding.</p>
</blockquote>
<h3 id="http-security-headers">HTTP Security Headers<a href="#http-security-headers" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>X_FRAME_OPTIONS</code>, <code>X_CONTENT_TYPE_OPTIONS</code>, and <code>CONTENT_SECURITY_POLICY_GENERAL</code> in <code>[security]</code>
configure standard defensive response headers. Per the Settings Catalog, <code>security.go</code> additionally
<strong>cross-reads <code>[cors]</code></strong> for <code>X_FRAME_OPTIONS</code> handling — meaning CORS policy and the frame-options
header are not fully independent and should be reviewed together, not in isolation, when hardening
either one.</p>
<h2 id="the-cors-section">The <code>[cors]</code> Section<a href="#the-cors-section" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Per the Settings Catalog, <code>cors.go</code> owns Cross-Origin Resource Sharing policy for the API
(<code>[cors]</code> section). The source documentation notes this section is cross-referenced by
<code>security.go</code> for <code>X_FRAME_OPTIONS</code> — a scanner or reviewer checking CORS configuration should
check both sections together rather than assuming <code>[cors]</code> is self-contained. Beyond that
cross-reference, the settings catalog does not enumerate individual <code>[cors]</code> keys in the material
reviewed for this page; treat the exact key list as something to verify directly against
<code>custom/conf/app.example.ini</code> before writing a hardening rule against it, per this documentation
set's convention of flagging gaps rather than guessing at specifics not confirmed in source docs.</p>
<h2 id="session-cookie-configuration-session">Session &amp; Cookie Configuration — <code>[session]</code><a href="#session-cookie-configuration-session" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The Settings Catalog maps <code>session.go</code> to the <code>[session]</code> section, describing it as the "web
session store backend and cookie behavior." The narrative <code>app.ini</code> walkthrough does not expand on
individual <code>[session]</code> keys beyond that mapping, so this page does not fabricate a key-by-key table
for it — but it is directly relevant to two mechanisms documented elsewhere in this set:</p>
<ul>
<li><strong>Session cookie behavior</strong> underlies the <code>Session</code> auth method (<code>services/auth/session.go</code>),
  which reads the <code>uid</code> key from the session store; <code>handleSignIn</code> (<code>services/auth/auth.go</code>)
  <strong>regenerates the session ID on login</strong> as session-fixation protection.</li>
<li><strong>Cross-site request protection</strong> for session-authenticated browser requests is <em>not</em> a
  classic CSRF-token-in-<code>[session]</code> mechanism in this codebase — per
  <a href="../../docs/02-architecture/request-lifecycle.html">Request Lifecycle</a>, Gitea uses Go's standard
  library <code>http.NewCrossOriginProtection().Check(ctx.Req)</code>, a <strong>Fetch Metadata</strong>
  (<code>Sec-Fetch-Site</code> header) based cross-site check, applied in <code>verifyAuthWithOptions</code>
  (<code>routers/web/web.go</code>) unless <code>SignOutRequired</code> or <code>DisableCrossOriginProtection</code> is set for a
  route. Routes that must legitimately accept cross-origin requests (<code>git</code> smart-HTTP, PAT/OAuth2
  API access) explicitly opt out.</li>
</ul>
<h3 id="session-cookie-and-remember-me-security">Session, Cookie, and Remember-Me Security<a href="#session-cookie-and-remember-me-security" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Two independent persistence mechanisms exist and should not be confused when reviewing session
security, per <a href="../../docs/08-services/auth-providers.html">Auth Providers</a>:</p>
<ol>
<li><strong>Session cookie</strong> (short-lived, backed by <code>[session]</code> store config) — carries only a <code>uid</code>
   lookup key; regenerated at login.</li>
<li><strong>"Remember me" auth token cookie</strong> (<code>LOGIN_REMEMBER_DAYS</code> in <code>[security]</code>) — a <em>separate</em>
   mechanism (<code>models/auth/auth_token.go</code>, <code>services/auth/auth_token.go</code>) modeled on
   <a href="https://paragonie.com/blog/2015/04/secure-authentication-php-with-long-term-persistence">Paragon Initiative's secure remember-me design</a>.
   The cookie value is <code>id:token</code>; the server stores only <code>TokenHash = sha256(token)</code>. Critically,
   <strong>the hash is rotated on every login</strong> (<code>RegenerateAuthToken</code>) while the <code>id</code> stays the same —
   if a stolen, already-used token is replayed, the hash mismatch triggers immediate revocation
   (<code>DeleteAuthTokenByID</code>) of that device's token, forcing re-authentication. This is a concrete,
   documented anti-token-theft control worth being aware of before assuming a long
   <code>LOGIN_REMEMBER_DAYS</code> value is purely a liability.</li>
</ol>

<h2 id="dynamic-runtime-editable-settings-are-explicitly-not-security-sensitive-by-design">Dynamic (Runtime-Editable) Settings Are Explicitly Not Security-Sensitive by Design<a href="#dynamic-runtime-editable-settings-are-explicitly-not-security-sensitive-by-design" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Per the <a href="../../docs/04-configuration/settings-catalog.html">Settings Catalog</a>, a small, deliberately
narrow set of options are <strong>dynamic</strong> — editable at runtime from <strong>Admin Panel → Configuration →
Config Settings</strong> without a restart, backed by <code>config.Option[T]</code> and persisted to the
<code>system_setting</code> database table instead of <code>app.ini</code>. The documented project convention is directly
relevant to hardening review:</p>
<blockquote>
<p>Static <code>app.ini</code> options are favored for anything that "is security-sensitive and should be
controlled by the file-system/deployment owner, not a web-authenticated admin session."
Dynamic options are reserved for settings that are "safe for a web admin to toggle without
SSH/file access to the host."</p>
</blockquote>
<p>The currently registered dynamic options — <code>picture.disable_gravatar</code>,
<code>picture.enable_federated_avatar</code>, <code>repository.open-with.editor-apps</code>,
<code>repository.git-guide-remote-name</code>, <code>instance.web_banner</code>, <code>instance.maintenance_mode</code> — are all
cosmetic/availability toggles, consistent with that stated convention. None of the <code>[security]</code>,
<code>[cors]</code>, <code>[webhook]</code>, <code>[mailer]</code>, or <code>[database]</code> secret-bearing keys catalogued above are dynamic;
they can only be changed by someone with file-system or environment-variable access to the deployed
instance, which is itself a deliberate security boundary — worth confirming stays true if new
dynamic options are ever proposed for security-adjacent settings.</p>
<h2 id="configuration-hardening-checklist">Configuration Hardening Checklist<a href="#configuration-hardening-checklist" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A condensed checklist derived from the settings above, for use when auditing a specific Gitea
deployment's <code>app.ini</code> / environment configuration (not a substitute for reading the full
<a href="../../docs/04-configuration/settings-catalog.html">Settings Catalog</a>, only a starting point):</p>
<ul>
<li>[ ] <code>INSTALL_LOCK = true</code> in production.</li>
<li>[ ] <code>SECRET_KEY</code> and <code>INTERNAL_TOKEN</code> are set via <code>*_URI</code>/<code>*_FILE</code> indirection (or at minimum
      backed up securely), never committed to version control.</li>
<li>[ ] <code>MIN_PASSWORD_LENGTH</code> raised above the default <code>8</code> if policy requires it.</li>
<li>[ ] <code>PASSWORD_HASH_ALGO</code> reviewed against current guidance (<code>argon2</code>/<code>bcrypt</code>/<code>scrypt</code> vs. the
      default <code>pbkdf2</code>).</li>
<li>[ ] <code>PASSWORD_CHECK_PWN</code> considered — off by default.</li>
<li>[ ] <code>TWO_FACTOR_AUTH = enforced</code> considered for sensitive instances — not enforced by default.</li>
<li>[ ] <code>DISABLE_GIT_HOOKS</code> left at its default <code>true</code> unless custom-hook installation by
      non-admin users is an explicit, reviewed requirement.</li>
<li>[ ] <code>REVERSE_PROXY_AUTHENTICATION_*</code> only enabled with a verified, header-stripping trusted
      proxy in front, and <code>REVERSE_PROXY_TRUSTED_PROXIES</code> scoped tightly.</li>
<li>[ ] <code>ALLOWED_HOST_LIST</code> reviewed — see the SSRF control discussion in
      <a href="../03-attack-surface/ssrf-webhooks-and-outbound-requests.html">SSRF, Webhooks &amp; Outbound Requests</a>.</li>
<li>[ ] <code>[webhook] SKIP_TLS_VERIFY</code> and <code>[mailer] FORCE_TRUST_SERVER_CERT</code> both <code>false</code> in
      production.</li>
<li>[ ] No literal secret values (<code>SECRET_KEY</code>, <code>INTERNAL_TOKEN</code>, <code>[database] PASSWD</code>,
      <code>[mailer] PASSWD</code>, LDAP <code>BindPassword</code>, OAuth2 client secrets) committed into any tracked
      <code>app.ini</code>, Helm values file, or Kubernetes <code>ConfigMap</code> (as opposed to a <code>Secret</code> resource or
      file-based indirection).</li>
</ul>

      var mh=[];for(var m=0;m<h.h.length;m++){if(h.h[m].toLowerCase().indexOf(q)>=0)mh.push(h.h[m]);}
      for(var n=0;n<Math.min(mh.length,2);n++){html+='<div class="search-heading">↳ '+mh[n]+'</div>';}
    }
    if(!hits.length)html='<div style="padding:8px 12px;color:var(--text-dim);font-size:0.8rem">No results</div>';

(function(){

  function _addMermaidButtons(){
    document.querySelectorAll('.mermaid,pre.mermaid').forEach(function(el){
      if(el.dataset.expandAdded)return;
      el.dataset.expandAdded='1';
      // Wrap in a div so the button is a sibling of pre, not inside it

      wrapper.style.cssText='position:relative;display:inline-block;width:100%;';
      el.parentNode.insertBefore(wrapper,el);
      wrapper.appendChild(el);
      var btn=document.createElement('button');
      btn.className='mermaid-expand';btn.textContent='⛶';btn.title='Expand diagram';
      btn.addEventListener('click',function(e){
        e.stopPropagation();
        var clone=el.cloneNode(true);
        delete clone.dataset.expandAdded;
        clone.removeAttribute('data-expand-added');
        clone.style.cssText='background:none;border:none;padding:0;margin:0;text-align:center;min-width:70vw;max-width:90vw;';
        // Clear overlay content safely, keep close button
        overlayInner.innerHTML='';
        var closeBtn=document.createElement('button');
        closeBtn.className='mermaid-overlay-close';closeBtn.textContent='×';closeBtn.title='Close';
        closeBtn.addEventListener('click',function(){overlay.classList.remove('open');});
        overlayInner.appendChild(clone);
        overlayInner.appendChild(closeBtn);
        overlay.classList.add('open');
        // Re-run mermaid on the clone after it's in the DOM
        setTimeout(function(){
          if(window.mermaid){
            try{mermaid.run({nodes:[clone]});}catch(err){}
          }
        },50);
      });
      wrapper.appendChild(btn);
    });
  }
  // Wait for mermaid to finish rendering before adding buttons (mermaid init runs above)
  setTimeout(_addMermaidButtons,800);
  if(overlay){
    overlay.addEventListener('click',function(e){if(e.target===overlay)overlay.classList.remove('open');});
    document.addEventListener('keydown',function(e){if(e.key==='Escape')overlay.classList.remove('open');});
  }
  // Code copy buttons
  document.querySelectorAll('pre').forEach(function(pre){
    if(pre.classList.contains('mermaid'))return;
    var btn=document.createElement('button');
    btn.className='code-copy';btn.textContent='Copy';
    btn.addEventListener('click',function(){
      var code=pre.querySelector('code');
      var text=code?code.textContent:pre.textContent;
      navigator.clipboard.writeText(text).then(function(){btn.textContent='Copied!';setTimeout(function(){btn.textContent='Copy';},2000);});
    });
    pre.appendChild(btn);
  });
  // Back to top
  var btt=document.getElementById('back-to-top');
  if(btt){
    window.addEventListener('scroll',function(){btt.style.display=window.scrollY>300?'flex':'none';});
    btt.addEventListener('click',function(){window.scrollTo({top:0,behavior:'smooth'});});
  }
  // TOC active scroll tracking
  var tocLinks=document.querySelectorAll('.toc-aside a[data-anchor]');
  if(tocLinks.length>0){
    var headingEls=[];
    tocLinks.forEach(function(l){var el=document.getElementById(l.dataset.anchor);if(el)headingEls.push({el:el,link:l});});
    var tocAside=document.querySelector('.toc-aside');
    var onScroll=function(){
      var scrollPos=window.scrollY+80;
      var active=null;
      for(var i=0;i<headingEls.length;i++){if(headingEls[i].el.offsetTop<=scrollPos)active=headingEls[i];}
      tocLinks.forEach(function(l){l.classList.remove('toc-active');});
      if(active){
        active.link.classList.add('toc-active');
        // Scroll active link into view within the TOC panel, not the page
        if(tocAside){
          var linkTop=active.link.offsetTop-tocAside.offsetTop;
          var visibleTop=tocAside.scrollTop;
          var visibleBottom=visibleTop+tocAside.clientHeight;
          if(linkTop<visibleTop+40||linkTop>visibleBottom-40){
            tocAside.scrollTop=linkTop-tocAside.clientHeight/2;
          }
        }
      }
    };
    window.addEventListener('scroll',onScroll);
    onScroll();
    // Prevent TOC links from scrolling the TOC panel to top on click
    tocLinks.forEach(function(l){
      l.addEventListener('click',function(e){
        e.preventDefault();
        var anchor=l.dataset.anchor;
        var target=document.getElementById(anchor);
        if(target){target.scrollIntoView({behavior:'smooth',block:'start'});}
      });
    });
  }
  // Persist sidebar scroll position across page navigations
  var sidebarEl=document.querySelector('nav.sidebar');
  if(sidebarEl){
    var sidebarKey='sasva-sidebar-scroll';
    // Restore scroll position on page load
    var savedScroll=sessionStorage.getItem(sidebarKey);
    if(savedScroll){sidebarEl.scrollTop=parseInt(savedScroll,10);}
    // Save scroll position before navigating away
    document.querySelectorAll('#sidebar-nav-links a').forEach(function(a){
      a.addEventListener('click',function(){
        sessionStorage.setItem(sidebarKey,String(sidebarEl.scrollTop));
      });
    });
    // Also scroll active item into view on load
    var activeLink=sidebarEl.querySelector('a.active');
    if(activeLink&&!savedScroll){
      var linkOffset=activeLink.offsetTop-sidebarEl.offsetTop;
      sidebarEl.scrollTop=Math.max(0,linkOffset-sidebarEl.clientHeight/2);
    }
  }
})();
