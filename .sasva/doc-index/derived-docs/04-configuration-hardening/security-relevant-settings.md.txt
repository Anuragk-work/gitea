# Security-Relevant Configuration & Secrets Management

Gitea's entire configuration surface is a single INI file (conventionally `custom/conf/app.ini`),
loaded and typed by `modules/setting/*.go`. Most of it is operational tuning, but a specific subset
of sections and keys directly control the instance's security posture: encryption/signing secrets,
password policy, HTTP security headers, reverse-proxy trust, outbound-request allowlisting, and
session/cookie behavior. This page catalogs that subset, explains how secrets are supplied and
protected in the loading pipeline itself, and flags what a scanner operator (Trivy for
dependencies/containers, opengrep for source/secret patterns) should specifically look for in this
repository's configuration files and templates.

This page synthesizes `docs/04-configuration/settings-catalog.md`, `docs/03-getting-started/configuration-app-ini.md`,
`docs/08-services/auth-providers.md`, and `docs/09-core-modules/notify-mailer-webhook.md`.

## How Configuration Reaches the Process (and Why It Matters for Secrets)

As described in the [Settings Catalog](../../docs/04-configuration/settings-catalog.md), Gitea's
config subsystem loads `app.ini` through `gopkg.in/ini.v1`, then layers environment variable
overrides on top, before handing typed values to package-level Go variables:

```mermaid
flowchart LR
    A["custom/conf/app.ini"] --> B["ini.File"]
    E["GITEA__SECTION__KEY env vars"] --> C["EnvironmentToConfig()"]
    C --> B
    B --> D["ConfigProvider"]
    D --> F["loadSecurityFrom(cfg)<br/>security.go"]
    F --> G["setting.SecretKey<br/>setting.InternalToken"]
    H["GITEA__SECURITY__SECRET_KEY__FILE"] -.->|"reads file contents"| C
```

Two mechanics are directly relevant to secret hygiene and to what a secret-scanner (opengrep-class
tooling) should be configured to recognize:

1. **`GITEA__SECTION__KEY=value`** — any `app.ini` key can be overridden or supplied purely via
   environment variable. `SECTION`/`KEY` are joined with a double underscore, and non-`[A-Z0-9_]`
   characters (dots, dashes in sub-section names like `[log.console]`) are hex-escaped as
   `_0x2E_`/`_0x2D_`.
2. **`GITEA__SECTION__KEY__FILE=/path`** — the standard pattern for injecting secrets from
   Docker/Kubernetes secret mounts *without* putting the literal secret value in the environment
   or in `app.ini` at all. `EnvironmentToConfig` reads the file's contents (trimming a trailing
   newline) and uses that as the value. Gitea itself uses this pattern for the two most sensitive
   settings:

   ```bash
   GITEA__SECURITY__SECRET_KEY__FILE=/run/secrets/gitea_secret_key
   GITEA__MAILER__PASSWD__FILE=/run/secrets/smtp_password
   ```

   Both `SECRET_KEY` and `INTERNAL_TOKEN` also support an equivalent `*_URI` form directly in
   `app.ini` (`SECRET_KEY_URI = file:/etc/gitea/secret_key`), mutually exclusive with setting the
   plaintext value inline.

> **Scanner takeaway:** when secret-scanning this repository or a deployed configuration bundle,
> treat literal, non-empty values for `SECRET_KEY`, `INTERNAL_TOKEN`, `[database] PASSWD`,
> `[mailer] PASSWD`, and any LDAP `BindPassword`/OAuth2 client secret written directly into an
> `app.ini` or Kubernetes `ConfigMap` (as opposed to a `Secret` or a `*_FILE`/`*_URI` reference) as
> a finding. The `__FILE`/`_URI` indirection pattern is the "correct" answer these scanners should
> not flag; a literal secret string is the anti-pattern they should.

`ClearEnvConfigKeys()` additionally unsets every `GITEA__*` variable from the process environment
once installation completes, specifically so that environment-supplied secrets are not inherited by
subprocesses Gitea spawns (e.g. git hooks) unless intentionally passed through — worth knowing when
reasoning about whether a secret leaked via `GITEA__...` env vars could leak further into subprocess
environments.

## The `[security]` Section — Core Secrets and Policy

As documented in [Configuration (`app.ini`)](../../docs/03-getting-started/configuration-app-ini.md)
and the [Settings Catalog](../../docs/04-configuration/settings-catalog.md) (`security.go`), this is
the single most security-dense section in the entire configuration surface.

| Key | Purpose | Security implication |
|---|---|---|
| `SECRET_KEY` (or `SECRET_KEY_URI`) | Symmetric key used to encrypt data at rest — e.g. TOTP 2FA shared secrets (via an MD5-derived key, see below), LDAP bind passwords | **Losing it means losing that encrypted data.** Leaking it means an attacker who also has DB access can decrypt those secrets. Auto-generated by the install wizard; back it up, never commit it. |
| `INTERNAL_TOKEN` (or `INTERNAL_TOKEN_URI`) | Secret used to authenticate internal/loopback API calls, e.g. from git hooks calling back into the `gitea web` process | Also auto-generated at install; a leaked `INTERNAL_TOKEN` could let a local process impersonate Gitea's own hook-callback path. |
| `INSTALL_LOCK` | `false` by default; set `true` to permanently disable the install wizard | Leaving this `false` in a running production instance re-exposes the install wizard endpoint. |
| `LOGIN_REMEMBER_DAYS` | Lifetime of "remember me" persistent login cookies (default 31) | Longer values increase the exposure window if a remember-me cookie is stolen (see [Auth Tokens](#session-cookie-and-remember-me-security) below for how theft is detected). |
| `MIN_PASSWORD_LENGTH` | Minimum password length (default 8) | Low defaults should be raised for hardened deployments. |
| `PASSWORD_HASH_ALGO` | `argon2`, `pbkdf2` (default), `scrypt`, or `bcrypt` | `argon2`/`bcrypt`/`scrypt` are generally preferred over `pbkdf2` for modern password-hashing guidance; worth confirming the deployment's chosen algorithm against current recommendations. |
| `PASSWORD_CHECK_PWN` | `false` by default; checks new passwords against haveibeenpwned.com | Off by default — a hardening opportunity worth calling out explicitly, per this documentation set's convention of not glossing over gaps. |
| `TWO_FACTOR_AUTH` | Set to `"enforced"` to require 2FA for all users | Not enforced by default. |
| `DISABLE_GIT_HOOKS` | `true` by default | Governs whether users with hook privileges may install custom Git hooks — a powerful, potentially dangerous capability if flipped to `false`; treat any deployment with this `false` as higher-risk / needing extra review. |
| `DISABLE_WEBHOOKS`, `IMPORT_LOCAL_PATHS` | Feature toggles | Both carry security implications per the source docs (webhook SSRF surface, local-filesystem-path import capability) — see [SSRF, Webhooks & Outbound Requests](../03-attack-surface/ssrf-webhooks-and-outbound-requests.md). |
| `REVERSE_PROXY_AUTHENTICATION_USER` / `..._EMAIL` / `..._FULL_NAME` | Header names trusted for reverse-proxy SSO | **Only safe if the reverse proxy is guaranteed to strip these headers from untrusted client input.** A misconfigured proxy that passes through a client-supplied version of the trusted header is a full authentication bypass. |
| `REVERSE_PROXY_TRUSTED_PROXIES`, `REVERSE_PROXY_LIMIT` | Which upstream hops are trusted to set those headers | Misconfiguration here is the concrete control that prevents the bypass above. |
| `X_FRAME_OPTIONS`, `X_CONTENT_TYPE_OPTIONS`, `CONTENT_SECURITY_POLICY_GENERAL` | HTTP security response headers | See [HTTP Security Headers](#http-security-headers) below. |
| `ALLOWED_HOST_LIST` | Restricts which hosts webhook/OAuth2 clients are allowed to call: `loopback`, `private`, `external`, `*`, CIDRs, or wildcard hostnames | This is Gitea's primary **SSRF control** for outbound webhook/OAuth2/migration requests — see [SSRF, Webhooks & Outbound Requests](../03-attack-surface/ssrf-webhooks-and-outbound-requests.md) for the enforcement path. |

```ini
[security]
INSTALL_LOCK = false        ; set true to disable the install wizard entirely
SECRET_KEY =                ; VERY IMPORTANT: encrypts things like 2FA secrets — losing it means losing that data
;SECRET_KEY_URI = file:/etc/gitea/secret_key   ; mutually exclusive with SECRET_KEY
INTERNAL_TOKEN =            ; secret used for internal (loopback) API calls, e.g. from git hooks
;INTERNAL_TOKEN_URI = file:/etc/gitea/internal_token
LOGIN_REMEMBER_DAYS = 31
MIN_PASSWORD_LENGTH = 8
PASSWORD_HASH_ALGO = pbkdf2 ; argon2, pbkdf2, scrypt, or bcrypt
PASSWORD_CHECK_PWN = false  ; check against haveibeenpwned.com
TWO_FACTOR_AUTH =           ; set to "enforced" to require 2FA for all users
```

> As noted in [Configuration (`app.ini`)](../../docs/03-getting-started/configuration-app-ini.md):
> `SECRET_KEY` and `INTERNAL_TOKEN` are auto-generated the first time the install wizard runs
> (`modules/generate`, `routers/install/install.go`) — operators rarely set them by hand, but **must
> back them up**. A regenerated `SECRET_KEY` on an existing database instantly makes any data it had
> encrypted (2FA secrets, certain source credentials) unrecoverable.

### Where `SECRET_KEY` Is Actually Used to Encrypt Data

Per [Auth Providers](../../docs/08-services/auth-providers.md), `setting.SecretKey` is not just a
theoretical value — it is the concrete key material behind at least two at-rest encryption
mechanisms:

- **TOTP 2FA shared secrets** (`models/auth/twofactor.go`): AES-encrypted at rest, with the AES key
  *derived from `setting.SecretKey` via MD5* (`getEncryptionKey`), then Base64-encoded into the
  `Secret` column.
- **LDAP `BindDN`/`BindPassword`** (`services/auth/source/ldap/source.go`): encrypted at rest via
  `secret.EncryptSecret` in the source's `ToDB` method before being persisted to the login-source
  table.

> **Note on the MD5-derived key:** the source documentation explicitly calls out that the TOTP
> encryption key is derived from `SecretKey` "via MD5." MD5 is a broken hash for collision
> resistance, but here it is used purely as a key-derivation step, not for integrity/collision
> purposes — still, this is exactly the kind of `crypto/md5` usage that an opengrep SAST rule
> tuned for "weak cryptographic primitive" will flag in this codebase, and it is worth triaging
> against this documented, intentional design rather than assuming it is an oversight. See the
> [Scanning Playbook](../06-scanning-playbook/running-trivy-and-opengrep.md) for how to route this
> kind of finding.

### HTTP Security Headers

`X_FRAME_OPTIONS`, `X_CONTENT_TYPE_OPTIONS`, and `CONTENT_SECURITY_POLICY_GENERAL` in `[security]`
configure standard defensive response headers. Per the Settings Catalog, `security.go` additionally
**cross-reads `[cors]`** for `X_FRAME_OPTIONS` handling — meaning CORS policy and the frame-options
header are not fully independent and should be reviewed together, not in isolation, when hardening
either one.

## The `[cors]` Section

Per the Settings Catalog, `cors.go` owns Cross-Origin Resource Sharing policy for the API
(`[cors]` section). The source documentation notes this section is cross-referenced by
`security.go` for `X_FRAME_OPTIONS` — a scanner or reviewer checking CORS configuration should
check both sections together rather than assuming `[cors]` is self-contained. Beyond that
cross-reference, the settings catalog does not enumerate individual `[cors]` keys in the material
reviewed for this page; treat the exact key list as something to verify directly against
`custom/conf/app.example.ini` before writing a hardening rule against it, per this documentation
set's convention of flagging gaps rather than guessing at specifics not confirmed in source docs.

## Session & Cookie Configuration — `[session]`

The Settings Catalog maps `session.go` to the `[session]` section, describing it as the "web
session store backend and cookie behavior." The narrative `app.ini` walkthrough does not expand on
individual `[session]` keys beyond that mapping, so this page does not fabricate a key-by-key table
for it — but it is directly relevant to two mechanisms documented elsewhere in this set:

- **Session cookie behavior** underlies the `Session` auth method (`services/auth/session.go`),
  which reads the `uid` key from the session store; `handleSignIn` (`services/auth/auth.go`)
  **regenerates the session ID on login** as session-fixation protection.
- **Cross-site request protection** for session-authenticated browser requests is *not* a
  classic CSRF-token-in-`[session]` mechanism in this codebase — per
  [Request Lifecycle](../../docs/02-architecture/request-lifecycle.md), Gitea uses Go's standard
  library `http.NewCrossOriginProtection().Check(ctx.Req)`, a **Fetch Metadata**
  (`Sec-Fetch-Site` header) based cross-site check, applied in `verifyAuthWithOptions`
  (`routers/web/web.go`) unless `SignOutRequired` or `DisableCrossOriginProtection` is set for a
  route. Routes that must legitimately accept cross-origin requests (`git` smart-HTTP, PAT/OAuth2
  API access) explicitly opt out.

### Session, Cookie, and Remember-Me Security

Two independent persistence mechanisms exist and should not be confused when reviewing session
security, per [Auth Providers](../../docs/08-services/auth-providers.md):

1. **Session cookie** (short-lived, backed by `[session]` store config) — carries only a `uid`
   lookup key; regenerated at login.
2. **"Remember me" auth token cookie** (`LOGIN_REMEMBER_DAYS` in `[security]`) — a *separate*
   mechanism (`models/auth/auth_token.go`, `services/auth/auth_token.go`) modeled on
   [Paragon Initiative's secure remember-me design](https://paragonie.com/blog/2015/04/secure-authentication-php-with-long-term-persistence).
   The cookie value is `id:token`; the server stores only `TokenHash = sha256(token)`. Critically,
   **the hash is rotated on every login** (`RegenerateAuthToken`) while the `id` stays the same —
   if a stolen, already-used token is replayed, the hash mismatch triggers immediate revocation
   (`DeleteAuthTokenByID`) of that device's token, forcing re-authentication. This is a concrete,
   documented anti-token-theft control worth being aware of before assuming a long
   `LOGIN_REMEMBER_DAYS` value is purely a liability.

## LFS, Webhooks, and Other Secret-Bearing Settings

Several settings outside `[security]` carry their own secret material or security-relevant
behavior and are worth tracking in the same inventory:

| Setting | Section / file | Purpose | Security note |
|---|---|---|---|
| `LFS_JWT_SECRET` (+ `LFS_START_SERVER`, `LFS_ALLOW_PURE_SSH`) | `[server]`, via `lfs.go` | Signs the short-lived JWTs (`Claims{RepoID, Op, UserID}`, HS256) that authorize Git LFS batch/transfer requests | Per [Git LFS & Server-Side Hooks](../../docs/09-core-modules/lfs-and-hooks.md), tokens expire after `HTTPAuthExpiry` (default 24h); leaking `LFS_JWT_SECRET` lets an attacker mint arbitrary-repo LFS access tokens. |
| Webhook `Secret` (per-webhook, stored in DB, not `app.ini`) | `services/webhook/deliver.go` | HMAC-SHA1 and HMAC-SHA256 signing of outgoing webhook payload bodies | See [SSRF, Webhooks & Outbound Requests](../03-attack-surface/ssrf-webhooks-and-outbound-requests.md) for the full signature-header table (`X-Gitea-Signature`, `X-Hub-Signature`, `X-Hub-Signature-256`). |
| `[webhook] PROXY_URL` / `PROXY_HOSTS` / `SKIP_TLS_VERIFY` | `[webhook]` | Controls the `webhookHTTPClient` used for outgoing deliveries | `SKIP_TLS_VERIFY = true` disables TLS certificate validation for webhook targets — a hardening regression if enabled in production. |
| `[mailer] PASSWD`, `FORCE_TRUST_SERVER_CERT` | `[mailer]` | SMTP credential; TLS trust override | `FORCE_TRUST_SERVER_CERT` disables TLS certificate validation for the mail server — per [Configuration (`app.ini`)](../../docs/03-getting-started/configuration-app-ini.md), intended "only for trusted, non-production setups." |
| `[database] PASSWD` | `[database]` | Database connection credential | Supports the same back-tick quoting convention (`` PASSWD = `your password` ``) as any INI value containing special characters. |
| `AccessToken.TokenHash` / `TokenSalt` (not an `app.ini` setting, but a related secret-storage pattern) | `models/auth/access_token.go` | Personal Access Tokens are never stored in plaintext — only a salted hash and a `TokenLastEight` index shortcut are persisted; lookups use constant-time hash comparison (`crypto/subtle`) | A good reference pattern to compare against if opengrep flags any *other* token/credential storage code in this codebase that does **not** follow the same hash-only-at-rest convention. |

## Dynamic (Runtime-Editable) Settings Are Explicitly Not Security-Sensitive by Design

Per the [Settings Catalog](../../docs/04-configuration/settings-catalog.md), a small, deliberately
narrow set of options are **dynamic** — editable at runtime from **Admin Panel → Configuration →
Config Settings** without a restart, backed by `config.Option[T]` and persisted to the
`system_setting` database table instead of `app.ini`. The documented project convention is directly
relevant to hardening review:

> Static `app.ini` options are favored for anything that "is security-sensitive and should be
> controlled by the file-system/deployment owner, not a web-authenticated admin session."
> Dynamic options are reserved for settings that are "safe for a web admin to toggle without
> SSH/file access to the host."

The currently registered dynamic options — `picture.disable_gravatar`,
`picture.enable_federated_avatar`, `repository.open-with.editor-apps`,
`repository.git-guide-remote-name`, `instance.web_banner`, `instance.maintenance_mode` — are all
cosmetic/availability toggles, consistent with that stated convention. None of the `[security]`,
`[cors]`, `[webhook]`, `[mailer]`, or `[database]` secret-bearing keys catalogued above are dynamic;
they can only be changed by someone with file-system or environment-variable access to the deployed
instance, which is itself a deliberate security boundary — worth confirming stays true if new
dynamic options are ever proposed for security-adjacent settings.

## Configuration Hardening Checklist

A condensed checklist derived from the settings above, for use when auditing a specific Gitea
deployment's `app.ini` / environment configuration (not a substitute for reading the full
[Settings Catalog](../../docs/04-configuration/settings-catalog.md), only a starting point):

- [ ] `INSTALL_LOCK = true` in production.
- [ ] `SECRET_KEY` and `INTERNAL_TOKEN` are set via `*_URI`/`*_FILE` indirection (or at minimum
      backed up securely), never committed to version control.
- [ ] `MIN_PASSWORD_LENGTH` raised above the default `8` if policy requires it.
- [ ] `PASSWORD_HASH_ALGO` reviewed against current guidance (`argon2`/`bcrypt`/`scrypt` vs. the
      default `pbkdf2`).
- [ ] `PASSWORD_CHECK_PWN` considered — off by default.
- [ ] `TWO_FACTOR_AUTH = enforced` considered for sensitive instances — not enforced by default.
- [ ] `DISABLE_GIT_HOOKS` left at its default `true` unless custom-hook installation by
      non-admin users is an explicit, reviewed requirement.
- [ ] `REVERSE_PROXY_AUTHENTICATION_*` only enabled with a verified, header-stripping trusted
      proxy in front, and `REVERSE_PROXY_TRUSTED_PROXIES` scoped tightly.
- [ ] `ALLOWED_HOST_LIST` reviewed — see the SSRF control discussion in
      [SSRF, Webhooks & Outbound Requests](../03-attack-surface/ssrf-webhooks-and-outbound-requests.md).
- [ ] `[webhook] SKIP_TLS_VERIFY` and `[mailer] FORCE_TRUST_SERVER_CERT` both `false` in
      production.
- [ ] No literal secret values (`SECRET_KEY`, `INTERNAL_TOKEN`, `[database] PASSWD`,
      `[mailer] PASSWD`, LDAP `BindPassword`, OAuth2 client secrets) committed into any tracked
      `app.ini`, Helm values file, or Kubernetes `ConfigMap` (as opposed to a `Secret` resource or
      file-based indirection).
