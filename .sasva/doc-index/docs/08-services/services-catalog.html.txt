<h1>Services Catalog</h1>
<h1 id="services-catalog">Services Catalog</h1>
<p>Gitea's business logic lives almost entirely under <a href="../../services"><code>services/</code></a>. Routers
(<code>routers/web</code>, <code>routers/api</code>) are intentionally thin — they parse HTTP input, call into a
service function, and render the result. This page catalogs the services that are <strong>not</strong>
covered by their own dedicated pages elsewhere in this documentation (auth, actions, packages,
notifications, storage/queue/cache, and git/LFS internals each have their own pages — see the
cross-references at the end).</p>
<blockquote>
<p>For authentication providers see <a href="auth-providers.html">Authentication &amp; Authorization</a>.
For CI/CD see <a href="../14-actions-ci/actions-architecture.html">Actions Architecture</a>.
For notifications/webhooks see <a href="../09-core-modules/notify-mailer-webhook.html">Notify, Mailer &amp; Webhook</a>.</p>
</blockquote>

<h2 id="agit-flow-servicesagit">AGit Flow — <code>services/agit</code><a href="#agit-flow-servicesagit" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea supports <a href="https://git-repo.info/en/2020/03/agit-flow-and-git-repo/">AGit-flow</a>, which lets
a contributor open (and update) a pull request purely by pushing to a special ref
(<code>refs/for/&lt;base&gt;/&lt;topic&gt;</code>) without needing a fork or a separate <code>git push</code> for a PR creation
API call. The implementation lives in <a href="../../services/agit/agit.go"><code>services/agit/agit.go</code></a>
and is invoked from the git <code>proc-receive</code> hook path.</p>
<p>Key entry points:</p>
<table>

<p>Behavior highlights from <code>ProcReceive</code>:</p>
<ul>
<li>Push options <code>title</code>, <code>description</code>, <code>topic</code>, and <code>force-push</code> are read from
  <code>opts.GitPushOptions</code>; values may be <code>{base64}</code>-prefixed (for multi-line values) and are
  decoded by <code>parseAgitPushOptionValue</code>.</li>
<li>The topic branch is always namespaced with the pusher's username
  (<code>&lt;username&gt;/&lt;topic&gt;</code>) so that different users can reuse the same topic name without
  collision.</li>
<li>If no existing PR is found, <code>title</code>/<code>description</code> fall back to the new commit's
  <code>MessageTitle()</code>/<code>MessageBody()</code>, and a new <code>PullRequest</code> + <code>Issue</code> pair is created via
  <code>pull_service.NewPullRequest</code>.</li>
<li>If a PR already exists, a non-force push is rejected unless the <code>force-push</code> Git push option
  was supplied (detected via <code>git rev-list --max-count=1 old..^new</code>), the PR's <code>HeadCommitID</code>
  is advanced, and <code>pull_service.UpdateRef</code> moves the internal ref. Existing reviews are marked
  stale (<code>issues_model.MarkReviewsAsStale</code>) and, if the branch protection rule has
  <code>DismissStaleApprovals</code> set, approvals are dismissed via <code>pull_service.DismissApprovalReviews</code>.</li>
</ul>

<h2 id="auto-merge-servicesautomerge-and-servicesautomergequeue">Auto-Merge — <code>services/automerge</code> and <code>services/automergequeue</code><a href="#auto-merge-servicesautomerge-and-servicesautomergequeue" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Two cooperating packages implement "merge this PR automatically once checks pass":</p>
<ul>
<li><strong><code>services/automergequeue</code></strong> owns the actual queue (<code>AutoMergeQueue *queue.WorkerPoolQueue[string]</code>)
  and the trigger function <code>StartPRCheckAndAutoMerge(ctx, pull)</code>, which resolves the PR's current
  head commit SHA via <code>gitrepo.OpenRepository</code> + <code>GetRefCommitID</code> and pushes a
  <code>"&lt;prID&gt;_&lt;sha&gt;"</code> item onto the queue through <code>AddToQueue</code>.</li>
<li><strong><code>services/automerge</code></strong> is the queue's consumer/business layer:</li>
<li><code>Init()</code> registers the queue handler (<code>handler</code>) which calls <code>handlePullRequestAutoMerge</code>.</li>
<li><code>ScheduleAutoMerge(ctx, doer, pull, style, message, deleteBranchAfterMerge)</code> records a
    scheduled auto-merge (creates a <code>pull_model.AutoMerge</code> row) and immediately calls
    <code>StartPRCheckAndAutoMergeBySHA</code> to check if it can merge right away.</li>
<li><code>RemoveScheduledAutoMerge(ctx, doer, pull)</code> cancels a pending schedule.</li>
<li><code>StartPRCheckAndAutoMergeBySHA(ctx, sha, repo)</code> looks up every unmerged PR whose head matches
    <code>sha</code> in that repo and enqueues each for a merge attempt.</li>
<li><a href="../../services/automerge/notify.go"><code>notify.go</code></a> implements <code>notify_service.Notifier</code>
    (<code>automergeNotifier</code>) so that <code>CreateCommitStatus</code> and PR review events automatically
    re-trigger an auto-merge check — e.g., once a CI status turns green, the notifier hook
    fires <code>StartPRCheckAndAutoMergeBySHA</code> for that repo/SHA.</li>
</ul>

<pre class="highlight"><code class="language-go">// ToUser convert user_model.User to api.User
// if doer is set, private information is added if the doer has the permission to see it
func ToUser(ctx context.Context, user, doer *user_model.User) *api.User {
    if user == nil {
        return nil
    }
    authed := false
    signed := false
    if doer != nil {
        signed = true
        authed = doer.ID == user.ID || doer.IsAdmin
    }
    return toUser(ctx, user, signed, authed)
}</code></pre>
<ol>
<li><strong>Nil-safety</strong> — every <code>To*</code> function returns <code>nil</code> for a <code>nil</code> input so callers can convert
   slices without special-casing.</li>
<li><strong>Viewer-aware redaction</strong> — many converters take the <em>requesting</em> user (<code>doer</code>) alongside the
   entity being converted, and selectively populate privileged fields (e.g. <code>LoginName</code>,
   <code>IsAdmin</code>, private email) only if the viewer is the owner or a site admin. This keeps
   authorization logic for "what fields can this caller see" in one place instead of duplicated
   across every API handler.</li>
</ol>

<h2 id="background-tasks-servicestask">Background Tasks — <code>services/task</code><a href="#background-tasks-servicestask" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>services/task</code> runs long-lived, asynchronous jobs off the request path — today this is scoped to
<strong>repository migration/import</strong>, driven by a queue.</p>
<pre class="highlight"><code class="language-go">func CreateMigrateTask(ctx context.Context, doer, u *user_model.User, opts base.MigrateOptions) (*admin_model.Task, error)
func MigrateRepository(ctx context.Context, doer, u *user_model.User, opts base.MigrateOptions) error
func RetryMigrateTask(ctx context.Context, repoID int64) error

func Init() error</code></pre>
<p><code>CreateMigrateTask</code> persists an <code>admin_model.Task</code> row (status <code>Queued</code>) and pushes it onto a
<code>queue.WorkerPoolQueue</code>; the registered <code>handler</code> (<code>task.go</code>) calls <code>Run</code>, which dispatches to
<code>runMigrateTask</code> in <a href="../../services/task/migrate.go"><code>migrate.go</code></a>. <code>runMigrateTask</code> invokes the
actual migration downloader/uploader pair from <code>modules/migration</code> (GitHub/GitLab/etc.
importers), updates task status/progress as it streams issues, PRs, releases, and Git objects
into the new local repository, and calls <code>handleCreateError</code> to translate low-level errors (auth
failures, remote-not-found) into user-facing task error messages. <code>RetryMigrateTask</code> re-enqueues
a previously failed migration task by ID.</p>
<h2 id="versioned-in-place-migrations-servicesversioned_migration">Versioned In-Place Migrations — <code>services/versioned_migration</code><a href="#versioned-in-place-migrations-servicesversioned_migration" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A single-purpose wrapper, <a href="../../services/versioned_migration/migration.go"><code>migration.go</code></a>,
around the database schema migration runner in <code>models/migrations</code>:</p>
<pre class="highlight"><code class="language-go">func Migrate(ctx context.Context, x db.EngineMigration) error {
    release, err := globallock.Lock(ctx, "gitea_versioned_migration")
    if err != nil {
        return err
    }
    defer release()
    return migrations.Migrate(ctx, x)
}</code></pre>
<p>The only thing this layer adds over calling <code>migrations.Migrate</code> directly is a <strong>global lock</strong>
(<code>modules/globallock</code>, backed by the DB or a configured lock provider) named
<code>gitea_versioned_migration</code> — this guarantees that if multiple <code>gitea</code> instances start up
simultaneously against the same database (a common pattern in container orchestration
rolling-restarts), only one instance actually runs the versioned migration steps while the
others block until it's done. See <a href="../05-database-models/migrations.html">Migrations</a> for the
migration steps themselves.</p>
<h2 id="web-theme-serviceswebtheme">Web Theme — <code>services/webtheme</code><a href="#web-theme-serviceswebtheme" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Discovers and describes CSS themes shipped under <code>public/assets/css/themes/theme-*.css</code> (or, in
development, served by the Vite dev server) for the theme picker in user settings.
<a href="../../services/webtheme/webtheme.go"><code>webtheme.go</code></a>:</p>
<pre class="highlight"><code class="language-go">type ThemeMetaInfo struct {
    FileName       string
    InternalName   string
    DisplayName    string
    ColorblindType string // "red-green" | "blue-yellow" | ""
    ColorScheme    string // "light" | "dark" | ...
}</code></pre>
<p>Each theme's metadata (display name, colorblind-friendliness, light/dark classification) is
authored <strong>inside the CSS file itself</strong>, in a private <code>gitea-theme-meta-info { --key: "value"; }</code>
rule block, and extracted at runtime by <code>parseThemeMetaInfoToMap</code> using a small regex-based
parser (<code>reMetaInfoItem</code>/<code>reMetaInfoBlock</code>) rather than a separate manifest file — keeping theme
metadata co-located with the theme it describes. The parsed results are cached in an

<h2 id="wiki-service-serviceswiki">Wiki Service — <code>services/wiki</code><a href="#wiki-service-serviceswiki" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea stores each repository's wiki as its <strong>own bare Git repository</strong> (named
<code>&lt;repo&gt;.wiki.git</code>), with page titles mapped to file paths using a reversible escaping scheme.
<a href="../../services/wiki/wiki_path.go"><code>wiki_path.go</code></a> implements that mapping:</p>
<pre class="highlight"><code class="language-go">type WebPath string

func UserTitleToWebPath(base, title string) WebPath
func WebPathToUserTitle(s WebPath) (dir, display string)
func WebPathToGitPath(s WebPath) string
func GitPathToWebPath(s string) (wp WebPath, err error)
func WebPathSegments(s WebPath) []string</code></pre>
<p>Special characters and path segments that would collide with Git path rules are escaped (e.g. a
literal <code>-</code> in a title needs a "dash marker" so it isn't confused with the directory separator
substitution scheme — see <code>hasDashMarker</code>/<code>addDashMarker</code>/<code>removeDashMarker</code>), so that a human
title like <code>Foo Bar/Sub Page</code> round-trips correctly to/from a <code>.md</code> file path in the wiki repo.</p>
<p><a href="../../services/wiki/wiki.go"><code>wiki.go</code></a> implements the actual content operations, all funneling
through the private <code>updateWikiPage</code>:</p>
<pre class="highlight"><code class="language-go">func InitWiki(ctx context.Context, repo *repo_model.Repository) error
func AddWikiPage(ctx context.Context, doer *user_model.User, repo *repo_model.Repository, wikiName WebPath, content, message string) error
func EditWikiPage(ctx context.Context, doer *user_model.User, repo *repo_model.Repository, oldWikiName, newWikiName WebPath, content, message string) error
func DeleteWikiPage(ctx context.Context, doer *user_model.User, repo *repo_model.Repository, wikiName WebPath) (err error)
func DeleteWiki(ctx context.Context, repo *repo_model.Repository) error
func ChangeDefaultWikiBranch(ctx context.Context, repo *repo_model.Repository, newBranch string) error</code></pre>
<p><code>InitWiki</code> creates the bare <code>.wiki.git</code> repository lazily on first page save.
<code>updateWikiPage</code> acquires a per-repository lock (<code>getWikiWorkingLockKey</code>) to serialize concurrent
wiki edits, clones/checks out a temporary working copy, writes the new file content, and commits
+ pushes back — reusing <code>services/asymkey.SignWikiCommit</code> (see above) so wiki commits respect
the instance's commit-signing policy just like any other Git write path.</p>
