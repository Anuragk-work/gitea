<h1>Supplementary Models</h1>
<h1 id="supplementary-models">Supplementary Models</h1>
<p>The four entity-focused pages in this section (<a href="repository-model.html">Repository</a>,
<a href="issues-and-pulls-model.html">Issues &amp; Pull Requests</a>, <a href="user-organization-model.html">User &amp; Organization</a>,
and <a href="permissions-model.html">Permissions</a>) cover the "core" of Gitea's domain model. This page
rounds out the picture by covering every other <code>models/*</code> package that has its own tables but
doesn't warrant (or is already covered by) a dedicated page: cryptographic keys, avatars, the
database-backed virtual filesystem, git-identity/commit-participant matching, projects (kanban
boards), pull-request auxiliary state, markup rendering helpers, secrets, shared types, instance
settings/state, repo units, webhooks, admin tasks, activity feed/notifications, actions, packages,
and git-specific metadata (branches, protection, LFS, commit statuses).</p>
<blockquote>
<p>Source of truth for this page: <code>models/asymkey/</code>, <code>models/avatars/</code>, <code>models/dbfs/</code>,
<code>models/gituser/</code>, <code>models/project/</code>, <code>models/pull/</code>, <code>models/renderhelper/</code>,
<code>models/secret/</code>, <code>models/shared/types/</code>, <code>models/system/</code>, <code>models/unit/</code>,
<code>models/webhook/</code>, <code>models/admin/</code>, <code>models/activities/</code>, <code>models/actions/</code>,
<code>models/packages/</code>, and <code>models/git/</code>.</p>
</blockquote>
<h2 id="modelsasymkey-gpg-ssh-keys"><code>models/asymkey</code> — GPG &amp; SSH Keys<a href="#modelsasymkey-gpg-ssh-keys" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Two independent-but-parallel key subsystems, both used to verify signed commits/pushes and to
authenticate SSH access:</p>
<ul>
<li><strong><code>GPGKey</code></strong> (<code>gpg_key.go</code>) — a user's registered GPG public key. Stores the raw armored key
  content, parsed sub-key IDs, fingerprint, and expiry. <code>gpg_key_commit_verification.go</code>
  implements <code>ParseCommitWithSignature</code>, which checks a commit's PGP signature against the
  committer's (or any collaborator's) registered keys and produces a <code>CommitVerification</code>
  (<code>verified</code>, <code>warning</code>, <code>trust level</code>) consumed by the web UI's "Verified" badge.</li>
<li><strong><code>PublicKey</code></strong> / <strong><code>DeployKey</code></strong> (<code>ssh_key.go</code>, <code>ssh_key_deploy.go</code>) — SSH public keys.
  <code>PublicKey.Type</code> distinguishes user keys (<code>KeyTypeUser</code>) from repository-scoped deploy keys
  (<code>KeyTypeDeployKey</code>) and CI-principal keys (<code>KeyTypePrincipal</code>). <code>ssh_key_authorized_keys.go</code>
  regenerates the SSH server's <code>authorized_keys</code> file from the <code>public_key</code> table (invoked
  whenever a key is added/removed, and by <code>gitea admin regenerate keys</code>).</li>
<li><code>ssh_key_fingerprint.go</code> / <code>ssh_key_parse.go</code> — fingerprint calculation and OpenSSH-format
  parsing, shared by both deploy keys and regular keys.</li>
</ul>
<h2 id="modelsavatars-avatar-resolution"><code>models/avatars</code> — Avatar Resolution<a href="#modelsavatars-avatar-resolution" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Not a heavyweight model — mainly a small <strong><code>EmailHash</code></strong> cache table
(<code>Hash</code> → <code>Email</code>, used so Gravatar/Libravatar URLs built from an MD5 hash can be reversed back
to an email for admin lookups) plus a large set of pure functions for building avatar URLs:</p>
<ul>
<li><code>GenerateUserAvatarImageLink</code> / <code>GenerateUserAvatarFastLink</code> — links to a locally-uploaded
  user avatar file (<code>User.Avatar</code>) vs. a redirect-based lookup by username.</li>
<li><code>GenerateEmailAvatarFastLink</code> / <code>GenerateEmailAvatarFinalLink</code> — Gravatar/Libravatar
  federated-avatar resolution, split into a "fast" (redirect, cheap) and "final" (may perform a
  DNS lookup for Libravatar) variant so page rendering never blocks on external DNS.</li>
<li><code>loadAvatarSetting()</code> caches parsed <code>GravatarSource</code> URL + a configured <code>libravatar.Libravatar</code>
  client behind an <code>atomic.Pointer</code>, invalidated whenever <code>setting.GravatarSource</code> changes.</li>
</ul>
<h2 id="modelsdbfs-database-backed-filesystem"><code>models/dbfs</code> — Database-Backed Filesystem<a href="#modelsdbfs-database-backed-filesystem" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A niche but important package: it implements a <code>fs.File</code>-like interface (<code>Open</code>, <code>Create</code>,
<code>Rename</code>, <code>Remove</code>) entirely on top of two tables, so that <strong>streamed, appendable data that must
work identically across a clustered/HA deployment</strong> (primarily live Actions log output) doesn't
need a shared filesystem or object-storage round-trip per line:</p>
<pre class="highlight"><code class="language-go">type dbfsMeta struct {
    ID              int64  `xorm:"pk autoincr"`
    FullPath        string `xorm:"VARCHAR(500) UNIQUE NOT NULL"`
    BlockSize       int64
    FileSize        int64
    CreateTimestamp int64
    ModifyTimestamp int64
}

type dbfsData struct {
    ID         int64  `xorm:"pk autoincr"`
    Revision   int64
    MetaID     int64  `xorm:"index(meta_offset)"`
    BlobOffset int64  `xorm:"index(meta_offset)"`
    BlobSize   int64
    BlobData   []byte `xorm:"BLOB NOT NULL"`
}</code></pre>
<p>Data is chunked into fixed-size <code>BlockSize</code> blobs (<code>dbfsData</code> rows), keyed by <code>(MetaID,
BlobOffset)</code>, so random-access reads/seeks only need to fetch the relevant blocks rather than
the whole file. <code>dbfsMeta</code> implements <code>fs.FileInfo</code> directly (<code>Name</code>, <code>Size</code>, <code>ModTime</code>, etc.),
so callers can treat a dbfs file exactly like an <code>os.File</code> for most purposes. The package doc
comment in <code>dbfs.go</code> explicitly rejects the alternative designs (local temp files, git-repo
storage, one-row-per-log-line) and explains why: cluster-safety, shared read/write interface, and
avoiding big-table performance problems from a line-per-row schema.</p>
<h2 id="modelsgituser-git-identity-gitea-user-matching"><code>models/gituser</code> — Git Identity ↔ Gitea User Matching<a href="#modelsgituser-git-identity-gitea-user-matching" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A small, read-only-in-nature helper package (not backed by its own tables) that reconciles git
commit authorship (<code>name &lt;email&gt;</code>) with registered Gitea accounts:</p>
<ul>
<li><code>GetUserCommitsByGitCommits</code> takes a slice of <code>*git.Commit</code> and returns <code>[]*UserCommit</code>, each
  pairing the raw commit with the matched <code>*user.User</code> (matched by <strong>author</strong> email, gathered
  via <code>user.GetUsersByEmails</code>) — this is what lets the commit-log view show a Gitea avatar/link
  next to commits instead of a bare "Name <email>" string.</li>
<li><code>CommitParticipant</code> / <code>BuildAvatarStackData</code> (<code>avatar_stack.go</code>) extend this to <em>all</em>
  participants of a commit (author, committer, and co-authors parsed from trailers), producing
  the small overlapping-avatar "stack" widget shown in commit list rows and the "N people"
  tooltip.</li>
</ul>
<h2 id="modelsproject-projects-kanban-boards"><code>models/project</code> — Projects (Kanban Boards)<a href="#modelsproject-projects-kanban-boards" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>Project</code> (<code>project.go</code>) models a kanban-style board that can be scoped to an individual user,
an organization, or a single repository (<code>Type</code>: <code>TypeIndividual</code> / <code>TypeOrganization</code> /
<code>TypeRepository</code>), with <code>OwnerID</code>/<code>RepoID</code> set accordingly (mutually exclusive, mirroring the
<code>Secret</code> model's ownership convention below).</p>
<ul>
<li><code>Column</code> (<code>column.go</code>) — one kanban column within a project (e.g. "To Do", "In Progress",
  "Done"); has a <code>Default</code> flag marking where newly-added issues land.</li>
<li><code>ProjectIssue</code> (<code>issue.go</code>) — the many-to-many join between <code>Issue</code> and <code>Project</code>/<code>Column</code>,
  also storing a <code>Sorting</code> position for drag-and-drop ordering within a column.</li>
<li><code>TemplateType</code>/<code>CardType</code> enums select the built-in column layout (e.g. "Basic Kanban",
  "Bug Triage") and card rendering style (text-only vs. cover-image) offered when creating a
  project.</li>
<li><code>GhostProjectID = -1</code> is a sentinel used the same way as Gitea's "ghost user" — for
  <code>ProjectIssue</code> rows whose parent project was deleted but the row wasn't cleaned up yet.</li>
</ul>
<p>See also <a href="repository-model.html">Repository Model</a> and
<a href="issues-and-pulls-model.html">Issues &amp; Pull Requests Model</a> for how <code>RepoID</code> and issue linkage work.</p>
<h2 id="modelspull-pull-request-auxiliary-state"><code>models/pull</code> — Pull Request Auxiliary State<a href="#modelspull-pull-request-auxiliary-state" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Two tables that extend <code>issues.PullRequest</code> (documented in
<a href="issues-and-pulls-model.html">Issues &amp; Pull Requests Model</a>) without living in the <code>issues</code>
package itself, to avoid import cycles with <code>repo</code>/<code>user</code>:</p>
<ul>
<li><strong><code>AutoMerge</code></strong> (<code>automerge.go</code>, table <code>pull_auto_merge</code>) — records that a PR is scheduled to
  merge automatically once its required checks pass; stores the requested <code>MergeStyle</code>, the
  merge commit <code>Message</code>, and whether to delete the branch afterward. One row per <code>PullID</code>
  (<code>UNIQUE</code>).</li>
<li><strong><code>ReviewState</code></strong> (<code>review_state.go</code>) — per-user, per-PR, per-commit "viewed files" tracking
  for the PR diff UI's "Viewed" checkboxes. <code>UpdatedFiles</code> is a <code>map[string]ViewedState</code> stored
  as JSON, where <code>ViewedState</code> is <code>Unviewed</code> / <code>HasChanged</code> (file changed since last viewed,
  cannot be set directly by the UI) / <code>Viewed</code>. Keyed by <code>(UserID, PullID, CommitSHA)</code> so that
  viewed-state correctly resets/carries forward as new commits are pushed to the PR.</li>
</ul>
<h2 id="modelsrenderhelper-markup-rendering-context-builders"><code>models/renderhelper</code> — Markup Rendering Context Builders<a href="#modelsrenderhelper-markup-rendering-context-builders" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Not database models — this package builds <code>*markup.RenderContext</code> + <code>markup.RenderHelper</code>
implementations for the four rendering surfaces that need repository-aware link/mention
resolution: <code>RepoComment</code> (issue/PR comments), <code>RepoFile</code> (README/markdown files in a repo tree),
<code>RepoWiki</code> (wiki pages), and <code>SimpleDocument</code> (context-free rendering, e.g. release notes preview).
Each implementation supplies <code>ResolveLink</code> (turning relative links into repo-relative URLs) and
<code>IsCommitIDExisting</code> (used to decide whether a <code>abcd1234</code>-looking string in text should be
auto-linked as a commit reference) — the latter backed by a shared <code>commitChecker</code> that batches
and caches git object lookups to avoid one git call per detected hash in a large comment/file.</p>
<h2 id="modelssecret-actions-secrets"><code>models/secret</code> — Actions Secrets<a href="#modelssecret-actions-secrets" class="heading-anchor" aria-label="Link">#</a></h2>
<p><strong><code>Secret</code></strong> stores encrypted values used by Gitea Actions (<code>${{ secrets.X }}</code>) and, more
generally, anything needing owner/repo-scoped encrypted key-value storage. Its doc comment
(reproduced in the model) is the load-bearing design note:</p>
<ul>
<li>Exactly one of <code>OwnerID</code> (org/user-level secret) or <code>RepoID</code> (repo-level secret) must be
  non-zero — never both, and never neither (global secrets are deliberately unsupported for
  security reasons, so a misconfigured "global" secret can't silently leak to every repo).</li>
<li><code>Data</code> stores the value already encrypted (via <code>modules/secret</code>) before it ever reaches the
  database — the DB layer never sees plaintext secret values.</li>
<li><code>(OwnerID, RepoID, Name)</code> is a compound unique index, so the same secret name can exist once
  per owner and independently once per repo without colliding.</li>
<li>Size limits are enforced in Go before insert: <code>SecretDataMaxLength = 65536</code>,
  <code>SecretDescriptionMaxLength = 4096</code>.</li>
</ul>
<h2 id="modelssharedtypes-cross-package-enums"><code>models/shared/types</code> — Cross-Package Enums<a href="#modelssharedtypes-cross-package-enums" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A tiny, dependency-free package that exists purely to break import cycles: <code>OwnerType</code> (<code>"system-
global"</code>, <code>"individual"</code>, <code>"repository"</code>, <code>"organization"</code>) is used by webhook, secret, variable,
and Actions-config models to tag <em>who</em> owns a row, without those packages needing to import each
other just to share one string enum. <code>OwnerType.LocaleString</code> renders each value through
<code>modules/translation</code> for admin UI displays.</p>
<h2 id="modelssystem-instance-wide-settings-state"><code>models/system</code> — Instance-Wide Settings &amp; State<a href="#modelssystem-instance-wide-settings-state" class="heading-anchor" aria-label="Link">#</a></h2>
<ul>
<li><strong><code>Setting</code></strong> (<code>setting.go</code>, table <code>system_setting</code>) — the persisted backing store for runtime-
  configurable settings (<code>SettingKey</code> → <code>SettingValue</code>), used by <code>modules/setting/config</code>'s

<li><strong><code>AppState</code></strong> (<code>appstate.go</code>) — a generic <code>ID → Content</code> key-value table for small pieces of

  revision=revision+1</code> first and only falls back to <code>INSERT</code> if no row was updated, avoiding a
  read-then-write race.</li>
<li><strong><code>Notice</code></strong> (<code>notice.go</code>) — admin-facing system notices (shown on the "Notices" admin page),

<p><code>Webhook</code> and <code>HookTask</code> (with <code>HookRequest</code>/<code>HookResponse</code> sub-structs) are the persistence

<h2 id="modelsadmin-background-task-records"><code>models/admin</code> — Background Task Records<a href="#modelsadmin-background-task-records" class="heading-anchor" aria-label="Link">#</a></h2>
<p><strong><code>Task</code></strong> (table <code>task</code>) records long-running admin-triggered background jobs — primarily
repository <strong>migrations</strong> (<code>gitea migrate</code> / "New Migration" in the UI) — with <code>Doer</code>/<code>Owner</code>/
