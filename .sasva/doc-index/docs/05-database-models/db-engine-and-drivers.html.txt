<h1>DB Engine and Drivers</h1>
<h1 id="db-engine-and-drivers">DB Engine and Drivers</h1>
<p>Gitea's data layer is built on top of <a href="https://xorm.io">XORM</a>, a Go ORM. All engine setup,
connection string construction, transaction handling, pagination and consistency checking
lives in the <code>models/db</code> package. This page walks through how the engine is created, how
drivers are selected, how transactions/contexts work, and the supporting utilities for
pagination and consistency checks.</p>
<blockquote>
<p>Source of truth for this page: <code>models/db/engine.go</code>, <code>models/db/engine_init.go</code>,
<code>models/db/engine_hook.go</code>, <code>models/db/conn.go</code>, <code>models/db/context.go</code>,
<code>models/db/context_committer_test.go</code>, <code>models/db/list.go</code>, <code>models/db/paginator/</code>,
and <code>models/db/consistency.go</code>.</p>
</blockquote>
<h2 id="overview">Overview<a href="#overview" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The <code>db</code> package wraps an <code>xorm.Engine</code> behind a small set of Go interfaces so that the rest
of the codebase (<code>models/*</code>, <code>services/*</code>, <code>routers/*</code>) never imports <code>xorm.io/xorm</code> directly.
This keeps the ORM as an implementation detail and makes it possible to swap the session for
a transaction (or vice versa) transparently.</p>
<pre class="mermaid">graph TD
    A["setting.Database (app.ini)"] --> B["db.GlobalConnOptions()"]
    B --> C["db.ConnStr(opts)"]
    C -->|"driver name + DSN"| D["xorm.NewEngine(driver, dsn)"]
    D --> E["newXORMEngine()"]
    E --> F["InitEngine(ctx)"]
    F --> G["SetMapper(GonicMapper)"]
    F --> H["SetLogger / ShowSQL"]
    F --> I["Pool settings: MaxOpenConns, MaxIdleConns, ConnMaxLifetime"]
    F --> J["AddHook(EngineHook) if SlowQueryThreshold > 0"]
    F --> K["SetDefaultEngine(ctx, engine)"]
    K --> L["xormEngine (package-level singleton)"]</pre>
<h2 id="engine-interfaces-enginego">Engine Interfaces (<code>engine.go</code>)<a href="#engine-interfaces-enginego" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>models/db/engine.go</code> defines a small hierarchy of interfaces that abstract over <code>*xorm.Engine</code>
and <code>*xorm.Session</code>:</p>
<table>
<thead>
<tr>
<th>Interface</th>
<th>Purpose</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>SQLSession</code></td>
<td>Common CRUD/query methods shared by an engine and a session (<code>Find</code>, <code>Get</code>, <code>Insert</code>, <code>Where</code>, <code>Limit</code>, <code>Iterate</code>, etc.)</td>
</tr>
<tr>
<td><code>Engine</code></td>
<td><code>SQLSession</code> + <code>Sync(...)</code> + <code>Ping()</code> — what most model code receives from <code>db.GetEngine(ctx)</code></td>
</tr>
<tr>
<td><code>Session</code></td>
<td><code>Engine</code> + transaction control (<code>Begin</code>, <code>Commit</code>, <code>Rollback</code>, <code>IsInTx</code>, <code>Close</code>)</td>
</tr>
<tr>
<td><code>EngineMigration</code></td>
<td><code>Engine</code> + extra methods only available on <code>*xorm.Engine</code> (<code>DropTables</code>, <code>DBMetas</code>, <code>SetMapper</code>, <code>SyncWithOptions</code>, <code>TableInfo</code>, ...) — used exclusively by the migration framework</td>
</tr>
</tbody>
</table>
<p>These are enforced with compile-time assertions:</p>
<pre class="highlight"><code class="language-go">var (
    _ Engine          = (*xorm.Engine)(nil)
    _ Engine          = (*xorm.Session)(nil)
    _ Session         = (*xorm.Session)(nil)
    _ EngineMigration = (*xorm.Engine)(nil)
)</code></pre>
<p>Model registration also happens in this file. Every model package calls <code>db.RegisterModel</code>
in its <code>init()</code> function, for example in <code>models/organization/team.go</code>:</p>
<pre class="highlight"><code class="language-go">func init() {
    db.RegisterModel(new(Team))
    db.RegisterModel(new(TeamUser))
    db.RegisterModel(new(TeamRepo))
    db.RegisterModel(new(TeamUnit))
    db.RegisterModel(new(TeamInvite))
}</code></pre>
<p><code>RegisterModel</code> accumulates beans into the package-level <code>registeredModels</code> slice, plus
optional post-sync <code>initFunc</code>s (<code>registeredInitFuncs</code>) that run once tables have been
synced (e.g., to seed default rows). <code>SyncAllTables()</code> calls
<code>xormEngine.StoreEngine("InnoDB").SyncWithOptions(...)</code> against every registered bean — this
is what creates/updates tables from Go struct tags and is also used heavily by the test suite.</p>
<p>Other engine-level helpers worth knowing:</p>
<ul>
<li><code>NamesToBean(names ...string)</code> — resolves table/struct names to registered beans (used by <code>dump</code>/<code>restore</code> commands to select a subset of tables).</li>
<li><code>MaxBatchInsertSize(bean)</code> — computes a safe batch insert size based on column count (SQLite's <code>999</code> variable limit).</li>
<li><code>IsTableNotEmpty</code>, <code>DeleteAllRecords</code>, <code>GetMaxID</code> — small raw-SQL helpers used by doctor checks and migrations.</li>
<li><code>SetLogSQL(ctx, on)</code> — toggles <code>ShowSQL</code> on the underlying <code>*xorm.Engine</code>/<code>*xorm.Session</code> at runtime.</li>
</ul>
<h2 id="engine-initialization-engine_initgo">Engine Initialization (<code>engine_init.go</code>)<a href="#engine-initialization-engine_initgo" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>newXORMEngine()</code> is the low-level constructor:</p>
<pre class="highlight"><code class="language-go">func newXORMEngine() (*xorm.Engine, error) {
    connOpts := GlobalConnOptions()
    driver, connStr, err := ConnStr(connOpts)
    ...
    engine, err := xorm.NewEngine(driver, connStr)
    ...
    switch {
    case connOpts.Type.IsMySQL():
        engine.Dialect().SetParams(map[string]string{"rowFormat": "DYNAMIC"})
    case connOpts.Type.IsMSSQL():
        engine.Dialect().SetParams(map[string]string{"DEFAULT_VARCHAR": "nvarchar"})
    }
    engine.SetSchema(connOpts.Schema)
    return engine, nil
}</code></pre>
<p><code>InitEngine(ctx)</code> builds on this and wires the engine into the rest of the process:</p>
<ol>
<li>Creates the engine via <code>newXORMEngine()</code>.</li>
<li>Sets the struct-to-table-name mapper to <code>names.GonicMapper{}</code> (so <code>UserID</code> maps to
   <code>user_id</code>, not <code>user_i_d</code>); <code>LintGonicMapper</code> is patched in <code>init()</code> to also treat <code>SSL</code>
   and <code>UID</code> as recognized acronyms.</li>
<li>Installs the XORM logger (<code>NewXORMLogger</code>, see <code>models/db/xorm_logger.go</code> conceptually) and
   toggles <code>ShowSQL</code> based on <code>setting.Database.LogSQL</code>.</li>
<li>Applies connection pool settings: <code>MaxOpenConns</code>, <code>MaxIdleConns</code>, <code>ConnMaxLifetime</code>.</li>
<li>If <code>setting.Database.SlowQueryThreshold &gt; 0</code>, attaches an <code>EngineHook</code> (see below) that
   logs slow queries and records tracing spans.</li>
<li>Calls <code>SetDefaultEngine(ctx, xe)</code>, which stores the engine in the package-level <code>xormEngine</code>
   variable and calls <code>xormEngine.SetDefaultContext(ctx)</code>.</li>
</ol>
<pre class="highlight"><code class="language-go">func InitEngine(ctx context.Context) error {
    xe, err := newXORMEngine()
    ...
    xe.SetMapper(names.GonicMapper{})
    xe.SetLogger(NewXORMLogger(setting.Database.LogSQL))
    xe.ShowSQL(setting.Database.LogSQL)
    xe.SetMaxOpenConns(setting.Database.MaxOpenConns)
    xe.SetMaxIdleConns(setting.Database.MaxIdleConns)
    xe.SetConnMaxLifetime(setting.Database.ConnMaxLifetime)

    if setting.Database.SlowQueryThreshold &gt; 0 {
        xe.AddHook(&amp;EngineHook{
            Threshold: setting.Database.SlowQueryThreshold,
            Logger:    log.GetLogger("xorm"),
        })
    }

    SetDefaultEngine(ctx, xe)
    return nil
}</code></pre>
<p><code>InitEngineWithMigration(ctx, migrateFunc)</code> is the entry point used by the actual server
startup path and CLI commands. It:</p>
<ol>
<li>Calls <code>InitEngine(ctx)</code>.</li>
<li><code>Ping()</code>s the database to fail fast on bad connection settings.</li>
<li>Calls <code>preprocessDatabaseCollation(xormEngine)</code> (see <code>models/db/collation.go</code>) to normalize
   MySQL/MariaDB charset/collation before schema sync.</li>
<li>Invokes the supplied <code>migrateFunc(ctx, xormEngine)</code> — this is where the migration framework
   (documented in <a href="migrations.html">migrations.md</a>) actually runs.</li>
<li>Calls <code>SyncAllTables()</code> to sync every registered model's schema.</li>
<li>Runs every registered <code>initFunc</code> (from <code>RegisterModel</code>).</li>
</ol>
<blockquote>
<p><strong>Important:</strong> <code>InitEngineWithMigration</code> must never call <code>Sync()</code> before <code>migrateFunc</code>
succeeds — otherwise XORM would alter table schemas ahead of the migration logic, which
would corrupt version tracking or produce column mismatches.</p>
</blockquote>
<p><code>UnsetDefaultEngine()</code> closes and nils out <code>xormEngine</code>; it's primarily used by tests to reset
state between engine re-initializations, since <code>SetDefaultEngine</code>/<code>UnsetDefaultEngine</code> aren't
strictly paired everywhere in the codebase yet (documented as a known rough edge in the code
comments).</p>

<h2 id="slow-query-tracing-hook-engine_hookgo">Slow Query &amp; Tracing Hook (<code>engine_hook.go</code>)<a href="#slow-query-tracing-hook-engine_hookgo" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>EngineHook</code> implements XORM's <code>contexts.Hook</code> interface and is attached whenever
<code>Database.SlowQueryThreshold &gt; 0</code>:</p>
<pre class="highlight"><code class="language-go">func (*EngineHook) BeforeProcess(c *contexts.ContextHook) (context.Context, error) {
    ctx, _ := gtprof.GetTracer().Start(c.Ctx, gtprof.TraceSpanDatabase)
    return ctx, nil
}

func (h *EngineHook) AfterProcess(c *contexts.ContextHook) error {
    span := gtprof.GetContextSpan(c.Ctx)
    if span != nil {
        span.SetAttributeString(gtprof.TraceAttrDbSQL, c.SQL)
        span.End()
    }
    if c.ExecuteTime &gt;= h.Threshold {
        h.Logger.Log(8, &amp;log.Event{Level: log.WARN}, "[Slow SQL Query] %s %v - %v", c.SQL, c.Args, c.ExecuteTime)
    }
    return nil
}</code></pre>
<p>Every SQL statement is wrapped with a tracing span (integrating with Gitea's <code>gtprof</code> module)
and, if execution time exceeds the threshold, a warning is logged with the offending SQL,
arguments and duration. Test fixture loading (<code>ContextKeyTestFixtures</code> in context) skips the
tracing/logging path to avoid noise during unit tests.</p>

<h3 id="sqlite-drivers-mattn-vs-modernc-pluggable-via-build-tags">SQLite Drivers: mattn vs modernc (pluggable via build tags)<a href="#sqlite-drivers-mattn-vs-modernc-pluggable-via-build-tags" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Gitea supports two interchangeable pure driver implementations for SQLite, selected at
<strong>compile time</strong> via Go build tags, both registering themselves through
<code>registerSQLiteConnStrMaker</code>:</p>
<pre class="mermaid">graph LR
    A["conn.go: makeSQLiteConnStr (default: unsupported)"] -->|"build tag: !sqlite_mattn"| B["driver_sqlite_modernc.go<br/>modernc.org/sqlite (pure Go, default)"]
    A -->|"build tag: sqlite_mattn && sqlite_unlock_notify"| C["driver_sqlite_mattn.go<br/>github.com/mattn/go-sqlite3 (CGO)"]
    B --> D["registerSQLiteConnStrMaker()"]
    C --> D
    D --> E["setting.SupportedDatabaseTypes += sqlite3"]</pre>
<ul>
<li><strong><code>models/db/driver_sqlite_modernc.go</code></strong> (<code>//go:build !sqlite_mattn</code>) — the <em>default</em> driver.
  Uses <code>modernc.org/sqlite</code>, a pure-Go SQLite implementation (no CGO required). Registers itself
  as the <code>sqlite3</code> SQL driver via <code>sql.Register(sqlDriverSQLite3, &amp;sqlite.Driver{})</code>. Connection
  string uses <code>_pragma=busy_timeout(...)</code> and <code>_pragma=journal_mode(...)</code> query parameters and
  <code>_txlock=immediate</code>.</li>
</ul>
<pre class="highlight"><code class="language-go">func makeSQLiteConnStrModerncCCGO(opts SQLiteConnStrOptions) (string, string, error) {
    var params []string
    params = append(params, fmt.Sprintf("_pragma=busy_timeout(%d)", opts.BusyTimeout))
    params = append(params, "_txlock=immediate")
    if opts.JournalMode != "" {
        params = append(params, fmt.Sprintf("_pragma=journal_mode(%s)", opts.JournalMode))
    }
    connStr := fmt.Sprintf("file:%s?%s", opts.FilePath, strings.Join(params, "&amp;"))
    return sqlDriverSQLite3, connStr, nil
}</code></pre>
<ul>
<li><strong><code>models/db/driver_sqlite_mattn.go</code></strong> (<code>//go:build sqlite_mattn &amp;&amp; sqlite_unlock_notify</code>) —
  the CGO-based driver using <code>github.com/mattn/go-sqlite3</code>, historically the default before the
  modernc driver matured. Requires <code>-tags sqlite_mattn,sqlite_unlock_notify</code> at build time.
  Connection string uses <code>cache=shared</code>, <code>mode=rwc</code>, <code>_busy_timeout=...</code>, and <code>_txlock=immediate</code>.</li>
</ul>
<p>Both drivers are functionally interchangeable from the application's perspective — they only
differ in binary size, build requirements (CGO vs none), and CI/build time, as documented
directly in the source comments of <code>driver_sqlite_modernc.go</code>.</p>
<p>If neither build tag applies and SQLite support isn't compiled in at all, <code>makeSQLiteConnStr</code>
keeps its default value which always errors:</p>
<pre class="highlight"><code class="language-go">var makeSQLiteConnStr = func(opts SQLiteConnStrOptions) (string, string, error) {

<h3 id="postgresql-connection-string-hostport-parsing">PostgreSQL connection string &amp; host/port parsing<a href="#postgresql-connection-string-hostport-parsing" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>makePgSQLConnStr</code> builds a <code>net/url.URL</code> for <code>postgres://user:pass@host:port/dbname?params</code>,
supporting Unix sockets (detected via a leading <code>/</code> in the host) by putting the socket
directory into the <code>host</code> query parameter (libpq convention) instead of the URL host segment.
<code>parsePgSQLHostPort</code> handles <code>host:port</code>, bare host (falls back to port <code>5432</code>), and IPv6
bracket-stripping.</p>
<h3 id="mssql-hostport-parsing">MSSQL host/port parsing<a href="#mssql-hostport-parsing" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>parseMSSQLHostPort</code> accepts both <code>host:port</code> and <code>host,port</code> (SQL Server's native connection
string convention), defaulting host to <code>127.0.0.1</code> and port to <code>"0"</code> (dynamic port) if unset.</p>
<h2 id="sessions-transactions-context-contextgo">Sessions, Transactions &amp; Context (<code>context.go</code>)<a href="#sessions-transactions-context-contextgo" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The <code>db</code> package threads the "current" <code>Engine</code> (which may be a plain engine session, or an
active transaction session) through <code>context.Context</code>, using an unexported context key:</p>
<pre class="highlight"><code class="language-go">var contextKeyEngine = contextKey{"engine"}

func GetEngine(ctx context.Context) Engine {
    if engine, ok := ctx.Value(contextKeyEngine).(Engine); ok {
        contextSafetyCheck(engine)
        return engine
    }
    return xormEngine.Context(ctx)
}</code></pre>
<p>Any model/service function that needs to run a query calls <code>db.GetEngine(ctx)</code> — if the
context already carries a transaction (because the caller wrapped it in <code>db.WithTx</code>), the
same transaction is reused; otherwise a lightweight non-transactional session bound to <code>ctx</code>
is created from the global <code>xormEngine</code>.</p>
<h3 id="contextsafetycheck"><code>contextSafetyCheck</code><a href="#contextsafetycheck" class="heading-anchor" aria-label="Link">#</a></h3>
<p>In non-production or testing builds, <code>GetEngine</code> calls <code>contextSafetyCheck</code>, which uses
<code>runtime.Callers</code> to detect a dangerous pattern: reusing a context-bound engine <strong>inside</strong>
an <code>Iterate</code> callback, which XORM implements with <code>autoResetStatement=false</code> sessions —
calling <code>GetEngine(ctx)</code> again inside such an iterator would corrupt query results. This
lookup table of "denied" caller program counters is computed once via <code>sync.Once</code> and then
checked on every call, cheaply, for the lifetime of the process.</p>
<h3 id="transactions-txcontext-and-withtx">Transactions: <code>TxContext</code> and <code>WithTx</code><a href="#transactions-txcontext-and-withtx" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Two APIs exist for running code within a transaction:</p>
<ul>
<li><strong><code>WithTx</code> (recommended for new code)</strong> — automatically begins a transaction (or reuses an
  existing one from the parent context), runs the callback, and commits/rolls back for you:</li>
</ul>
<pre class="highlight"><code class="language-go">func WithTx(parentCtx context.Context, f func(ctx context.Context) error) error {
    if sess := getTransactionSession(parentCtx); sess != nil {
        err := f(withContextEngine(parentCtx, sess))
        if err != nil {
            _ = sess.Close() // rollback immediately
        }
        return err
    }
    return txWithNoCheck(parentCtx, f)
}</code></pre>
<p><code>txWithNoCheck</code> begins a brand-new session, runs <code>f</code>, and calls <code>sess.Commit()</code> if <code>f</code>
  returned no error (deferring <code>sess.Close()</code> regardless).</p>
<ul>
<li><strong><code>TxContext</code> (legacy pattern, still used in older code)</strong> — returns a <code>context.Context</code>
  plus a <code>Committer</code> that the caller must explicitly <code>Commit()</code>/<code>Close()</code>:</li>
</ul>
<pre class="highlight"><code class="language-go">ctx, committer, err := db.TxContext(parentCtx)
if err != nil { return err }
defer committer.Close()
// ... perform DB operations using ctx ...
return committer.Commit()</code></pre>
<p>If a transaction is already active in <code>parentCtx</code>, <code>TxContext</code> returns a <code>*halfCommitter</code>
  wrapping the existing session's committer: calling <code>Commit()</code> on it is a no-op (the <em>outer</em>
  transaction owner is responsible for the real commit), but calling <code>Close()</code> without a prior
  <code>Commit()</code> immediately rolls back the <strong>entire</strong> outer transaction — this "poison the whole
  transaction on error" behavior is intentional and documented at length in the code comments.</p>
<p><code>WithTx2[T]</code> is a generic variant of <code>WithTx</code> that also returns a typed value alongside the
error, useful for functions that both mutate and return data within one transaction.</p>
<p><code>InTransaction(ctx)</code> reports whether the current context is inside an active transaction, by
checking whether the context-bound engine is a <code>*xorm.Session</code> with <code>IsInTx() == true</code>.</p>
<h3 id="context_committer_testgo-testing-halfcommitter"><code>context_committer_test.go</code> — testing <code>halfCommitter</code><a href="#context_committer_testgo-testing-halfcommitter" class="heading-anchor" aria-label="Link">#</a></h3>

<th>Expected call sequence</th>

<h3 id="generic-crud-helpers">Generic CRUD helpers<a href="#generic-crud-helpers" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>context.go</code> also exposes a set of small generic helper functions built on top of <code>GetEngine</code>,

<h2 id="pagination-modelsdblistgo-and-modelsdbpaginator">Pagination (<code>models/db/list.go</code> and <code>models/db/paginator/</code>)<a href="#pagination-modelsdblistgo-and-modelsdbpaginator" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Pagination is modeled through a small <code>Paginator</code> interface:</p>
<pre class="highlight"><code class="language-go">type Paginator interface {
    GetSkipTake() (skip, take int)
    IsListAll() bool
}</code></pre>
<p><code>ListOptions</code> is the standard page/pageSize implementation used throughout the REST API and
web UI:</p>
<pre class="highlight"><code class="language-go">type ListOptions struct {
    PageSize int
    Page     int  // start from 1
    ListAll  bool // if true, then PageSize and Page will not be taken
}

func (opts *ListOptions) GetSkipTake() (skip, take int) {
    opts.SetDefaultValues()
    return (opts.Page - 1) * opts.PageSize, opts.PageSize
}

func (opts *ListOptions) SetDefaultValues() {
    if opts.PageSize &lt;= 0 {
        opts.PageSize = setting.API.DefaultPagingNum
    }
    if opts.PageSize &gt; setting.API.MaxResponseItems {
        opts.PageSize = setting.API.MaxResponseItems
    }
    if opts.Page &lt;= 0 {
        opts.Page = 1
    }
}</code></pre>
<p><code>ListOptionsAll = ListOptions{ListAll: true}</code> is a convenient shared sentinel for "fetch
everything." <code>AbsoluteListOptions</code> is a variant that takes pre-clamped <code>skip</code>/<code>take</code> values
directly (used, for example, for internal APIs that need explicit offsets rather than
page numbers):</p>
<pre class="highlight"><code class="language-go">func NewAbsoluteListOptions(skip, take int) *AbsoluteListOptions {
    if skip &lt; 0 { skip = 0 }
    if take &lt;= 0 { take = setting.API.DefaultPagingNum }
    if take &gt; setting.API.MaxResponseItems { take = setting.API.MaxResponseItems }
    return &amp;AbsoluteListOptions{skip, take}
}</code></pre>
<p><code>SetSessionPagination(sess, p)</code> applies <code>p.GetSkipTake()</code> directly to an XORM session's
<code>Limit(...)</code> call — the lowest-level plumbing point most list queries eventually go through.</p>
<h3 id="findoptions-and-the-generic-findcountfindandcount"><code>FindOptions</code> and the generic <code>Find</code>/<code>Count</code>/<code>FindAndCount</code><a href="#findoptions-and-the-generic-findcountfindandcount" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Beyond plain pagination, <code>list.go</code> defines a richer <code>FindOptions</code> interface that most
model-level "list criteria" structs implement:</p>
<pre class="highlight"><code class="language-go">type FindOptions interface {
    GetPage() int
    GetPageSize() int
    IsListAll() bool
    ToConds() builder.Cond
}</code></pre>
<p>Optional extension interfaces let a caller's options struct also contribute joins
(<code>FindOptionsJoin.ToJoins() []JoinFunc</code>) or ordering (<code>FindOptionsOrder.ToOrders() string</code>).
The generic functions <code>Find[T]</code>, <code>Count[T]</code>, and <code>FindAndCount[T]</code> compose all of this
automatically:</p>
<pre class="highlight"><code class="language-go">func Find[T any](ctx context.Context, opts FindOptions) ([]*T, error) {
    sess := GetEngine(ctx).Where(opts.ToConds())
    // ... apply joins if FindOptionsJoin ...
    // ... apply order if FindOptionsOrder ...
    // ... apply Limit(pageSize, offset) unless IsListAll() ...
    objects := make([]*T, 0, findPageSize)
    return objects, sess.Find(&amp;objects)
}</code></pre>
<p>This pattern lets each model package define a small, self-contained "options" struct (e.g.
<code>repo_search.SearchRepoOptions</code>) that implements <code>ToConds()</code>/<code>ToOrders()</code>/<code>ToJoins()</code>, and get
consistent, safe pagination for free.</p>

whose stated purpose is to eventually host the pagination types from <code>models/db/list.go</code>

<pre class="highlight"><code class="language-go">package paginator

// dummy only. in the future, the models/db/list_options.go should be moved here to decouple from db package

<h2 id="consistency-checks-consistencygo">Consistency Checks (<code>consistency.go</code>)<a href="#consistency-checks-consistencygo" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>models/db/consistency.go</code> provides two generic helpers for finding and removing "orphaned"
rows — rows in a <code>subject</code> table whose referenced row in a <code>refObject</code> table no longer exists:</p>
<pre class="highlight"><code class="language-go">func CountOrphanedObjects(ctx context.Context, subject, refObject, joinCond string) (int64, error) {
    return GetEngine(ctx).
        Table("`"+subject+"`").
        Join("LEFT", "`"+refObject+"`", joinCond).
        Where(builder.IsNull{"`" + refObject + "`.id"}).
        Select("COUNT(`" + subject + "`.`id`)").
        Count()
}

func DeleteOrphanedObjects(ctx context.Context, subject, refObject, joinCond string) error {
    subQuery := builder.Select("`"+subject+"`.id").
        From("`" + subject + "`").
        Join("LEFT", "`"+refObject+"`", joinCond).
        Where(builder.IsNull{"`" + refObject + "`.id"})
    b := builder.Delete(builder.In("id", subQuery)).From("`" + subject + "`")
    _, err := GetEngine(ctx).Exec(b)
    return err
}</code></pre>
<p>Both use a <code>LEFT JOIN ... WHERE ref.id IS NULL</code> pattern to identify rows in <code>subject</code> that no
longer have a matching row in <code>refObject</code>. These are consumed by:</p>
<ul>
<li><strong><code>services/doctor/dbconsistency.go</code></strong> — the <code>gitea doctor</code> command's generic "check for
  orphaned rows" logic across dozens of table pairs (e.g., <code>action</code> orphaned from <code>repository</code>,
  <code>attachment</code> orphaned from <code>issue</code>, etc.), driven by a declarative list of
  <code>(subject, refObject, joinCond)</code> tuples.</li>
<li><strong><code>services/doctor/repository.go</code></strong> — specifically checks for repositories whose owning user
  no longer exists: <code>db.CountOrphanedObjects(ctx, "repository", "user", "repository.owner_id=</code>user<code>.id")</code>.</li>
<li>Unit tests such as <code>models/db/engine_test.go</code>'s <code>TestDeleteOrphanedObjects</code> and
  <code>models/issues/pull_test.go</code>'s <code>testDeleteOrphanedObjects</code>, which validate the pull-request/
  issue relationship stays consistent.</li>
</ul>

<p><strong>Note:</strong> table/column names are directly interpolated into the SQL string (wrapped in
backticks) rather than parameterized, because table/column identifiers cannot be bound as
SQL parameters. Callers must only pass trusted, hard-coded identifiers — never user input —
to these functions.</p>
