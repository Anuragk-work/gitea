<h1>Database Migrations</h1>
<h1 id="database-migrations">Database Migrations</h1>
<p>Gitea uses a hand-rolled, linear migration framework (not a third-party migration library)
built on top of the <a href="db-engine-and-drivers.html">DB Engine</a> abstractions. Every schema change
ever shipped since Gitea 1.5.3 is represented as a numbered, ordered Go function. This page
explains how the framework works, the version-per-release directory convention, how to add a
new migration, and the test harness used to validate migrations against real fixture data.</p>
<blockquote>
<p>Source of truth for this page: <code>models/migrations/migrations.go</code>,
<code>models/migrations/migrations_test.go</code>, <code>models/migrations/base/</code>,
<code>models/migrations/migrationtest/tests.go</code>, <code>models/migrations/fixtures/</code>,
and the per-version packages <code>models/migrations/v1_6</code> through <code>models/migrations/v1_27</code>.</p>
</blockquote>
<h2 id="why-a-custom-framework">Why a Custom Framework?<a href="#why-a-custom-framework" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea doesn't use raw <code>.sql</code> files. Because it must run against SQLite, MySQL, PostgreSQL and
MSSQL with a single codebase, migrations are written as <strong>Go functions that operate on an
<code>db.EngineMigration</code></strong> (an XORM engine), using XORM's schema-sync capabilities
(<code>Sync</code>, <code>SyncWithOptions</code>) plus raw SQL where needed for data transformations. This lets a
single migration function work across all four supported databases without needing a
dialect-specific SQL file per migration.</p>
<h2 id="the-migration-type-and-ordered-list">The <code>migration</code> Type and Ordered List<a href="#the-migration-type-and-ordered-list" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>models/migrations/migrations.go</code> defines the central <code>migration</code> struct:</p>
<pre class="highlight"><code class="language-go">type migration struct {
    idNumber    int64 // DB version is "the last migration's idNumber" + 1
    description string
    migrate     func(context.Context, db.EngineMigration) error
}</code></pre>
<p><code>newMigration</code> is a small generic helper that accepts <em>either</em> a context-aware function or a
plain <code>func(db.EngineMigration) error</code> (for older-style migrations that don't need a
<code>context.Context</code>), normalizing both into the same signature:</p>
<pre class="highlight"><code class="language-go">func newMigration[T func(db.EngineMigration) error | func(context.Context, db.EngineMigration) error](
    idNumber int64, desc string, fn T,
) *migration {
    m := &amp;migration{idNumber: idNumber, description: desc}
    var ok bool
    if m.migrate, ok = any(fn).(func(context.Context, db.EngineMigration) error); !ok {
        m.migrate = func(ctx context.Context, x db.EngineMigration) error {
            return any(fn).(func(db.EngineMigration) error)(x)
        }
    }
    return m
}</code></pre>
<p>All migrations are registered, in strict chronological order, inside <code>prepareMigrationTasks()</code>.
This function is memoized via the package-level <code>preparedMigrations</code> slice (computed once, then
cached) and returns a big literal slice such as:</p>
<pre class="highlight"><code class="language-go">func prepareMigrationTasks() []*migration {
    if preparedMigrations != nil {
        return preparedMigrations
    }
    preparedMigrations = []*migration{
        // Gitea 1.5.0 ends at database version 69

        newMigration(70, "add issue_dependencies", v1_6.AddIssueDependencies),
        newMigration(71, "protect each scratch token", v1_6.AddScratchHash),
        newMigration(72, "add review", v1_6.AddReview),

        // Gitea 1.6.0 ends at database version 73

        newMigration(73, "add must_change_password column for users table", v1_7.AddMustChangePassword),
        ...
        newMigration(342, "Add scoped workflows schema", v1_27.AddScopedWorkflowsSchema),
    }
    return preparedMigrations
}</code></pre>
<p>Comments like <code>// Gitea X.Y.0 ends at database version N</code> mark release boundaries within the
otherwise flat list — this is purely documentation for maintainers, it has no functional effect.</p>
<h3 id="mindbversion-and-the-version-table"><code>minDBVersion</code> and the Version Table<a href="#mindbversion-and-the-version-table" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code class="language-go">const minDBVersion = 70 // Gitea 1.5.3</code></pre>
<p>Gitea refuses to auto-migrate databases older than version 70 (Gitea 1.5.3); such installs
must first be upgraded to an intermediate release (documented as v1.6.4 in the fatal error
message) before jumping to the current version. The current applied version is tracked in a
dedicated <code>version</code> table, mapped from the <code>Version</code> struct:</p>
<pre class="highlight"><code class="language-go">type Version struct {
    ID      int64 `xorm:"pk autoincr"`
    Version int64 // DB version is "the last migration's idNumber" + 1
}</code></pre>
<p>Only one row (<code>ID == 1</code>) is ever used.</p>
<h2 id="the-migration-lifecycle">The Migration Lifecycle<a href="#the-migration-lifecycle" class="heading-anchor" aria-label="Link">#</a></h2>
<pre class="mermaid">sequenceDiagram
    participant App as Startup / CLI (routers/common/db.go, cmd/migrate.go, ...)
    participant DB as db.InitEngineWithMigration
    participant Mig as migrations.Migrate
    participant Ver as version table

    App->>DB: InitEngineWithMigration(ctx, migrateFunc)
    DB->>DB: InitEngine(ctx) + Ping() + preprocessDatabaseCollation()
    DB->>Mig: migrateFunc(ctx, xormEngine)
    Mig->>Ver: Sync(Version{}) then Get(currentVersion)
    alt fresh install (no version row)
        Mig->>Ver: Insert Version{Version: maxDBVer}
        Note over Mig: Skip all migrations,<br/>tables created fresh by XORM sync
    else existing install
        Mig->>Mig: getPendingMigrations(curDBVer, migrations)
        loop for each pending migration m
            Mig->>Mig: m.Migrate(ctx, x)
            Mig->>Ver: Update Version{Version: m.idNumber+1}
        end
    end
    DB->>DB: SyncAllTables() (sync every registered model)
    DB->>DB: run registered post-sync initFuncs</pre>
<p><code>Migrate(ctx, x)</code> (the top-level entry point, in <code>migrations.go</code>) implements this logic:</p>
<pre class="highlight"><code class="language-go">func Migrate(ctx context.Context, x db.EngineMigration) error {
    migrations := prepareMigrationTasks()
    maxDBVer := calcDBVersion(migrations)

    x.SetMapper(names.GonicMapper{})
    if err := x.Sync(new(Version)); err != nil {
        return fmt.Errorf("sync: %w", err)
    }

    currentVersion := &amp;Version{ID: 1}
    has, err := x.Get(currentVersion)
    if err != nil {
        return fmt.Errorf("get: %w", err)
    } else if !has {
        // fresh installation: skip all migrations, XORM will create all tables when syncing
        currentVersion.ID = 0
        currentVersion.Version = maxDBVer
        if _, err = x.Insert(currentVersion); err != nil {
            return fmt.Errorf("insert: %w", err)
        }
    }

    curDBVer := currentVersion.Version
    if curDBVer &lt; minDBVersion {
        log.Fatal(`Gitea no longer supports auto-migration from your previously installed version...`)
        return nil
    }
    if maxDBVer &lt; curDBVer {
        log.Fatal("Migration Error: %s", ...) // downgrade protection
        return nil
    }

    if err = git.InitSimple(); err != nil {
        return err
    }

    for _, m := range getPendingMigrations(curDBVer, migrations) {
        log.Info("Migration[%d]: %s", m.idNumber, m.description)
        x.SetMapper(names.GonicMapper{})
        if err = m.Migrate(ctx, x); err != nil {
            return fmt.Errorf("migration[%d]: %s failed: %w", m.idNumber, m.description, err)
        }
        currentVersion.Version = migrationIDNumberToDBVersion(m.idNumber)
        if _, err = x.ID(1).Update(currentVersion); err != nil {
            return err
        }
    }
    return nil
}</code></pre>
<p>Key behaviors:</p>
<ul>
<li><strong>Fresh installs skip migrations entirely.</strong> If there's no <code>version</code> row at all, Gitea
  assumes this is a brand new database, sets the version straight to <code>maxDBVer</code>, and lets
  <code>SyncAllTables()</code> (called afterwards by <code>InitEngineWithMigration</code>) create the full, current
  schema directly from the model structs — no need to replay 250+ historical migrations.</li>
<li><strong>Downgrade protection.</strong> If the on-disk DB claims a version <em>newer</em> than what this binary
  knows about, Gitea refuses to start (<code>log.Fatal</code>) rather than silently running an older
  binary against a newer schema, which could corrupt data. In non-production builds, the fatal
  message even suggests the exact <code>UPDATE version SET version=...</code> statement to force past it
  (for developers who know what they're doing).</li>
<li><strong>Too-old protection.</strong> <code>curDBVer &lt; minDBVersion</code> also calls <code>log.Fatal</code>, instructing the
  admin to upgrade to an intermediate Gitea version first.</li>
<li><strong>The mapper is reset before every single migration</strong> (<code>x.SetMapper(names.GonicMapper{})</code>)
  because migrations aren't supposed to depend on mapper state left over by a previous one.</li>
<li><strong><code>git.InitSimple()</code> is called before running any pending migration</strong>, since some migrations
  need to invoke git commands (e.g., to inspect repositories on disk).</li>
<li><strong>Version is persisted after each migration, not just at the end</strong> — so a crash partway
  through a long migration run resumes correctly from the last successfully applied migration
  rather than re-running everything (or worse, skipping migrations).</li>
</ul>

<h2 id="directory-naming-convention-per-gitea-version">Directory / Naming Convention per Gitea Version<a href="#directory-naming-convention-per-gitea-version" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Migrations live in one package per <strong>minor Gitea release line</strong>, named <code>v1_&lt;minor&gt;</code>
(e.g. <code>v1_6</code>, <code>v1_7</code>, ..., <code>v1_27</code>), under <code>models/migrations/</code>:</p>
<pre class="highlight"><code>models/migrations/
├── migrations.go            # the ordered list + Migrate()/EnsureUpToDate() entry points
├── migrations_test.go
├── base/                    # shared helpers (RecreateTable, DropTableColumns, ModifyColumn, hashing...)
├── migrationtest/           # PrepareTestEnv() harness used by v1_NN/*_test.go files
├── fixtures/                # YAML fixtures for specific migration tests, keyed by Go test name
├── v1_6/
│   ├── v70.go
│   ├── v71.go
│   └── v72.go
├── v1_7/  ...
├── ...
└── v1_27/
    ├── main_test.go
    ├── v331.go   v331_test.go
    ├── v332.go
    ├── v333.go   v333_test.go
    ├── v334.go   v334_test.go
    ├── v335.go
    ├── v336.go
    ├── v337.go
    ├── v338.go   v338_test.go
    ├── v339.go   v339_test.go
    ├── v340.go
    ├── v341.go   v341_test.go
    └── v342.go</code></pre>
<p><strong>File naming inside each version package is <code>v&lt;idNumber&gt;.go</code></strong> — the file name's number
matches exactly the <code>idNumber</code> passed to <code>newMigration(idNumber, ...)</code> in <code>migrations.go</code>.
For example, <code>v1_27/v340.go</code> implements migration ID <code>340</code>, registered as:</p>
<pre class="highlight"><code class="language-go">newMigration(340, "Add ContinueOnError column to ActionRunJob", v1_27.AddContinueOnErrorToActionRunJob),</code></pre>
<p>And the file itself:</p>
<pre class="highlight"><code class="language-go">// models/migrations/v1_27/v340.go
package v1_27

import (
    "gitea.dev/models/db"

    "xorm.io/xorm"
)

// AddContinueOnErrorToActionRunJob adds the ContinueOnError column to ActionRunJob,
// storing the job-level continue-on-error value from the workflow YAML.
func AddContinueOnErrorToActionRunJob(x db.EngineMigration) error {
    type ActionRunJob struct {
        ContinueOnError bool `xorm:"NOT NULL DEFAULT FALSE"`
    }

    _, err := x.SyncWithOptions(xorm.SyncOptions{
        IgnoreDropIndices: true,
        IgnoreConstrains:  true,
    }, new(ActionRunJob))
    return err
}</code></pre>
<p>Notice the pattern common to almost every simple column-add migration:</p>
<ol>
<li>Define a <strong>local, minimal struct</strong> inside the function (not the "real" model struct from
   <code>models/actions</code>) containing only the field(s) being added, with the correct <code>xorm</code> tag.</li>
<li>Call <code>x.SyncWithOptions(xorm.SyncOptions{IgnoreDropIndices: true, IgnoreConstrains: true}, new(LocalStruct))</code>
   so XORM adds just the missing column, without trying to reconcile the <em>entire</em> schema
   (which could drop indices/constraints the migration doesn't know about).</li>
</ol>
<p>Each version package's file numbers are contiguous with the previous package's last number —
e.g., <code>v1_26</code> ends at some ID, and <code>v1_27</code> begins at <code>id+1</code> (<code>331</code> in this case) — enforced at
runtime by the <code>calcDBVersion</code> panic checks (<code>"migrations should start at minDBVersion"</code> /
<code>"migrations are not in order"</code>), and validated by <code>migrations_test.go</code>.</p>
<h2 id="how-to-add-a-new-migration">How to Add a New Migration<a href="#how-to-add-a-new-migration" class="heading-anchor" aria-label="Link">#</a></h2>
<ol>
<li><strong>Determine the next ID.</strong> Find the highest <code>idNumber</code> currently registered in
   <code>prepareMigrationTasks()</code> (the last entry in the list) — your new migration is <code>+1</code>.</li>
<li><strong>Create (or reuse) the current release's version package.</strong> If a <code>v1_28</code> directory doesn't
   exist yet (assuming <code>v1_27</code> is the latest), create it following the same <code>main_test.go</code>
   pattern used by every existing version package:</li>
</ol>
<pre class="highlight"><code class="language-go">// models/migrations/v1_28/main_test.go
package v1_28

import (
    "testing"

    "gitea.dev/models/migrations/migrationtest"
)

func TestMain(m *testing.M) {
    migrationtest.MainTest(m)
}</code></pre>
<ol>
<li><strong>Write the migration file <code>v&lt;idNumber&gt;.go</code></strong> in that package, implementing a function with
   signature <code>func(x db.EngineMigration) error</code> or <code>func(ctx context.Context, x db.EngineMigration) error</code>.
   Common patterns (see <code>models/migrations/base/db.go</code> for shared helpers):</li>
<li><strong>Add a column</strong>: define a minimal local struct and call <code>x.SyncWithOptions(...)</code>.</li>
<li><strong>Rename/modify a column's type</strong>: use <code>base.ModifyColumn(x, tableName, col)</code>.</li>
<li><strong>Drop columns</strong>: use <code>base.DropTableColumns(sess, tableName, columnNames...)</code>.</li>
<li><strong>Fully recreate a table</strong> (e.g., changing a primary key or removing a <code>NOT NULL</code>
     constraint SQLite can't <code>ALTER</code>): use <code>base.RecreateTables(beans...)</code> /
     <code>base.RecreateTable(sess, bean)</code>, which copies data into a temp table, drops the old one,
     and renames the temp table into place.</li>
<li><strong>Data-only migrations</strong> (no schema change, e.g., re-hashing values): operate directly via
     <code>x.Iterate(...)</code> or raw SQL through <code>x.Exec(...)</code>.</li>
<li><strong>Register it</strong> in <code>models/migrations/migrations.go</code>, appending to the very bottom of the
   <code>preparedMigrations</code> slice inside <code>prepareMigrationTasks()</code>:</li>
</ol>
<pre class="highlight"><code class="language-go">newMigration(343, "describe what this migration does", v1_28.YourNewMigrationFunc),</code></pre>
<blockquote>
<p>Never insert a migration in the middle of the list or reuse/change an existing <code>idNumber</code>
— that breaks version tracking for every already-deployed instance at that version.</p>
</blockquote>
<ol>
<li><strong>Write a migration test</strong> (see below) exercising the migration against fixture/inserted
   data, verifying the resulting schema/data is correct.</li>
<li><strong>If a migration must be retired</strong> (per code comments in <code>migrations.go</code>): remove it from
   the <em>top</em> of the list and bump <code>minDBVersion</code> accordingly — never remove from the middle.</li>
</ol>
<h3 id="data-type-dialect-notes">Data type / dialect notes<a href="#data-type-dialect-notes" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Because the same Go function must work on SQLite, MySQL, PostgreSQL and MSSQL, migrations
generally avoid raw dialect-specific SQL unless unavoidable — note the existence of migrations
like <code>v1_27.FixLegacyMSSQLDateTimeColumns</code>, which specifically targets MSSQL's legacy
<code>DATETIME</code> type (versus <code>DATETIME2</code>), showing that dialect-conditional logic inside a migration
(checking <code>x.Dialect().URI().DBType</code>) is an accepted pattern when truly necessary.</p>
<h2 id="migration-test-harness">Migration Test Harness<a href="#migration-test-harness" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="migrationtestpreparetestenv"><code>migrationtest.PrepareTestEnv</code><a href="#migrationtestpreparetestenv" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>models/migrations/migrationtest/tests.go</code> provides the shared setup used by (almost) every
<code>v1_NN/*_test.go</code> file:</p>
<pre class="highlight"><code class="language-go">func PrepareTestEnv(t *testing.T, skip int, syncModels ...any) (db.EngineMigration, func()) {
    ...
    require.NoError(t, unittest.SyncDirs(...))
    cleanup, err := unittest.ResetTestDatabase()
    ...
    err = db.InitEngine(t.Context())
    x := unittest.GetXORMEngine()

    if len(syncModels) &gt; 0 {
        if err := x.Sync(syncModels...); err != nil { ... }
    }

    fixturesDir := filepath.Join(giteaRoot, "models", "migrations", "fixtures", t.Name())
    if _, err := os.Stat(fixturesDir); err == nil {
        unittest.InitFixtures(unittest.FixturesOptions{Dir: fixturesDir})
        unittest.LoadFixtures()
    }
    return x, deferFn
}</code></pre>
<p>Key behavior:</p>
<ul>
<li><code>syncModels</code> are the <strong>local struct definitions the test needs</strong> — since migrations often
  work with minimal, function-local structs rather than the full current model, tests sync
  exactly the "before" schema shape they need to insert fixture rows into.</li>
<li><strong>Fixtures are auto-discovered by test name</strong>: <code>PrepareTestEnv</code> looks for a directory at
  <code>models/migrations/fixtures/&lt;TestName&gt;/</code> — if it exists, all <code>.yml</code> files in it are loaded as
  fixtures before the migration under test runs. This means a test named
  <code>TestAddIssueResourceIndexTable</code> will automatically pick up
  <code>models/migrations/fixtures/Test_AddIssueResourceIndexTable/issue.yml</code> if present.</li>
<li>Returns <code>(x, deferFn)</code> where <code>x</code> is a ready-to-use <code>db.EngineMigration</code> and <code>deferFn</code> cleans
  up the test database, closes the engine, and restores logging — callers must
  <code>defer deferable()</code> immediately.</li>
</ul>
<p><code>LoadTableSchemasMap(t, x)</code> is a small helper for tests that need to assert on the resulting
schema shape (column types, indices) after a migration runs, returning <code>map[string]*schemas.Table</code>
keyed by table name via <code>x.DBMetas()</code>.</p>
<p><code>MainTest(m)</code> / <code>mainTest(m)</code> set up the shared test process: initializing the test logger,
loading the integration test config (<code>setting.PrepareIntegrationTestConfig()</code>), setting up the
Gitea test environment, and initializing git — every version package's <code>main_test.go</code> simply
calls <code>migrationtest.MainTest(m)</code> from its own <code>TestMain</code>.</p>
<h3 id="example-a-full-migration-test-pair">Example: A full migration + test pair<a href="#example-a-full-migration-test-pair" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>models/migrations/v1_27/v334.go</code> and <code>v334_test.go</code> together show the standard shape:</p>
<pre class="highlight"><code class="language-go">// v334.go
func AddCancellingSupportToActionRunner(x db.EngineMigration) error {
    type ActionRunner struct {
        HasCancellingSupport bool `xorm:"has_cancelling_support NOT NULL DEFAULT false"`
    }

    _, err := x.SyncWithOptions(xorm.SyncOptions{
        IgnoreConstrains:  true,
        IgnoreDropIndices: true,
    }, new(ActionRunner))
    return err
}</code></pre>
<pre class="highlight"><code class="language-go">// v334_test.go
func TestAddCancellingSupportToActionRunner(t *testing.T) {
    type ActionRunner struct {
        ID   int64 `xorm:"pk autoincr"`
        Name string
    }

    x, deferable := migrationtest.PrepareTestEnv(t, 0, new(ActionRunner))
    defer deferable()
    if x == nil || t.Failed() {
        return
    }

    _, err := x.Insert(&amp;ActionRunner{Name: "runner"})
    require.NoError(t, err)

    require.NoError(t, AddCancellingSupportToActionRunner(x))

    var hasCancellingSupport bool
    has, err := x.SQL("SELECT has_cancelling_support FROM action_runner WHERE id = ?", 1).Get(&amp;hasCancellingSupport)
    require.NoError(t, err)
    require.True(t, has)
    require.False(t, hasCancellingSupport)
}</code></pre>
<p>The test: (1) syncs the <strong>pre-migration</strong> shape of <code>ActionRunner</code> (without the new column), (2)
inserts a row, (3) runs the migration function directly, then (4) verifies the new column
exists with the expected default value — all against a real (test) database engine, not mocks.</p>
<h3 id="fixtures-directory"><code>fixtures/</code> Directory<a href="#fixtures-directory" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>models/migrations/fixtures/</code> holds YAML fixture data for migration tests that need
pre-existing rows with specific values (rather than programmatically inserting rows in the
test body). Each subdirectory is named exactly after the Go test function it belongs to, e.g.:</p>
<pre class="highlight"><code>models/migrations/fixtures/
├── Test_AddCombinedIndexToIssueUser/
├── Test_AddConfidentialClientColumnToOAuth2ApplicationTable/
├── Test_AddHeaderAuthorizationEncryptedColWebhook/
├── Test_AddIssueResourceIndexTable/
│   └── issue.yml
├── Test_AddRepoIDForAttachment/
├── Test_AddUniqueIndexForProjectIssue/
├── Test_CheckProjectColumnsConsistency/
├── Test_DeleteOrphanedIssueLabels/
├── Test_FixCommitStatusTargetURLToUseRunAndJobID/
├── Test_RemigrateU2FCredentials/
├── Test_RemoveInvalidLabels/
├── Test_RepositoryFormat/
├── Test_StoreWebauthnCredentialIDAsBytes/
├── Test_UnwrapLDAPSourceCfg/
├── Test_UpdateBadgeColName/
└── Test_UpdateOpenMilestoneCounts/</code></pre>
<p>Each <code>.yml</code> file inside a test's directory is a standard Gitea unit-test fixture (same format
used by <code>models/fixtures/*.yml</code> for regular model tests — see the Database &amp; Models overview),
loaded via <code>unittest.InitFixtures</code>/<code>unittest.LoadFixtures</code> and matched to the table whose name
equals the YAML file's base name (<code>issue.yml</code> → <code>issue</code> table).</p>
<blockquote>
<p><strong>Tip:</strong> Prefer fixtures over hand-written <code>Insert</code> calls when a migration test needs many
rows, specific edge-case values (NULLs, empty strings, duplicate keys), or when mirroring a
real bug report's exact data shape that triggered the migration in the first place.</p>
</blockquote>
<h2 id="shared-migration-helpers-modelsmigrationsbase">Shared Migration Helpers (<code>models/migrations/base/</code>)<a href="#shared-migration-helpers-modelsmigrationsbase" class="heading-anchor" aria-label="Link">#</a></h2>
<ul>
<li><strong><code>db.go</code></strong> — dialect-agnostic schema surgery helpers used across many version packages:</li>
<li><code>RecreateTables(beans ...any) func(db.EngineMigration) error</code> /
    <code>RecreateTable(sess db.Session, bean any) error</code> — safely recreate a table (needed for
    changes SQLite can't <code>ALTER TABLE</code> for, like dropping a <code>NOT NULL</code> or changing a primary
    key): creates a <code>tmp_recreate__&lt;table&gt;</code> table with the new definition, copies data over,
    drops the old table, and renames the temp table into place.</li>
<li><code>DropTableColumns(sess, tableName, columnNames...)</code> — dialect-aware column dropping.</li>
<li><code>ModifyColumn(x, tableName, col *schemas.Column)</code> — dialect-aware column type/constraint
    changes.</li>
<li><strong><code>hash.go</code></strong> — small hashing helper(s) used by password/token migration functions (e.g.,
  <code>v1_9.HashAppToken</code>).</li>
</ul>
