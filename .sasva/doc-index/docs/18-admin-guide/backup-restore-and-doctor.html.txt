<h1>Backup, Restore & Doctor</h1>
<h1 id="backup-restore-doctor">Backup, Restore &amp; Doctor</h1>
<p>Gitea ships two CLI subcommand families dedicated to instance
maintenance: <code>gitea dump</code> (backup) and <code>gitea doctor</code> (diagnose/fix/
recreate/convert). Both are plain <code>github.com/urfave/cli/v3</code> commands
defined in <code>cmd/dump.go</code> and <code>cmd/doctor.go</code>, and both operate directly
against the configured database and storage backends — they must be run
on a host that can reach the same <code>app.ini</code>, database, and repository
storage as the running server (or against a copy of them).</p>
<h2 id="gitea-dump-creating-a-backup"><code>gitea dump</code> — Creating a Backup<a href="#gitea-dump-creating-a-backup" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="command-shape">Command Shape<a href="#command-shape" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code class="language-go">func newDumpCommand() *cli.Command {
    return &amp;cli.Command{
        Name:   "dump",
        Usage:  "Dump Gitea files and database",
        Action: runDump,
        Flags: []cli.Flag{ /* --file, --verbose, --quiet, --tempdir, --database, ... */ },
    }
}</code></pre>

<h3 id="supported-archive-formats">Supported Archive Formats<a href="#supported-archive-formats" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/dump/dumper.go</code> defines:</p>
<pre class="highlight"><code class="language-go">var SupportedOutputTypes = []string{"zip", "tar", "tar.sz", "tar.gz", "tar.xz", "tar.bz2", "tar.br", "tar.lz4", "tar.zst"}</code></pre>
<p><code>PrepareFileNameAndType(argFile, argType)</code> resolves the final output name
and type from whatever combination of <code>--file</code>/<code>--type</code> was given: if
neither is set, it defaults to <code>zip</code> with a timestamped name; if only
<code>--file</code> is given and its extension matches one of the supported suffixes,
that suffix determines the type; an unrecognized combination returns an
empty type, which <code>runDump</code> treats as fatal. <code>NewDumper</code> maps each type to
a <code>mholt/archives</code> <code>ArchiverAsync</code> implementation (<code>archives.Zip</code>,
<code>archives.Tar</code>, or a <code>CompressedArchive</code> wrapping <code>Tar</code> with the
appropriate <code>Compression</code> codec) and runs the archive writer
asynchronously against a channel of <code>ArchiveAsyncJob</code>s (<code>Dumper.jobs</code>), so
files are compressed and written as they're discovered rather than being
buffered entirely in memory first.</p>
<h3 id="what-gets-dumped-in-order">What Gets Dumped, in Order<a href="#what-gets-dumped-in-order" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>runDump</code> (<code>cmd/dump.go</code>) assembles the archive in a fixed sequence:</p>
<ol>
<li><strong><code>setting.MustInstalled()</code></strong> — refuses to run against an
   uninitialized instance (no completed <code>/install</code> flow).</li>
<li><strong>Repositories</strong> (<code>repos/</code>) — the entire <code>setting.RepoRootPath</code> tree via
   <code>dumper.AddRecursiveExclude</code>, unless <code>--skip-repository</code>.</li>
<li><strong>LFS objects</strong> (<code>data/lfs/</code>) — iterated object-by-object from
   <code>storage.LFS</code> via <code>IterateObjects</code>, skipped automatically if
   <code>setting.LFS.StartServer</code> is false, and independently skippable with
   <code>--skip-lfs-data</code> even when LFS is enabled.</li>
<li><strong>Database</strong> (<code>gitea-db.sql</code>) — dumped to a temporary file with
   <code>db.DumpDatabase(path, targetDBType)</code>, then added to the archive and
   the temp file removed; <code>--database</code> lets you dump into a <em>different</em>
   SQL dialect than the one currently configured, which is the supported
   path for <strong>migrating between database engines</strong> (e.g. SQLite → MySQL):
   restore the resulting SQL into the target engine, point a fresh
   <code>app.ini</code> at it, then run <code>gitea doctor check</code> before going live. If
   <code>--skip-db</code> is set, the dumper additionally calls
   <code>GlobalExcludeAbsPath(setting.Database.Path)</code> so an on-disk SQLite file
   living under <code>AppDataPath</code> isn't accidentally captured by the later
   data-directory pass.</li>
<li><strong><code>app.ini</code></strong> (<code>app.ini</code>) — always included via <code>AddFileByPath</code>,
   copied from <code>setting.CustomConf</code> (the actual config file that was
   loaded, respecting <code>--config</code>/<code>GITEA_CUSTOM</code> overrides).</li>
<li><strong>Custom directory</strong> (<code>custom/</code>) — the whole <code>setting.CustomPath</code> tree
   (templates overrides, custom locales, <code>public/</code> assets), unless
   <code>--skip-custom-dir</code>; skipped automatically (with a log message, not an
   error) if <code>CustomPath</code> happens to live <em>inside</em> <code>AppDataPath</code>, since
   step 7 would otherwise duplicate it.</li>
<li><strong>Application data directory</strong> (<code>data/</code>) — <code>setting.AppDataPath</code>,
   excluding whatever is dumped by more specific steps: the session
   provider's file-store path (parsed out of
   <code>setting.SessionConfig.ProviderConfig</code> when using the <code>file</code> session
   provider), the search-index directories (if <code>--skip-index</code>),
   <code>RepoRootPath</code>, LFS/Attachment/Packages/RepoArchive storage paths, and
   <code>Log.RootPath</code> — each excluded here specifically so it isn't
   double-counted against the dedicated steps above/below.</li>
<li><strong>Attachments</strong> (<code>data/attachments/</code>) — iterated from
   <code>storage.Attachments</code>, unless <code>--skip-attachment-data</code>.</li>
<li><strong>Packages</strong> (<code>data/packages/</code>) — iterated from <code>storage.Packages</code>,
   unless <code>--skip-package-data</code> or <code>setting.Packages.Enabled</code> is false.</li>
<li><strong>Logs</strong> (<code>log/</code>) — <code>setting.Log.RootPath</code>, unless <code>--skip-log</code>; this
    step deliberately does not pre-check whether the directory exists so
    that a genuinely-skipped dump is unambiguous in the log output either
    way.</li>
</ol>
<p>Finally, unless the output was streamed to stdout (<code>--file -</code>), the
archive file's permissions are tightened to <code>0600</code> — dumps routinely
contain secrets (<code>app.ini</code>'s <code>SECRET_KEY</code>/<code>INTERNAL_TOKEN</code>, the database
dump, LFS/attachment contents) and must not be left world-readable.</p>
<blockquote>
<p><strong>External storage caveat</strong>: if LFS/Attachments/Packages are configured
to use MinIO/S3 rather than local disk (see
<a href="../03-getting-started/README.html">Getting Started &amp; Configuration</a>),
<code>dump</code> still iterates and embeds every object's bytes through
<code>storage.Object.Stat()</code>/<code>AddFileByReader</code> — the dump remains
self-contained, but can become very large and slow for buckets with a
lot of data. Use the granular <code>--skip-*-data</code> flags to produce a
"config + database only" dump when object storage is backed up
separately (e.g. via the storage provider's own snapshot/replication
tooling).</p>
</blockquote>
<h3 id="restoring-from-a-dump">Restoring from a Dump<a href="#restoring-from-a-dump" class="heading-anchor" aria-label="Link">#</a></h3>
<p>There is no single <code>gitea restore</code> command — restoration is the dump
process run in reverse, manually:</p>
<ol>
<li>Stop the Gitea service.</li>
<li>Unpack the archive to a scratch location.</li>
<li>Restore <code>repos/</code> to the (new) <code>RepoRootPath</code>.</li>
<li>Restore <code>data/lfs</code>, <code>data/attachments</code>, <code>data/packages</code> to their
   respective storage backends (local paths or object storage, matching
   whatever <code>app.ini</code> will point at).</li>
<li>Import <code>gitea-db.sql</code> into a fresh, empty database of the target
   engine (<code>mysql</code>/<code>psql</code>/<code>sqlite3 &lt; gitea-db.sql</code>, per the dialect it was
   dumped with).</li>
<li>Restore <code>custom/</code> and the remainder of <code>data/</code> (minus the pieces
   already restored in steps 3–4) to <code>CustomPath</code>/<code>AppDataPath</code>.</li>
<li>Restore (or hand-merge) <code>app.ini</code> to the config path, updating any
   paths/credentials that differ in the new environment (data directory
   location, DB host, storage endpoint, <code>ROOT_URL</code>, etc.).</li>
<li>Run <code>gitea doctor check --all</code> before starting the service, to catch
   anything the manual restore missed.</li>
<li>Start Gitea and confirm via <code>/-/admin</code> → <em>Self Check</em> and, ideally, the
   <a href="monitoring-and-observability.html">Monitoring &amp; Observability</a> <code>/metrics</code>
   endpoint.</li>
</ol>

<h3 id="gitea-doctor-check-the-checks-engine"><code>gitea doctor check</code> — the Checks Engine<a href="#gitea-doctor-check-the-checks-engine" class="heading-anchor" aria-label="Link">#</a></h3>

<p><code>check-db-consistency</code> (<code>services/doctor/dbconsistency.go</code>) is itself a
list of ~25 <code>consistencyCheck</code> entries — each a <code>{Name, Counter, Fixer}</code>
triple that counts orphaned rows with a <code>db.CountOrphanedObjects(subject,
refObject, joinCond)</code> LEFT JOIN query and, when <code>--fix</code> is set, deletes
them with <code>db.DeleteOrphanedObjects</code>. Covered relationships include
labels/issue-labels without a repo, issues without a repo, pull requests
without an issue or base repo, tracked time without an issue, attachments
without an issue/release, <code>is_archived IS NULL</code> repositories, label
comments referencing deleted/foreign labels, Actions runners/variables/
secrets with an inconsistent <code>owner_id</code>, protected branches/branches/LFS
locks/collaborations/access rows without a repo or user, OAuth2 grants/
applications/authorization codes without an owning user/grant, stopwatches
without a user or issue, and user redirects pointing at a deleted user.
On PostgreSQL specifically, an extra <code>db.CountBadSequences</code> check detects
sequence values that have drifted behind the actual max row ID (a known
failure mode after certain restore/migration paths) and
<code>db.FixBadSequences</code> realigns them.</p>

the configured Git binary version supported, are required directories
writable — are performed automatically by <code>setting.LoadSettings()</code>/
<code>git.InitFull()</code> during normal startup and surfaced as
<code>setting.StartupProblems</code>, which is why they show up on the <em>Admin Panel</em>
dashboard and self-check page (see
<a href="admin-panel-and-operations.html#self-check-selfcheck--selfcheckpost">Admin Panel &amp; Operations</a>)
rather than as separate named <code>doctor</code> checks.</p>
<h3 id="gitea-doctor-recreate-table"><code>gitea doctor recreate-table</code><a href="#gitea-doctor-recreate-table" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code>gitea doctor recreate-table [TABLE]...</code></pre>
<p>Forces Xorm to drop and recreate the named table(s) (or every table, if
none are named) from their current Go struct definitions, copying
existing data across in the process. This repairs schema drift caused by
manual database edits or interrupted migrations — column defaults,
types, and indexes end up exactly matching what the running Gitea version
expects. <code>runRecreateTable</code> first runs <code>migrations.EnsureUpToDate</code> to
guarantee the migration version table itself is current before touching
any table structure, and accepts a <code>--debug</code> flag to echo every SQL
statement it issues. <strong>Always back up the database with <code>gitea dump</code>
first</strong> — this is a structural, in-place operation with no automatic undo.</p>
<h3 id="gitea-doctor-convert"><code>gitea doctor convert</code><a href="#gitea-doctor-convert" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Converts the database's charset/collation in place (implemented in
<code>cmd/doctor_convert.go</code>) — primarily used for MySQL installations created
with an incorrect or legacy charset that need to move to
<code>utf8mb4</code>/<code>utf8mb4_general_ci</code> (or another target collation) without a
full dump/restore cycle. As with <code>recreate-table</code>, take a backup first.</p>
