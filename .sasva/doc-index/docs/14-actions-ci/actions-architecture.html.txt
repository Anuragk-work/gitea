<h1>Actions Architecture</h1>
<h1 id="actions-architecture">Actions Architecture</h1>
<p>Gitea Actions is a built-in CI/CD system compatible with GitHub Actions workflow syntax. It parses workflow YAML from a repository, decides which workflows a webhook event should trigger, persists runs/jobs/tasks in the database, and hands work off to external <strong>runners</strong> (<code>act_runner</code> or compatible clients) over a Connect-RPC protocol. This page documents the full pipeline: workflow parsing, the data model, the runner protocol, artifact storage, commit status reporting, and secret/variable scoping.</p>
<blockquote>
<p>Gitea Actions purposefully does not execute workflows itself — the Gitea server only detects, schedules, and tracks runs. All actual step execution happens inside a runner process (typically <code>act_runner</code>), which polls Gitea over gRPC/Connect-RPC.</p>
</blockquote>
<h2 id="high-level-execution-flow">High-Level Execution Flow<a href="#high-level-execution-flow" class="heading-anchor" aria-label="Link">#</a></h2>
<pre class="mermaid">sequenceDiagram
    participant User as Git client
    participant Gitea as Gitea server
    participant DB as Database
    participant Runner as act_runner

    User->>Gitea: git push
    Gitea->>Gitea: notifier.go fires PushEvent
    Gitea->>Gitea: workflowpattern + workflows.go<br/>DetectWorkflows() matches on: push
    Gitea->>DB: PrepareRunAndInsert()<br/>creates ActionRun + ActionRunAttempt + ActionRunJob rows
    Gitea->>DB: CreateCommitStatusForRunJobs()<br/>posts "pending" CommitStatus
    loop Runner polling
        Runner->>Gitea: FetchTask (Connect-RPC)
        Gitea->>DB: PickTask() claims a waiting ActionRunJob
        Gitea-->>Runner: runnerv1.Task (workflow YAML, secrets, vars, context)
        Runner->>Runner: executes steps in containers/host
        Runner->>Gitea: UpdateLog (stream stdout/stderr)
        Gitea->>DB: WriteLogs() appends to DBFS file
        Runner->>Gitea: UpdateTask (status transitions)
        Gitea->>DB: UpdateTaskByState()
        Gitea->>Gitea: CreateCommitStatusForRunJobs()<br/>updates CommitStatus to success/failure
    end
    Gitea->>DB: EmitJobsIfReadyByRun()<br/>schedules jobs whose `needs` are satisfied</pre>
<h2 id="workflow-detection-and-parsing">Workflow Detection and Parsing<a href="#workflow-detection-and-parsing" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="listing-and-validating-workflow-files">Listing and validating workflow files<a href="#listing-and-validating-workflow-files" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/actions/workflows.go</code> is the entry point for workflow discovery. Workflow files live under configurable directories:</p>
<pre class="highlight"><code class="language-go">// modules/setting/actions.go

ScopedWorkflowDirs: []string{".gitea/scoped_workflows"},</code></pre>

<p><code>DetectWorkflows</code> is the main entry called by the notifier. It lists all workflow files at a commit, extracts every <code>on:</code> event from each file (a workflow can have multiple triggers), and classifies each into one of three buckets via <code>detectWorkflowMatch</code>:</p>
<pre class="highlight"><code class="language-go">const (
    detectMatched       detectResult = iota // event matched; run normally
    detectNotApplicable                     // event/type doesn't apply; create nothing
    detectFilteredOut                       // matched but excluded by a branch/paths filter;
                                             // posts a "skipped" commit status when required
)</code></pre>
<p><code>detectWorkflowMatch</code> first checks <code>canGithubEventMatch</code> (see <a href="#github-actions-compatibility-layer">GitHub compatibility layer</a>) and then dispatches to an event-specific matcher:</p>
<ul>
<li><code>matchPushEvent</code> — evaluates <code>branches</code>, <code>branches-ignore</code>, <code>tags</code>, <code>tags-ignore</code>, <code>paths</code>, <code>paths-ignore</code> filters against the push payload</li>
<li><code>matchIssuesEvent</code>, <code>matchIssueCommentEvent</code>, <code>matchPullRequestEvent</code>, <code>matchPullRequestReviewEvent</code>, <code>matchPullRequestReviewCommentEvent</code>, <code>matchReleaseEvent</code>, <code>matchPackageEvent</code>, <code>matchWorkflowRunEvent</code> — check <code>types:</code> activity filters</li>
<li>Events with no activity types (<code>create</code>, <code>delete</code>, <code>fork</code>, <code>wiki</code>, <code>schedule</code>) always match if the event name matches</li>
</ul>
<p>Scheduled workflows (<code>on: schedule</code>) are collected separately via <code>DetectScheduledWorkflows</code> and are handled by <code>services/actions/schedule_tasks.go</code>, not by the push-triggered path.</p>
<h3 id="branchtagpath-pattern-matching-workflowpattern">Branch/tag/path pattern matching (<code>workflowpattern/</code>)<a href="#branchtagpath-pattern-matching-workflowpattern" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/actions/workflowpattern/workflow_pattern.go</code> implements the glob-based filter semantics GitHub Actions uses for <code>branches</code>, <code>branches-ignore</code>, <code>paths</code>, <code>paths-ignore</code>:</p>
<pre class="highlight"><code class="language-go">func CompilePatterns(patterns ...string) ([]*WorkflowPattern, error)
func Skip(sequence []*WorkflowPattern, input []string) bool    // for "positive" filters: branches, paths, tags
func Filter(sequence []*WorkflowPattern, input []string) bool  // for "-ignore" filters: branches-ignore, paths-ignore</code></pre>
<p><code>Skip</code> returns true (meaning "don't run") only if <strong>every</strong> input string fails to match a positive (non-<code>!</code>) pattern, honoring negation (<code>!file.md</code>) semantics identical to GitHub's. <code>Filter</code> returns true (meaning "matched, exclude") only if <strong>every</strong> input matches at least one ignore pattern. Patterns are compiled with <code>glob.CompileWorkflow</code>, Gitea's glob dialect tuned for GitHub-Actions-style globbing (double-star, character classes, etc.).</p>
<h3 id="job-parsing-jobparser">Job parsing (<code>jobparser/</code>)<a href="#job-parsing-jobparser" class="heading-anchor" aria-label="Link">#</a></h3>
<p>While <code>workflows.go</code> deals with whole-workflow <em>triggers</em>, <code>modules/actions/jobparser/</code> (rewritten from <code>nektos/act</code>'s parser) turns one workflow YAML document into per-job <strong><code>SingleWorkflow</code></strong> documents ready to hand to a runner.</p>
<p><code>jobparser.Parse(content, options...)</code> (in <code>jobparser.go</code>):</p>
<ol>
<li>Decodes the raw YAML with <code>act</code>'s <code>model.ReadWorkflow</code> to get canonical job graph info (<code>Needs()</code>, matrices).</li>
<li>Re-decodes into the package's own <code>SingleWorkflow</code>/<code>Job</code>/<code>Step</code> structs (<code>model.go</code>), which keep most fields as raw <code>yaml.Node</code> so they can be selectively re-evaluated.</li>
<li>Expression-evaluates the workflow's <code>run-name</code>.</li>
<li>For every job, computes its <code>matrix</code> combinations (<code>getMatrixes</code>), interpolates <code>runs-on</code>, evaluates <code>continue-on-error</code>, and <strong>clones</strong> the job once per matrix cell — this is why a matrix job becomes multiple <code>SingleWorkflow</code> results, each with a single fully-resolved job.</li>
<li>Returns a <code>[]*SingleWorkflow</code> — normally one entry per (job × matrix-cell) pair — which becomes the <code>WorkflowPayload</code> stored on each <code>ActionRunJob</code> row and sent to runners.</li>
</ol>
<p>Supporting files:</p>
<ul>
<li><code>model.go</code> — <code>SingleWorkflow</code>, <code>Job</code>, <code>Step</code>, <code>Strategy</code>, <code>Defaults</code>, <code>ContainerSpec</code> types; note fields like <code>RawNeeds</code>, <code>RawRunsOn</code>, <code>RawContinueOnError</code> stay as <code>yaml.Node</code> until explicitly decoded/evaluated, since they may contain unresolved <code>${{ }}</code> expressions.</li>
<li><code>evaluator.go</code> / <code>interpeter.go</code> — wraps <code>act</code>'s <code>exprparser</code> to interpolate <code>${{ github.* }}</code>, <code>${{ vars.* }}</code>, <code>${{ inputs.* }}</code>, <code>${{ needs.*.outputs.* }}</code> expressions inside strings and YAML nodes.</li>
<li><code>uses.go</code> — parses <code>uses: owner/repo/path@ref</code> action references (including local <code>./</code> and Docker <code>docker://</code> forms).</li>
<li><code>workflow_call.go</code> — implements <strong>reusable workflows</strong> (<code>on: workflow_call</code>, job-level <code>uses: ./.github/workflows/x.yml</code>), including input/secret/output propagation contracts consumed by <code>services/actions/reusable_workflow.go</code>.</li>
</ul>
<pre class="mermaid">flowchart LR
    A[Workflow YAML] --> B["model.ReadWorkflow<br/>(act canonical parse)"]
    A --> C["yaml.Unmarshal into<br/>jobparser.SingleWorkflow"]
    C --> D["getMatrixes()<br/>per-job matrix expansion"]
    D --> E["NewExpressionEvaluator<br/>interpolate runs-on, name, continue-on-error"]
    E --> F["Clone per matrix cell"]
    F --> G["[]*SingleWorkflow<br/>one per job×matrix"]
    G --> H["ActionRunJob.WorkflowPayload<br/>(stored in DB)"]</pre>
<h2 id="github-actions-compatibility-layer">GitHub Actions Compatibility Layer<a href="#github-actions-compatibility-layer" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>modules/actions/github.go</code> maps Gitea's internal webhook event taxonomy (<code>webhook_module.HookEventType</code>) onto the GitHub Actions event vocabulary used inside <code>on:</code> blocks.</p>
<pre class="highlight"><code class="language-go">const (
    GithubEventPullRequest              = "pull_request"
    GithubEventPullRequestTarget        = "pull_request_target"
    GithubEventPullRequestReviewComment = "pull_request_review_comment"
    GithubEventPullRequestReview        = "pull_request_review"
    GithubEventRegistryPackage          = "registry_package"
    GithubEventCreate                   = "create"
    GithubEventDelete                   = "delete"
    GithubEventFork                     = "fork"
    GithubEventPush                     = "push"
    GithubEventIssues                   = "issues"
    GithubEventIssueComment             = "issue_comment"
    GithubEventRelease                  = "release"
    GithubEventPullRequestComment       = "pull_request_comment"
    GithubEventGollum                   = "gollum" // Gitea's wiki event
    GithubEventSchedule                 = "schedule"
)</code></pre>
<p>Two functions do the actual translation work:</p>
<ul>
<li><strong><code>IsDefaultBranchWorkflow(triggedEvent)</code></strong> — reports whether an event type only ever triggers workflows on the <em>default</em> branch (GitHub's documented behavior for <code>delete</code>, <code>fork</code>, <code>issue_comment</code>, <code>pull_request_comment</code>, <code>gollum</code>/wiki, <code>schedule</code>, <code>issues</code>, and <code>workflow_run</code>). The notifier (<code>services/actions/notifier_helper.go</code>) uses this to fall back to the default branch ref when computing which workflow file version to evaluate.</li>
<li><strong><code>canGithubEventMatch(eventName, triggedEvent)</code></strong> — the reverse mapping: given the <code>on:</code> event name written in YAML, decide whether it should fire for the concrete Gitea <code>HookEventType</code> that occurred. This absorbs GitHub's many-to-one relationships, e.g. <code>issues:</code> in YAML matches Gitea's <code>HookEventIssues</code>, <code>HookEventIssueAssign</code>, <code>HookEventIssueLabel</code>, and <code>HookEventIssueMilestone</code>; <code>pull_request_review:</code> matches both approved/rejected/commented review sub-events; <code>gollum:</code> (GitHub's wiki-edit event name) maps to Gitea's <code>HookEventWiki</code>; <code>issue_comment:</code> matches both true issue comments and PR comments (GitHub treats PR comments as <code>issue_comment</code> too).</li>
</ul>
<p>This layer keeps the rest of the codebase — commit status naming, workflow trigger evaluation — speaking GitHub's public vocabulary while Gitea's internal event bus keeps its own richer, more granular event types.</p>
<blockquote>
<p><code>ShouldEventCreateCommitStatus</code> (in <code>workflows.go</code>) is a related allowlist that decides which trigger events are allowed to become <strong>required status checks</strong> (<code>push</code>, <code>pull_request</code>, <code>pull_request_target</code>, <code>pull_request_review</code>, <code>pull_request_review_comment</code>, <code>release</code>). Its author's own comment flags that this list must be kept in sync by hand with <code>services/actions.getCommitStatusEventNameAndCommitID</code>, which is the authoritative source for which events actually post a status.</p>
</blockquote>

<h3 id="actionrun-modelsactionsrungo">ActionRun (<code>models/actions/run.go</code>)<a href="#actionrun-modelsactionsrungo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>An <code>ActionRun</code> represents one triggered run of a workflow file. Notable fields:</p>
<ul>
<li><code>RepoID</code> + <code>Index</code> — unique per-repo, human-visible run number (<code>xorm:"unique(repo_index)"</code>)</li>
<li><code>Event</code> / <code>TriggerEvent</code> — the Gitea webhook event type and the literal <code>on:</code> trigger string that matched</li>
<li><code>IsForkPullRequest</code> / <code>NeedApproval</code> / <code>ApprovedBy</code> — the fork-PR approval gate; untrusted fork PRs are held until a maintainer approves them (see <code>services/actions/approve.go</code>)</li>
<li><code>WorkflowRepoID</code> / <code>WorkflowCommitSHA</code> — always populated; for a normal run these equal <code>(RepoID, CommitSHA)</code>, but for a <strong>scoped run</strong> (see below) they point to the <em>source</em> repo/commit that owns the workflow file</li>
<li><code>IsScopedRun</code> — explicit flag distinguishing scoped runs from ordinary repo-level runs</li>
<li><code>LatestAttemptID</code> — points at the current <code>ActionRunAttempt</code>; <code>Status</code>/<code>Started</code>/<code>Stopped</code> on the run always mirror the latest attempt</li>
<li><code>RawConcurrency</code> — the raw, unevaluated <code>concurrency:</code> YAML block at workflow level</li>
</ul>
<h3 id="actionrunattempt-modelsactionsrun_attemptgo">ActionRunAttempt (<code>models/actions/run_attempt.go</code>)<a href="#actionrunattempt-modelsactionsrun_attemptgo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Introduced to properly support <strong>reruns</strong>: rather than mutating the original run's timing/status in place, each rerun creates a new <code>ActionRunAttempt</code> row (unique on <code>(RunID, Attempt)</code>), and <code>ActionRun.LatestAttemptID</code> is repointed at it. <code>UpdateRunAttempt</code> propagates <code>status</code>/<code>started</code>/<code>stopped</code> column changes back up to the parent <code>ActionRun</code> — but only if the attempt being updated is still the run's <code>LatestAttemptID</code>, guarding against a stale older attempt overwriting a newer rerun's status. Attempts also carry <code>ConcurrencyGroup</code>/<code>ConcurrencyCancel</code>, the evaluated workflow-level <code>concurrency:</code> settings (see <code>services/actions/concurrency.go</code>).</p>
<h3 id="actionrunjob-modelsactionsrun_jobgo">ActionRunJob (<code>models/actions/run_job.go</code>)<a href="#actionrunjob-modelsactionsrun_jobgo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>One row per job × matrix-cell (up to <code>MaxJobNumPerRun = 256</code>, mirroring GitHub's own limit). Highlights:</p>
<ul>
<li><code>WorkflowPayload</code> — the serialized single-job <code>jobparser.SingleWorkflow</code> YAML that gets sent verbatim to the runner</li>
<li><code>RunAttemptID</code> / <code>AttemptJobID</code> — <code>AttemptJobID</code> is stable across reruns for "the same logical job", <code>RunAttemptID</code> scopes it to one attempt; a value of <code>0</code> in either marks a legacy pre-attempt job</li>
<li><code>TaskID</code> / <code>SourceTaskID</code> — <code>TaskID</code> is the task created in <em>this</em> attempt; <code>SourceTaskID</code> points at a historical task from an earlier attempt when a rerun chooses to <strong>reuse</strong> that job's prior result instead of re-executing it</li>
<li><code>TokenPermissions</code> — explicit <code>permissions:</code> from the workflow/job YAML, JSON-encoded (<code>repo_model.ActionsTokenPermissions</code>); org/repo-level clamps are applied at token-mint time, not stored here</li>
<li>Reusable-workflow-caller fields: <code>IsReusableCaller</code>, <code>IsExpanded</code>, <code>CallUses</code>, <code>ReusableWorkflowContent</code>, <code>CallSecrets</code> (<code>""</code>, <code>"inherit"</code>, or a JSON alias map), <code>CallPayload</code> — a caller job (<code>uses: ./.github/workflows/x.yml</code>) does not itself run on a runner; when expanded, its children are inserted as separate <code>ActionRunJob</code> rows with <code>ParentJobID</code> pointing back at the caller</li>
<li><code>ParentJobID</code> — scopes <code>needs:</code> name resolution to siblings sharing the same parent, so reusable-workflow children can't accidentally satisfy <code>needs:</code> against unrelated jobs</li>
<li><code>ConcurrencyGroup</code> / <code>ConcurrencyCancel</code> / <code>IsConcurrencyEvaluated</code> — job-level <code>concurrency:</code> evaluation results (may depend on other jobs' outputs, hence the "evaluated" flag)</li>
</ul>
<h3 id="actiontask-actiontaskstep-modelsactionstaskgo-task_stepgo">ActionTask / ActionTaskStep (<code>models/actions/task.go</code>, <code>task_step.go</code>)<a href="#actiontask-actiontaskstep-modelsactionstaskgo-task_stepgo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>An <code>ActionTask</code> is the runner-facing unit of work created when a job is <strong>picked up</strong>. It owns the authentication token the runner uses for the rest of the job's lifetime (<code>TokenHash</code>/<code>TokenSalt</code>, checked with <code>crypto/subtle.ConstantTimeCompare</code>), plus the log-file bookkeeping: <code>LogFilename</code>, <code>LogInStorage</code>, <code>LogLength</code> (line count), <code>LogSize</code> (byte size), <code>LogIndexes</code> (line-number → byte-offset index for fast seeking).</p>

<h3 id="actionrunner-modelsactionsrunnergo">ActionRunner (<code>models/actions/runner.go</code>)<a href="#actionrunner-modelsactionsrunnergo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Runners register at one of three scopes — decided by which registration token was used — and the model comments are explicit that <code>OwnerID</code> and <code>RepoID</code> must never both be non-zero simultaneously (to keep "belongs to owner" queries unambiguous):</p>
<pre class="highlight"><code class="language-go">// It can be:
//  1. global runner, OwnerID is 0 and RepoID is 0
//  2. org/user level runner, OwnerID is org/user ID and RepoID is 0
//  3. repo level runner, OwnerID is 0 and RepoID is repo ID</code></pre>
<p>Runner liveness uses debounced timestamps rather than a write on every poll:</p>
<pre class="highlight"><code class="language-go">RunnerOfflineTime       = time.Minute      // no poll within this window -&gt; OFFLINE
RunnerIdleTime          = 10 * time.Second
RunnerHeartbeatInterval = 30 * time.Second // min interval between last_online writes
RunnerActiveInterval    = 5 * time.Second  // min interval between last_active writes</code></pre>
<p><code>ShouldPersistLastOnline</code> / <code>ShouldPersistLastActive</code> gate whether a given RPC call actually issues a DB write — this matters because <code>UpdateLog</code> can fire many times per second while a runner streams output, and a naive "write timestamp on every RPC" implementation would be a major source of database load at fleet scale (this exact rationale is called out in <code>routers/api/actions/runner/interceptor.go</code>).</p>
<h2 id="runner-registration-connect-rpc-protocol">Runner Registration &amp; Connect-RPC Protocol<a href="#runner-registration-connect-rpc-protocol" class="heading-anchor" aria-label="Link">#</a></h2>

<h3 id="authentication-interceptor">Authentication interceptor<a href="#authentication-interceptor" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Every RPC except <code>Register</code> is guarded by a Connect <strong>unary interceptor</strong> (<code>routers/api/actions/runner/interceptor.go</code>) that authenticates the caller via two custom headers:</p>
<pre class="highlight"><code class="language-go">const (
    uuidHeaderKey  = "x-runner-uuid"
    tokenHeaderKey = "x-runner-token"
)</code></pre>
<p>The interceptor loads the <code>ActionRunner</code> by UUID, verifies the token hash with a constant-time comparison (<code>subtle.ConstantTimeCompare</code>), then — subject to the debounce rules above — updates <code>last_online</code> (all methods) and <code>last_active</code> (<code>UpdateTask</code>/<code>UpdateLog</code> only) before injecting the authenticated <code>*ActionRunner</code> into the request context via <code>GetRunner(ctx)</code>.</p>
<h3 id="registration-flow">Registration flow<a href="#registration-flow" class="heading-anchor" aria-label="Link">#</a></h3>
<pre class="highlight"><code class="language-go">func (s *Service) Register(ctx, req *connect.Request[runnerv1.RegisterRequest]) (...) {
    runnerToken, err := actions_model.GetRunnerToken(ctx, req.Msg.Token)
    // ... validates token is active, owner/repo referenced by the token still exists
    runner := &amp;actions_model.ActionRunner{
        UUID:                 gouuid.New().String(),
        Name:                 name,
        OwnerID:              runnerToken.OwnerID,
        RepoID:               runnerToken.RepoID,
        Version:              req.Msg.Version,
        AgentLabels:          labels,
        Ephemeral:            req.Msg.Ephemeral,
        HasCancellingSupport: hasCancellingSupport,
    }
    runner.GenerateAndFillToken()
    actions_model.CreateRunner(ctx, runner)
    runnerToken.IsActive = true // registration tokens are one-shot: reused after first registration only if left active by admin
    actions_model.UpdateRunnerToken(ctx, runnerToken, "is_active")
    // returns Runner{Id, Uuid, Token, Name, Version, Labels, Ephemeral}
}</code></pre>
<p>Runner <strong>capabilities</strong> (currently just <code>"cancelling"</code>, meaning the runner understands the transitional <code>StatusCancelling</code> flow and will run post-step cleanup before finalizing a cancelled task) are advertised as a string list on <code>Register</code>/<code>Declare</code> requests, and echoed back on <code>Declare</code> responses via a header rather than a proto field bump:</p>
<pre class="highlight"><code class="language-go">resp.Header().Set("X-Gitea-Actions-Capabilities", actions_model.RunnerCapabilities())</code></pre>
<h3 id="task-pickup-fetchtask">Task pickup (<code>FetchTask</code>)<a href="#task-pickup-fetchtask" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Task assignment uses a monotonically increasing <strong>tasks version</strong> counter per scope <code>(OwnerID, RepoID)</code> to avoid runners busy-polling the database on every request when nothing changed:</p>
<pre class="mermaid">sequenceDiagram
    participant R as Runner
    participant S as RunnerService.FetchTask
    participant DB as DB

    R->>S: FetchTask{tasksVersion: N}
    S->>DB: GetTasksVersionByScope(ownerID, repoID)
    alt tasksVersion == latestVersion
        S-->>R: FetchTaskResponse{task: nil, tasksVersion: N}
        note over R: nothing changed, runner sleeps and retries
    else tasksVersion != latestVersion
        S->>S: actions_service.TryPickTask(runner)
        alt throttled (too many concurrent picks)
            S-->>R: FetchTaskResponse{task: nil, tasksVersion: N}
            note over R: version NOT advanced, retries immediately
        else task claimed
            S->>DB: CreateTaskForRunner + buildRunnerTask
            S-->>R: FetchTaskResponse{task, tasksVersion: latest}
        end
    end</pre>
<p><code>TryPickTask</code> (<code>services/actions/task.go</code>) bounds concurrent pick transactions with a semaphore sized by <code>setting.Actions.MaxConcurrentTaskPicks</code> (default 16), guarding against a "thundering herd" when many runners poll simultaneously. When throttled, the response deliberately does <strong>not</strong> advance <code>tasksVersion</code>, so the runner retries on its very next poll instead of falling asleep until the next real version bump.</p>
<p>Inside <code>PickTask</code>:</p>
<ol>
<li>Disabled runners (<code>runner.IsDisabled</code>) never get a task.</li>
<li>Ephemeral runners (single-job, then self-destruct) are checked for an existing unfinished task first; if their one task already finished, the runner row itself is deleted.</li>
<li><code>actions_model.CreateTaskForRunner</code> atomically claims one waiting <code>ActionRunJob</code> matching the runner's labels/scope and creates the <code>ActionTask</code> row.</li>
<li><code>buildRunnerTask</code> assembles the wire payload: <code>WorkflowPayload</code> bytes, <code>Secrets</code> (via <code>secret_model.GetSecretsOfTask</code>), <code>Vars</code> (<code>GetVariablesOfRun</code>), <code>Needs</code> outputs from upstream jobs (<code>FindTaskNeeds</code>), and a <code>Context</code> struct built by <code>GenerateGiteaContext</code> plus an ephemeral <code>gitea_runtime_token</code> (<code>CreateAuthorizationToken</code>) scoped to <code>(task, run, job)</code>.</li>
<li>If the request's context was cancelled before the response could reach the runner, the claim is released (<code>ReleaseTaskForRunner</code>) so another runner can pick it up — never leaving a job silently stuck in "running" with no runner attached.</li>
<li>Commit status is posted/updated (<code>CreateCommitStatusForRunJobs</code>) and job/run status-update notifications fire immediately.</li>
</ol>
<h3 id="status-log-reporting-updatetask-updatelog">Status &amp; log reporting (<code>UpdateTask</code>, <code>UpdateLog</code>)<a href="#status-log-reporting-updatetask-updatelog" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>UpdateTask</code> (see full code in <code>routers/api/actions/runner/runner.go</code>) applies the runner-reported <code>TaskState</code> via <code>actions_model.UpdateTaskByState</code>, persists any new step <strong>outputs</strong> (size-capped: 255-byte keys, 1 MiB values), reloads the job/run, re-posts the commit status, fires job/run status-update notifications when the task is done, and — if the job produced a final result — calls <code>EmitJobsIfReadyByRun</code> to unblock any downstream jobs whose <code>needs:</code> are now satisfied.</p>
<p><code>UpdateLog</code> implements incremental, idempotent log streaming:</p>
<ul>
<li>The server tracks an <strong>ack index</strong> (<code>task.LogLength</code>) — the runner resends unacked rows if a previous <code>UpdateLog</code> call's response was lost.</li>
<li>Rows the runner previously had acked are trimmed before writing.</li>
<li>Once a task calls <code>NoMore: true</code>, the log is sealed (<code>LogInStorage = true</code>) and transferred from the temporary DBFS append log into permanent object storage (<code>actions.TransferLogs</code>); any further append attempts return <code>codes.AlreadyExists</code>.</li>
<li>Actual line storage during the "live" phase goes through <code>modules/actions/log.go</code>'s <code>WriteLogs</code>, which appends to a DBFS-backed file (<code>gitea.dev/models/dbfs</code>) prefixed <code>actions_log/</code> — DBFS is chosen specifically because object storage backends are inefficient to append to, while the underlying database can absorb frequent small appends.</li>
</ul>
<h2 id="artifact-storage">Artifact Storage<a href="#artifact-storage" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Two generations of artifact protocol coexist:</p>
<ul>
<li><strong>Legacy (v3-ish) chunked upload API</strong> — <code>routers/api/actions/artifacts.go</code> + <code>artifacts_chunks.go</code>, used by older <code>actions/upload-artifact</code>.</li>
<li><strong>GitHub Actions Results API v4</strong> — <code>routers/api/actions/artifactsv4.go</code>, a Twirp-style JSON RPC surface (<code>/twirp/github.actions.results.api.v1.ArtifactService/...</code>) compatible with modern <code>actions/upload-artifact@v4</code>/<code>download-artifact@v4</code>.</li>
</ul>
<p>The v4 flow, documented in the source comments of <code>artifactsv4.go</code>, is:</p>
<pre class="mermaid">sequenceDiagram
    participant Runner
    participant Gitea as Gitea (ArtifactService)
    participant Blob as Object Storage

    Runner->>Gitea: CreateArtifact{workflow_run_backend_id, name}
    Gitea-->>Runner: signedUploadUrl (HMAC-signed, expiring)
    Runner->>Blob: PUT signedUploadUrl (comp=block, repeated)
    Runner->>Blob: PUT signedUploadUrl (comp=blockList, XML manifest)
    Runner->>Gitea: FinalizeArtifact{name, size, hash}
    Gitea-->>Runner: {ok, artifactId}

    Note over Runner,Gitea: Later, download
    Runner->>Gitea: ListArtifacts / GetSignedArtifactURL
    Gitea-->>Runner: signedUrl
    Runner->>Blob: GET signedUrl (DownloadArtifact)</pre>
<p>The signed URLs embed an HMAC signature and expiry, built by <code>modules/actions/artifacts.go</code>:</p>
<pre class="highlight"><code class="language-go">// BuildSignature builds a hmac signature for the input values.
// "tag" is an internal pre-defined static string to distinguish the signatures for different purpose.
func BuildSignature(tag tagType, vals ...string) []byte {
    m := hmac.New(sha256.New, setting.GetGeneralTokenSigningSecret())
    // ... writes tag + length-prefixed vals into the HMAC
    return m.Sum(nil)
}</code></pre>
<p>This lets the "upload zip content" and "download zip" endpoints remain <strong>unauthenticated</strong> (no runner token needed) while still being cryptographically bound to a specific artifact name, task ID, and expiry — anyone who doesn't hold a valid signature can't upload/download arbitrary artifact blobs.</p>
<p>The <code>ActionArtifact</code> model (<code>models/actions/artifact.go</code>) tracks per-artifact upload/expiry state via <code>ArtifactStatus</code>:</p>
<pre class="highlight"><code class="language-go">const (
    ArtifactStatusUploadPending   ArtifactStatus = iota + 1 // upload started, not confirmed
    ArtifactStatusUploadConfirmed                           // finalized, ready for download
    ArtifactStatusUploadError                                // upload failed
    ArtifactStatusExpired                                    // past retention period
    ArtifactStatusPendingDeletion                            // marked for cleanup
    ArtifactStatusDeleted                                    // cleanup complete
)</code></pre>
<p>Content can additionally carry a <code>ContentEncodingOrType</code> marker (<code>ContentEncodingV3Gzip = "gzip"</code> or <code>ContentTypeZip = "application/zip"</code>) distinguishing legacy per-file gzip streams from full zip archives, which matters when re-serving individual files from within a workflow run versus a full artifact download. <code>services/actions/artifacts.go</code> and <code>services/actions/cleanup.go</code> implement expiry sweeping and storage reclamation.</p>
<h2 id="commit-status-reporting">Commit Status Reporting<a href="#commit-status-reporting" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Two complementary pieces post and render GitHub-style commit statuses for Actions runs.</p>
<h3 id="posting-a-status-servicesactionscommit_statusgo">Posting a status (<code>services/actions/commit_status.go</code>)<a href="#posting-a-status-servicesactionscommit_statusgo" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>CreateCommitStatusForRunJobs(ctx, run, jobs...)</code> is called at every job-status transition point: run insertion (<code>PrepareRunAndInsert</code>), job pickup (<code>PickTask</code>), and task update (<code>UpdateTask</code>). It:</p>
<ol>
<li>Skips scheduled/cron runs (<code>run.ScheduleID != 0</code>) — cron jobs don't map onto a PR/commit check.</li>
<li>Resolves the <code>(event, commitID)</code> pair via <code>getCommitStatusEventNameAndCommitID</code>, which switches on <code>run.Event</code> to pull the right commit SHA out of the stored event payload (e.g. <code>HookEventPush</code> → <code>HeadCommit.ID</code> from the push payload).</li>
<li>For a <strong>scoped run</strong> (workflow physically defined in another repository, see below), computes a source-repo prefix (<code>ScopedStatusContextPrefix</code>) so the status context clearly identifies where the workflow came from.</li>
<li>Builds the context name using <code>WorkflowStatusContextName</code> / <code>ScopedWorkflowStatusContextName</code> from <code>modules/actions/workflows.go</code>:</li>
</ol>
<pre class="highlight"><code class="language-go">// "&lt;workflow display name&gt; / &lt;job name&gt; (&lt;event&gt;)"
func WorkflowStatusContextName(displayName, jobName, event string) string {
    return strings.TrimSpace(fmt.Sprintf("%s / %s (%s)", displayName, jobName, event))
}
// "&lt;source repo prefix&gt;: &lt;display&gt; / &lt;job&gt; (&lt;event&gt;)"
func ScopedWorkflowStatusContextName(prefix, displayName, jobName, event string) string {
    return strings.TrimSpace(fmt.Sprintf("%s: %s", prefix, WorkflowStatusContextName(displayName, jobName, event)))
}</code></pre>
<p>This context string is exactly what becomes a branch protection "required status check" name in the repo settings UI.</p>
<h3 id="rendering-a-live-status-modulesactionscommit_status_infogo">Rendering a live status (<code>modules/actions/commit_status_info.go</code>)<a href="#rendering-a-live-status-modulesactionscommit_status_infogo" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Rendering commit-status icons (e.g. on the commits list or PR checks tab) needs the <em>current</em> job status, but the <code>CommitStatus</code> row's own <code>State</code> field is a point-in-time snapshot written when the status was created — it can go stale while the job keeps running. <code>GetCommitActionsStatusMap</code> bridges this gap:</p>
<pre class="highlight"><code class="language-go">type CommitActionsStatusMap map[int64]actions_model.Status

func GetCommitActionsStatusMap(ctx context.Context, statuses []*git_model.CommitStatus) CommitActionsStatusMap</code></pre>
<p>For every <code>CommitStatus</code> row whose <code>TargetURL</code> parses as a Gitea-Actions run URL (<code>ParseGiteaActionsTargetURL</code>), it batch-loads the current <code>ActionRunJob.Status</code> and returns a <code>CommitStatus.ID → live Status</code> map. <code>CommitActionsStatusMap.IconStatus(status)</code> is then used purely for icon selection — non-Actions statuses (external CI, API-created statuses) fall through untouched and keep rendering from their stored <code>State</code>.</p>
<h2 id="secrets-variables-scoping">Secrets &amp; Variables Scoping<a href="#secrets-variables-scoping" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Both secrets and variables follow the same three-tier ownership model used by runners: <strong>global</strong> (<code>OwnerID=0, RepoID=0</code>), <strong>org/user</strong> (<code>OwnerID=owner, RepoID=0</code>), and <strong>repo</strong> (<code>OwnerID=0, RepoID=repo</code>) — with the model comments explicitly forbidding both IDs being non-zero at once to keep "belongs to" lookups unambiguous. Note: unlike variables, Gitea deliberately does <strong>not</strong> support global secrets (<code>models/secret/secret.go</code> requires at least one of <code>OwnerID</code>/<code>RepoID</code> to be non-zero), "for security reasons, admin may not be aware that the secrets could be stolen by any user when setting them as global."</p>
<blockquote>
<p>Gitea has <strong>no separate "environment" scope</strong> for Actions secrets/variables (unlike GitHub Environments). The only tiers that exist are org/user and repo (plus global for variables only). A workflow's <code>environment:</code> key is accepted for compatibility but does not currently gate secret visibility in Gitea — secret scoping is driven entirely by <code>OwnerID</code>/<code>RepoID</code>, the fork-PR check, and the reusable-workflow <code>secrets:</code> policy documented below.</p>
</blockquote>
<h3 id="write-path-servicessecrets-orguserrepo-secret-management">Write path: <code>services/secrets</code> (org/user/repo secret management)<a href="#write-path-servicessecrets-orguserrepo-secret-management" class="heading-anchor" aria-label="Link">#</a></h3>
<p>All secret <strong>mutations</strong> — as opposed to the read path used at task-dispatch time (<code>GetSecretsOfTask</code>, covered above) — funnel through the small, scope-agnostic <code>services/secrets</code> package (<code>services/secrets/secrets.go</code>, <code>services/secrets/validation.go</code>). It intentionally has no knowledge of <em>which</em> scope (org, user, or repo) it is operating at; the caller decides that by which <code>(ownerID, repoID)</code> pair it passes in:</p>
<pre class="highlight"><code class="language-go">// services/secrets/secrets.go
func CreateOrUpdateSecret(ctx context.Context, ownerID, repoID int64, name, data, description string) (*secret_model.Secret, bool, error)
func DeleteSecretByID(ctx context.Context, ownerID, repoID, secretID int64) error
func DeleteSecretByName(ctx context.Context, ownerID, repoID int64, name string) error</code></pre>
<p><code>CreateOrUpdateSecret</code> first runs <code>ValidateName</code> (<code>services/secrets/validation.go</code>), which enforces the same naming rules GitHub Actions uses: names must match <code>^[A-Z_][A-Z0-9_]*$</code> (case-insensitive), must not start with the reserved <code>GITHUB_</code>/<code>GITEA_</code> prefix (case-insensitive, so <code>github_foo</code> is also rejected), and must not be the literal name <code>CI</code> (always implicitly <code>true</code> in Actions runs). It then looks up any existing secret at that exact <code>(ownerID, repoID, name)</code> via <code>db.Find[secret_model.Secret]</code> — if none exists it calls <code>secret_model.InsertEncryptedSecret</code> (new row, data encrypted at rest), otherwise it calls <code>secret_model.UpdateSecret</code> on the existing row's ID (update in place, preserving the secret's ID and audit history). <code>DeleteSecretByID</code>/<code>DeleteSecretByName</code> both first resolve to exactly one matching row via <code>FindSecretsOptions</code> and return <code>secret_model.ErrSecretNotFound{}</code> if zero or more than one row matches, then delete by primary key.</p>
<p>This single service package is reused by every scope's controller, which is what keeps org/repo/env-style secrets management consistent across the codebase:</p>

<p>Because <code>FindSecretsOptions.ToConds()</code> (<code>models/secret/secret.go</code>) special-cases <code>RepoID != 0</code> by forcing <code>OwnerID</code> to <code>0</code> in the query, a caller can safely always pass both IDs (one of which is <code>0</code>) without accidentally matching secrets from the wrong scope — this is the same "belongs to" disambiguation guard called out for <code>ActionRunner</code> and <code>ActionRun</code> above. <code>CountWrongRepoLevelSecrets</code>/<code>UpdateWrongRepoLevelSecrets</code> (also in <code>models/secret/secret.go</code>) exist as a one-time repair migration for legacy rows that had <code>OwnerID</code> set on what should have been a pure repo-level secret.</p>
<h3 id="precedence">Precedence<a href="#precedence" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>GetVariablesOfRun</code> (<code>models/actions/variable.go</code>) resolves variables with <strong>repo &gt; org/user &gt; global</strong> precedence, by simply iterating global, then owner, then repo variables into the same map (later writes win):</p>
<pre class="highlight"><code class="language-go">for _, v := range append(globalVariables, append(ownerVariables, repoVariables...)...) {
    variables[v.Name] = v.Data
}</code></pre>
<p>Secrets (<code>GetSecretsOfTask</code>, <code>models/secret/secret.go</code>) follow the same idea but only across <strong>owner + repo</strong> (no global tier), and always seed two auto-generated tokens first:</p>
<pre class="highlight"><code class="language-go">baseSecrets["GITHUB_TOKEN"] = task.Token
baseSecrets["GITEA_TOKEN"] = task.Token</code></pre>
<h3 id="fork-pull-request-restriction">Fork pull request restriction<a href="#fork-pull-request-restriction" class="heading-anchor" aria-label="Link">#</a></h3>
<p>If the run is a fork pull request (<code>task.Job.Run.IsForkPullRequest</code>) and the trigger wasn't <code>pull_request_target</code> (which intentionally runs in base-branch context and is therefore trusted), <strong>only</strong> the two auto-tokens are exposed — all user-defined secrets are withheld to prevent a malicious fork PR from exfiltrating repository secrets.</p>
<h3 id="reusable-workflow-scoping-getscopedsecretsforjob">Reusable workflow scoping (<code>getScopedSecretsForJob</code>)<a href="#reusable-workflow-scoping-getscopedsecretsforjob" class="heading-anchor" aria-label="Link">#</a></h3>
<p>For jobs with a non-zero <code>ParentJobID</code> (children of a reusable-workflow caller), secret visibility recurses up the caller chain and applies each caller's declared <code>secrets:</code> policy stored on <code>CallSecrets</code>:</p>
<pre class="highlight"><code class="language-go">func getScopedSecretsForJob(ctx context.Context, job *actions_model.ActionRunJob, baseSecrets map[string]string) (map[string]string, error) {
    if job.ParentJobID == 0 {
        return baseSecrets, nil
    }
    caller, _ := actions_model.GetRunJobByRunAndID(ctx, job.RunID, job.ParentJobID)
    parentScope, _ := getScopedSecretsForJob(ctx, caller, baseSecrets)

    if caller.CallSecrets == jobparser.SecretsInherit {
        return parentScope, nil // "secrets: inherit" — pass everything through unchanged
    }
    // otherwise: only auto-tokens + explicitly aliased secrets are exposed
    scoped := map[string]string{"GITHUB_TOKEN": baseSecrets["GITHUB_TOKEN"], ...}
    // ... maps aliases from caller.CallSecrets JSON object
}</code></pre>
<p>This means a reusable workflow caller with no <code>secrets:</code> section (or an explicit alias mapping) creates a hard secret boundary: the callee only ever sees the auto-generated tokens plus whatever was explicitly named, never the caller's full secret set — unless the caller wrote <code>secrets: inherit</code>.</p>
<h3 id="runtime-tokens-vs-stored-secrets">Runtime tokens vs. stored secrets<a href="#runtime-tokens-vs-stored-secrets" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Beyond user secrets, every task gets a short-lived <strong>Gitea runtime token</strong> (<code>gitea_runtime_token</code>, minted per <code>(task, run, job)</code> by <code>CreateAuthorizationToken</code> in <code>services/actions/context.go</code>/<code>auth.go</code>) injected into the task context alongside the classic <code>token</code>/<code>GITHUB_TOKEN</code>. This is the credential the <code>actions/checkout</code>-equivalent and Gitea API calls from within a workflow actually use, distinct from any user-configured secret.</p>
<h2 id="scoped-workflows">Scoped Workflows<a href="#scoped-workflows" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea Actions supports <strong>scoped workflows</strong>: workflow files that live in a <code>.gitea/scoped_workflows</code> directory of a <em>different</em> ("source") repository but can be triggered by events in a <em>consuming</em> repository, letting an organization centralize CI templates. The relevant pieces:</p>
<ul>
<li><code>modules/actions/scoped_workflows.go</code> — <code>ListScopedWorkflows</code>/<code>ParseScopedWorkflows</code> read and parse workflow files from the source repo's <code>SCOPED_WORKFLOW_DIRS</code>; <code>MatchScopedWorkflows</code> evaluates them against a consuming event using the exact same <code>workflowpattern</code> matching logic as ordinary workflows.</li>
<li><code>models/actions/scoped_workflow.go</code> — the mapping between source and consumer repos, plus <code>ScopedStatusContextPrefix</code> used to disambiguate commit-status context names.</li>
<li><code>services/actions/scoped_workflow_cache.go</code> — caches parsed scoped-workflow metadata to avoid re-parsing on every event.</li>
<li>On <code>ActionRun</code>, <code>IsScopedRun</code>, <code>WorkflowRepoID</code>, and <code>WorkflowCommitSHA</code> distinguish a scoped run from a normal one; <code>WorkflowLink()</code> includes <code>scoped_workflow_source_repo_id</code> in the generated URL so the UI can disambiguate two differently-sourced workflows that happen to share a file name.</li>
</ul>
<h2 id="job-scheduling-and-dependency-resolution-servicesactionsjob_emittergo">Job Scheduling and Dependency Resolution (<code>services/actions/job_emitter.go</code>)<a href="#job-scheduling-and-dependency-resolution-servicesactionsjob_emittergo" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Jobs with <code>needs:</code> dependencies start life as <code>StatusBlocked</code> and only transition to <code>StatusWaiting</code> (eligible for <code>FetchTask</code> pickup) once their dependencies finish. This is handled by an internal debounced queue:</p>
<pre class="highlight"><code class="language-go">var jobEmitterQueue *queue.WorkerPoolQueue[*jobUpdate]

func EmitJobsIfReadyByRun(runID int64) error {
    err := jobEmitterQueue.Push(&amp;jobUpdate{RunID: runID})
    if errors.Is(err, queue.ErrAlreadyInQueue) {
        return nil // coalesce: a check is already pending for this run
    }
    return err
}</code></pre>
<p>The queue handler (<code>jobEmitterQueueHandler</code> → <code>checkJobsByRunID</code>) re-evaluates, inside one DB transaction, which blocked jobs in the run can now proceed (<code>checkJobsOfCurrentRunAttempt</code>) and whether workflow-level concurrency cancellation needs to happen (<code>checkRunConcurrency</code>). Re-emission for any jobs that changed as a side effect (e.g. reusable-workflow expansion producing new child jobs) happens <strong>after</strong> the transaction commits, specifically to avoid a nested-transaction deadlock under immediate-mode queue backends. <code>EmitJobsIfReadyByRun</code> is called from <code>PrepareRunAndInsert</code> (initial job graph), <code>UpdateTask</code> (a job just finished), and <code>PickTask</code> — i.e. every place a job's status can change in a way that might unblock a downstream job.</p>
