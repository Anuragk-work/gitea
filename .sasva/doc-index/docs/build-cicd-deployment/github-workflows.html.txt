<h1>GitHub Workflows & Actions</h1>
<h1 id="github-workflows-actions">GitHub Workflows &amp; Actions</h1>
<p>Gitea's continuous integration and release pipelines are entirely defined under <code>.github/workflows/*.yml</code>, with shared logic factored into reusable composite actions under <code>.github/actions/*</code>. This page catalogs every workflow and custom action, what triggers it, and what it runs.</p>

<tr>

<th>Trigger</th>
<th>Purpose</th>
</tr>
</thead>

<td><code>pull-compliance.yml</code></td>
<td><code>pull_request</code></td>

</tr>
<tr>
<td><code>pull-db-tests.yml</code></td>
<td><code>pull_request</code></td>
<td>Full backend integration test matrix across SQLite/MySQL/PostgreSQL/MSSQL, plus unit tests</td>
</tr>
<tr>
<td><code>pull-e2e-tests.yml</code></td>
<td><code>pull_request</code></td>
<td>Playwright end-to-end browser tests</td>
</tr>
<tr>
<td><code>pull-docker-dryrun.yml</code></td>
<td><code>pull_request</code></td>
<td>Builds (but doesn't push) Docker images for amd64/arm64/riscv64 when Docker-related files change</td>
</tr>

<td><code>pull-labeler.yml</code></td>

<td><code>files-changed.yml</code></td>
<td><code>workflow_call</code> (reusable)</td>
<td>Computes path-filter outputs (<code>backend</code>, <code>frontend</code>, <code>docker</code>, …) consumed by other workflows to skip irrelevant jobs</td>
</tr>

</tr>

</tr>
<tr>

<h2 id="files-changedyml-path-filter-gatekeeper"><code>files-changed.yml</code> — Path-Filter Gatekeeper<a href="#files-changedyml-path-filter-gatekeeper" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Nearly every PR workflow starts by calling this <strong>reusable workflow</strong> (<code>uses: ./.github/workflows/files-changed.yml</code>) to avoid running expensive jobs when irrelevant files changed. It uses <a href="https://github.com/dorny/paths-filter"><code>dorny/paths-filter</code></a> to compute boolean outputs:</p>
<pre class="highlight"><code class="language-yaml">outputs:
  backend:    ${{ jobs.detect.outputs.backend }}
  frontend:   ${{ jobs.detect.outputs.frontend }}
  docs:       ${{ jobs.detect.outputs.docs }}
  actions:    ${{ jobs.detect.outputs.actions }}
  templates:  ${{ jobs.detect.outputs.templates }}
  docker:     ${{ jobs.detect.outputs.docker }}
  dockerfile: ${{ jobs.detect.outputs.dockerfile }}
  swagger:    ${{ jobs.detect.outputs.swagger }}
  yaml:       ${{ jobs.detect.outputs.yaml }}
  json:       ${{ jobs.detect.outputs.json }}
  e2e:        ${{ jobs.detect.outputs.e2e }}
  shell:      ${{ jobs.detect.outputs.shell }}</code></pre>
<p>The <code>backend</code> filter, for example, matches <code>**/*.go</code>, <code>templates/**/*.tmpl</code>, <code>go.mod</code>/<code>go.sum</code>, <code>Makefile</code>, <code>.golangci.yml</code>, fixtures, and integration test data — any of these trigger the full backend test matrix. Downstream jobs gate on these outputs, e.g.:</p>
<pre class="highlight"><code class="language-yaml">lint-backend:
  if: needs.files-changed.outputs.backend == 'true' || needs.files-changed.outputs.actions == 'true'
  needs: files-changed</code></pre>

<h2 id="pull-docker-dryrunyml-container-build-validation"><code>pull-docker-dryrun.yml</code> — Container Build Validation<a href="#pull-docker-dryrunyml-container-build-validation" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Validates that both <code>Dockerfile</code> and <code>Dockerfile.rootless</code> still build for multiple architectures, <strong>without pushing</strong> anything:</p>
<pre class="highlight"><code class="language-yaml">container-amd64:
  if: needs.files-changed.outputs.docker == 'true'
  steps:
    - uses: ./.github/actions/docker-dryrun
      with: { platform: linux/amd64 }
container-arm64:
  if: needs.files-changed.outputs.dockerfile == 'true'
  steps:
    - uses: ./.github/actions/docker-dryrun
      with: { platform: linux/arm64 }
container-riscv64: # same shape, linux/riscv64</code></pre>
<p>The <code>amd64</code> build runs whenever <strong>any</strong> docker-related file changes (fast, ~4 min, native arch). The <code>arm64</code>/<code>riscv64</code> builds — which require slow QEMU emulation (40-50 minutes) — only run when the <code>Dockerfile</code>(s) themselves change, to keep PR turnaround reasonable. See <a href="docker-and-packaging.html">Docker &amp; Packaging</a> for the Dockerfile internals this validates.</p>

<h3 id="release-nightlyyml"><code>release-nightly.yml</code><a href="#release-nightlyyml" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Triggered on every push to <code>main</code> or <code>release/v*</code> branches. Two parallel jobs:</p>
<ul>
<li><strong><code>nightly-binary</code></strong> (runs on the self-hosted <code>namespace-profile-gitea-release-binary</code> runner):</li>
<li><code>git fetch --unshallow --quiet --tags --force</code> (needed for accurate <code>git describe</code> versioning)</li>
<li><code>make deps-frontend deps-backend</code></li>
<li><code>make release</code> with <code>TAGS=bindata</code> — this is the same <code>xgo</code>-based cross-compile pipeline described in <a href="makefile-and-build.html#cross-compilation-via-xgo">Makefile &amp; Build System → Cross-Compilation via xgo</a></li>
<li>Installs Cosign, imports a GPG signing key (<code>GPGSIGN_KEY</code>/<code>GPGSIGN_PASSPHRASE</code> secrets), then for every artifact in <code>dist/release/*</code>: creates a Sigstore bundle (<code>cosign sign-blob ... --bundle *.sigstore.json</code>) <strong>and</strong> a detached GPG signature (<code>*.asc</code>)</li>
<li>
<p>Computes a cleaned branch name (e.g. <code>main-nightly</code>, <code>v1.22-nightly</code>) and uploads all <code>dist/release</code> artifacts to S3 under that prefix</p>
</li>
<li>
<p><strong><code>nightly-container</code></strong> (runs on <code>namespace-profile-gitea-release-docker</code>):</p>
</li>
<li>Sets up QEMU + Buildx for multi-arch builds</li>
<li>Computes Docker tags/annotations via <code>docker/metadata-action</code> for both the regular and <code>-rootless</code>-suffixed image flavors</li>
<li>Logs into Docker Hub and GHCR</li>
<li>Builds and pushes <code>linux/amd64,linux/arm64,linux/riscv64</code> images for <strong>both</strong> <code>Dockerfile</code> and <code>Dockerfile.rootless</code>, using separate registry-backed BuildKit cache scopes (<code>buildcache-rootful</code> / <code>buildcache-rootless</code>)</li>
</ul>
<h3 id="release-tag-rcyml-and-release-tag-versionyml"><code>release-tag-rc.yml</code> and <code>release-tag-version.yml</code><a href="#release-tag-rcyml-and-release-tag-versionyml" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Structurally near-identical to <code>release-nightly.yml</code>'s <code>nightly-binary</code> job (fetch tags → <code>make release</code> → Cosign + GPG sign → upload to S3), but triggered by pushing a Git tag instead of a branch push:</p>
<ul>
<li><code>release-tag-rc.yml</code> fires on tags matching <code>v1*-rc*</code> (release candidates)</li>
<li><code>release-tag-version.yml</code> fires on tags matching <code>v1.*</code> while excluding <code>v1*-rc*</code> and <code>v1*-dev</code> (stable releases), and additionally has <code>packages: write</code> permission to publish Docker images to GHCR</li>
</ul>
<h3 id="release-nightly-snapcraftyml"><code>release-nightly-snapcraft.yml</code><a href="#release-nightly-snapcraftyml" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Builds and publishes the Snap package (see <a href="docker-and-packaging.html#snapcraft-packaging">Docker &amp; Packaging → Snapcraft Packaging</a>) on every push to <code>main</code> or manual dispatch, using a matrix of <code>ubuntu-24.04</code> (amd64) and <code>ubuntu-24.04-arm</code> runners:</p>
<pre class="highlight"><code class="language-yaml">steps:
  - uses: actions/checkout@... 
    with: { fetch-depth: 0 }
  - uses: snapcore/action-build@...
    id: build
  - uses: snapcore/action-publish@...
    env: { SNAPCRAFT_STORE_CREDENTIALS: ${{ secrets.SNAPCRAFT_STORE_CREDENTIALS }} }
    with: { snap: ${{ steps.build.outputs.snap }}, release: latest/edge }</code></pre>

<h2 id="cache-seederyml-build-cache-warmup"><code>cache-seeder.yml</code> — Build Cache Warmup<a href="#cache-seederyml-build-cache-warmup" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Populates the Go module/build/lint caches scoped to <code>main</code> so that PR runs restore-only and start "warm." Triggered by pushes to <code>main</code> that touch <code>go.sum</code>, <code>.golangci.yml</code>, or the cache/setup action files themselves. Two jobs:</p>
<ul>
<li><strong><code>gobuild</code></strong>: builds the backend with both <code>TAGS=bindata</code> and <code>TAGS="bindata gogit"</code>, then warms the <strong>test compile</strong> cache for both tag sets (<code>GOTEST_FLAGS: -race -list=^$$ -count=1</code> — compiles tests without running any), and finally warms the <strong>integration test compile</strong> cache for three tag/race combinations.</li>
<li><strong><code>lint</code></strong>: runs <code>make generate-go</code> + <code>make lint-backend</code> under a matrix (currently just <code>{tags: bindata, target: lint-backend}</code>) with <code>lint-cache: "true"</code> to populate the <code>golangci-lint</code> cache.</li>
</ul>
<p>The extensive header comment in the file explains the cache-scoping model precisely — see <a href="#go-cache"><code>.github/actions/go-cache</code></a> below for the restore/save split this depends on.</p>
<h2 id="giteabotyml-and-giteabot-backportyml-pr-automation-bot"><code>giteabot.yml</code> and <code>giteabot-backport.yml</code> — PR Automation Bot<a href="#giteabotyml-and-giteabot-backportyml-pr-automation-bot" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>giteabot.yml</code> runs the <a href="https://github.com/go-gitea/giteabot"><code>go-gitea/giteabot</code></a> action across a wide set of triggers: <code>push</code> to <code>main</code> (to promptly re-run merge-queue maintenance), <code>pull_request_target</code> (label/status maintenance — deliberately annotated <code>zizmor: ignore[dangerous-triggers]</code> since it only runs a pinned action and never checks out PR HEAD code), <code>pull_request_review</code>, a daily cron backstop, and <code>workflow_dispatch</code> for manual debugging.</p>
<pre class="highlight"><code class="language-yaml">concurrency:
  group: ${{ format('{0}-{1}', github.workflow, (github.event_name == 'pull_request_target' || ...) &amp;&amp; format('pr-{0}', github.event.pull_request.number) || 'maintenance') }}
  cancel-in-progress: false

jobs:
  giteabot:
    steps:
      - uses: go-gitea/giteabot@912675d47455ac93be82d8bda4667a02b20a6fe4 # v1.0.4
        with:
          github_token: ${{ secrets.GITEABOT_TOKEN || github.token }}
          checks: ${{ github.event.inputs.checks || 'labels,merge_queue,lock,feedback,last_call,milestones,lgtm,translation_comment,pr_actions' }}</code></pre>
<p>The default <code>checks</code> list drives: label syncing, merge-queue promotion, PR locking, contributor feedback nudges, "last call" reminders, milestone assignment, <code>lgtm</code> label management, translation-PR comments, and other bot-triggered PR actions. <code>giteabot-backport.yml</code> handles the separate automated-backport-PR-creation flow triggered by backport labels.</p>
<p><code>pull-labeler.yml</code> is a related but distinct workflow: it uses <code>actions/labeler</code> (path-based auto-labeling with <code>sync-labels: true</code>) plus a <code>pr-title</code> job that lints PR titles for non-draft PRs.</p>

<h3 id="go-cache-restoresave-split"><code>go-cache</code> Restore/Save Split<a href="#go-cache-restoresave-split" class="heading-anchor" aria-label="Link">#</a></h3>
<p>The <code>go-cache</code> action deliberately only <strong>saves</strong> caches when running inside the <code>cache-seeder</code> workflow, and only <strong>restores</strong> (via <code>actions/cache/restore</code>, with <code>restore-keys</code> fallback) everywhere else:</p>
<pre class="highlight"><code class="language-yaml">- if: ${{ github.workflow == 'cache-seeder' }}
  uses: actions/cache@...
  with: { path: ~/go/pkg/mod, key: gomod-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles('go.sum') }} }
- if: ${{ github.workflow != 'cache-seeder' }}
  uses: actions/cache/restore@...
  with:
    path: ~/go/pkg/mod
    key: gomod-${{ runner.os }}-${{ runner.arch }}-${{ hashFiles('go.sum') }}
    restore-keys: gomod-${{ runner.os }}-${{ runner.arch }}</code></pre>
<p>This avoids cache-key contention: only <code>cache-seeder</code>'s <code>gobuild</code> job ever writes the cache (populated by pushes to <code>main</code>), so PR runs always get a clean, bounded-size warm start via <code>restore-keys</code> fallback instead of every PR job racing to write its own cache entry.</p>
