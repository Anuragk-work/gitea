<h1>Third-Party Integrations</h1>
<h1 id="third-party-integrations">Third-Party Integrations</h1>
<p>Beyond outgoing webhooks (covered in <a href="webhook-delivery-pipeline.html">Webhook Delivery Pipeline</a>
and <a href="webhook-event-types-and-payloads.html">Webhook Event Types &amp; Payloads</a>), Gitea exposes and
consumes several other integration surfaces that let external systems act on behalf of a user
or pull/push data in and out of a Gitea instance. This page documents:</p>
<ol>
<li><strong>OAuth2 application registration</strong> — Gitea as an OAuth2/OIDC <em>provider</em> for third-party
   apps (CLIs, mobile apps, other SaaS products) that want to act on a user's behalf.</li>
<li><strong>External issue tracker / external wiki units</strong> — redirecting a repository's Issues/Wiki
   tab to a third-party system instead of Gitea's own.</li>
<li><strong>Repository migration &amp; mirroring downloaders</strong> — pulling repository data (and, for some
   services, issues/PRs/releases/labels) from other Git hosting services.</li>
<li><strong>Package registry protocol endpoints</strong> — Gitea acting as a drop-in registry for existing
   third-party package-manager clients (npm, Docker, Cargo, NuGet, ...).</li>
<li><strong>Inbound webhook-style consumers</strong> — the reverse direction, where Gitea itself receives
   calls from CI systems / other tools (commit statuses, mirrored pushes).</li>
</ol>
<p>Verified against <code>models/auth/oauth2.go</code>, <code>routers/web/user/setting/oauth2*.go</code>,
<code>routers/web/admin/applications.go</code>, <code>routers/web/org/setting_oauth2.go</code>,
<code>models/repo/repo_unit.go</code>, <code>services/migrations/</code>, and <code>routers/api/packages/</code>.</p>
<h2 id="1-oauth2-application-registration">1. OAuth2 application registration<a href="#1-oauth2-application-registration" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea can act as a full OAuth2 (+ OpenID Connect) <strong>provider</strong>, issuing access/refresh/ID
tokens to third-party applications that register an <code>OAuth2Application</code>. This is the mechanism
by which external tools integrate with a Gitea instance <em>as the logged-in user</em>, without ever
seeing that user's password — e.g. a desktop Git client offering "Sign in with Gitea", a mobile
app, a CI/CD SaaS product, or an internal company tool.</p>
<blockquote>
<p>This is the deep-dive summary for the integrations page; the full technical treatment of the
Authorization Code + PKCE flow, <code>OAuth2Grant</code>, scopes, and every OAuth2 provider endpoint
lives in
<a href="../11-authentication/tokens-and-oauth-apps.html#oauth2-applications--gitea-as-a-provider">Access Tokens &amp; OAuth2 Applications</a>.
This section focuses on the <em>registration</em> surface — who can register an app, at what scope,
and through which UI/route.</p>
</blockquote>
<h3 id="registration-scopes-user-organization-and-instance-wide">Registration scopes: user, organization, and instance-wide<a href="#registration-scopes-user-organization-and-instance-wide" class="heading-anchor" aria-label="Link">#</a></h3>

<h3 id="instance-wide-builtin-applications">Instance-wide "builtin" applications<a href="#instance-wide-builtin-applications" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Separately from user-registered apps, <code>auth.BuiltinApplications()</code> hardcodes a small,
fixed set of pre-registered <code>OAuth2Application</code>s for Gitea's own first-party tooling:
<code>git-credential-oauth</code>, Git Credential Manager, and the <code>tea</code> CLI, each with a pre-set
<code>http(s)://127.0.0.1</code> redirect URI so those tools work out of the box against any Gitea
instance without an administrator needing to register them manually. <code>Init(ctx)</code>
(called during application start-up) reconciles the DB against
<code>setting.OAuth2.DefaultApplications</code> — administrators can trim this list in <code>app.ini</code> to
disable specific builtin integrations instance-wide. The admin applications page
(<code>/-/admin/applications</code>) surfaces both the DB-registered global apps and this builtin list
(<code>ctx.Data["BuiltinApplications"]</code>) for visibility, though builtin apps are not editable through
the UI.</p>
<h3 id="consuming-the-registration-what-a-third-party-does-with-it">Consuming the registration: what a third party does with it<a href="#consuming-the-registration-what-a-third-party-does-with-it" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Once registered, a third-party application's typical flow (fully detailed in
<a href="../11-authentication/tokens-and-oauth-apps.html">Access Tokens &amp; OAuth2 Applications</a>) is:</p>
<ol>
<li>Redirect the user to <code>/login/oauth/authorize</code> with <code>client_id</code>, <code>redirect_uri</code>,
   <code>response_type=code</code>, <code>scope</code>, and (for public clients) a PKCE <code>code_challenge</code>.</li>
<li>The user reviews and approves a consent screen (unless <code>SkipSecondaryAuthorization</code> and a
   prior grant exists), creating/updating an <code>OAuth2Grant</code> row.</li>
<li>Gitea redirects back to <code>redirect_uri</code> with a short-lived <code>code</code>.</li>
<li>The third party exchanges the code (plus <code>client_secret</code> for confidential clients, or
   <code>code_verifier</code> for PKCE) at <code>/login/oauth/access_token</code> for access/refresh/ID tokens.</li>
<li>The access token is then used exactly like a scoped Personal Access Token on subsequent API
   calls (<code>Authorization: Bearer &lt;token&gt;</code>), and <code>/login/oauth/userinfo</code> /
   <code>/.well-known/openid-configuration</code> provide standard OIDC discovery/userinfo support for
   identity-focused integrations (e.g. "Login with Gitea" SSO buttons on other products).</li>
</ol>
<h3 id="revocation-audit-surface">Revocation &amp; audit surface<a href="#revocation-audit-surface" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Every OAuth2 grant a user has approved (for any application, at any registration scope they can
see) is listed on their own applications settings page (<code>ctx.Data["Grants"]</code>,
<code>GetOAuth2GrantsByUserID</code>) with a <strong>Revoke</strong> action (<code>RevokeOAuth2Grant</code> /
<code>OAuth2CommonHandlers.RevokeGrant</code>) — revoking immediately invalidates every access/refresh
token tied to that grant, since token validation re-loads the grant by ID on every request.</p>
<h2 id="2-external-issue-tracker-external-wiki">2. External issue tracker &amp; external wiki<a href="#2-external-issue-tracker-external-wiki" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A repository can delegate its <strong>Issues</strong> and/or <strong>Wiki</strong> unit entirely to a third-party system
instead of using Gitea's built-in tracker/wiki — the repo's "Issues" and "Wiki" tabs simply
become external links, and Gitea does no data storage or synchronization for that unit at all.
This is the simplest possible "integration": a redirect, configured per-repository through
<code>RepoUnit.Config</code>:</p>
<pre class="highlight"><code class="language-go">// models/repo/repo_unit.go
type ExternalWikiConfig struct {
    ExternalWikiURL string
}

type ExternalTrackerConfig struct {
    ExternalTrackerURL           string
    ExternalTrackerFormat        string // e.g. "https://issues.example.com/{user}/{repo}/issues/{index}"
    ExternalTrackerStyle         string // "numeric" | "alphanumeric" | "regexp"
    ExternalTrackerRegexpPattern string // used when Style == "regexp", to recognize issue refs in commit messages
}</code></pre>
<p>When <code>unit.TypeExternalTracker</code> is enabled for a repo, its <code>ExternalTrackerFormat</code> is injected
into the Markdown-rendering metas map (<code>metas["format"]</code>, <code>metas["style"]</code>,
<code>metas["regexp"]</code> — see <code>repo.go</code>'s <code>ComposeCommentMetas</code>) so that references like <code>#123</code> inside
commit messages, issue bodies, and PR descriptions are rewritten as links to the external
tracker rather than to Gitea's own (disabled) issue tracker. This makes the integration
transparent throughout the rest of the UI — a repo using an external tracker still gets
clickable issue references everywhere Gitea would normally cross-link its own issues.</p>

<h2 id="4-package-registry-protocol-endpoints-gitea-as-a-drop-in-registry">4. Package registry protocol endpoints — Gitea as a drop-in registry<a href="#4-package-registry-protocol-endpoints-gitea-as-a-drop-in-registry" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>routers/api/packages/</code> implements the <em>actual wire protocols</em> of numerous package-manager
ecosystems (npm, Docker/OCI, Cargo, Composer, Maven, NuGet, PyPI, Helm, Conda, Debian, RPM,
Conan, Go proxy, Vagrant, Chef, and more), so that unmodified third-party package-manager
<strong>clients</strong> (<code>npm publish</code>, <code>docker push</code>, <code>cargo publish</code>, <code>dotnet nuget push</code>, ...) can treat a
Gitea instance as their registry with zero client-side plugin/configuration beyond a
credentials/URL change. This is the mirror image of the OAuth2 provider section above: instead
of a third-party <em>application</em> authenticating a <em>user</em>, here a third-party <em>CLI tool</em>
authenticates against Gitea using ecosystem-native credential conventions (<code>.npmrc</code> tokens,
<code>~/.cargo/credentials</code>, Basic Auth, NuGet API keys, <code>docker login</code>, ...) that those tools already
know how to send.</p>
<p>This surface is documented in full — routes, per-ecosystem auth middleware, and the OCI
container-registry token-exchange flow — in
<a href="../07-rest-api/packages-and-actions-api.html#packages-registry-api-routersapipackages">Packages &amp; Actions API</a>.
It is mentioned here because, architecturally, it is Gitea's largest and most protocol-diverse
third-party integration surface, even though it is not built on the webhook/OAuth2 machinery
described elsewhere on this page.</p>
<h2 id="5-inbound-integrations-commit-statuses-from-ci-systems">5. Inbound integrations: commit statuses from CI systems<a href="#5-inbound-integrations-commit-statuses-from-ci-systems" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The reverse direction — external systems pushing data <em>into</em> Gitea rather than Gitea notifying
<em>out</em> — is most commonly exercised by CI/CD systems reporting build results back onto a commit,
via the commit status API (<code>POST /repos/{owner}/{repo}/statuses/{sha}</code>, modeled by
<code>git_model.CommitStatus</code>). A typical third-party CI integration:</p>
<ol>
<li>Registers an outgoing webhook (<code>push</code> and/or <code>pull_request</code> events) on the repository so it
   is notified when there's new work to build — see
   <a href="webhook-delivery-pipeline.html">Webhook Delivery Pipeline</a>.</li>
<li>Runs its build/test pipeline against the referenced commit.</li>
<li>Reports the outcome back via the commit status API, which Gitea then surfaces on the commit,
   PR checks list, and (via <code>notify.CreateCommitStatus</code> — see
   <a href="../09-core-modules/notify-mailer-webhook.html">Notifications, Mailer &amp; Webhooks</a>) fans back out
   to a <code>status</code> webhook event and, for a matching branch, potentially blocks merge via branch
   protection required-status-check rules (see
   <a href="../13-issues-pullrequests/branch-protection-and-merge.html">Branch Protection &amp; Merge</a>).</li>
</ol>
<p>This "outgoing webhook notifies → external system does work → external system calls back via
API" round trip is the canonical integration pattern for third-party CI/CD, code-quality, and
security-scanning tools that don't use Gitea Actions directly.</p>

    if(!hits.length)html='<div style="padding:8px 12px;color:var(--text-dim);font-size:0.8rem">No results</div>';
    searchResults.innerHTML=html;
  });
})();

<script>
(function(){
  // Mermaid expand buttons — added AFTER mermaid renders (so button is on wrapper, not inside pre)
  var overlay=document.getElementById('mermaid-overlay');
  var overlayInner=document.getElementById('mermaid-overlay-inner');
  function _addMermaidButtons(){
    document.querySelectorAll('.mermaid,pre.mermaid').forEach(function(el){
      if(el.dataset.expandAdded)return;
      el.dataset.expandAdded='1';
      // Wrap in a div so the button is a sibling of pre, not inside it
      var wrapper=document.createElement('div');
      wrapper.style.cssText='position:relative;display:inline-block;width:100%;';
      el.parentNode.insertBefore(wrapper,el);
      wrapper.appendChild(el);
      var btn=document.createElement('button');
      btn.className='mermaid-expand';btn.textContent='⛶';btn.title='Expand diagram';
      btn.addEventListener('click',function(e){
        e.stopPropagation();
        var clone=el.cloneNode(true);
        delete clone.dataset.expandAdded;
        clone.removeAttribute('data-expand-added');
        clone.style.cssText='background:none;border:none;padding:0;margin:0;text-align:center;min-width:70vw;max-width:90vw;';
        // Clear overlay content safely, keep close button
        overlayInner.innerHTML='';
        var closeBtn=document.createElement('button');
        closeBtn.className='mermaid-overlay-close';closeBtn.textContent='×';closeBtn.title='Close';
        closeBtn.addEventListener('click',function(){overlay.classList.remove('open');});
        overlayInner.appendChild(clone);
        overlayInner.appendChild(closeBtn);
        overlay.classList.add('open');
        // Re-run mermaid on the clone after it's in the DOM
        setTimeout(function(){
          if(window.mermaid){
            try{mermaid.run({nodes:[clone]});}catch(err){}
          }
        },50);
      });
      wrapper.appendChild(btn);
    });
  }
  // Wait for mermaid to finish rendering before adding buttons (mermaid init runs above)
  setTimeout(_addMermaidButtons,800);
  if(overlay){
    overlay.addEventListener('click',function(e){if(e.target===overlay)overlay.classList.remove('open');});
    document.addEventListener('keydown',function(e){if(e.key==='Escape')overlay.classList.remove('open');});
  }
  // Code copy buttons
  document.querySelectorAll('pre').forEach(function(pre){
    if(pre.classList.contains('mermaid'))return;
    var btn=document.createElement('button');
    btn.className='code-copy';btn.textContent='Copy';
    btn.addEventListener('click',function(){
      var code=pre.querySelector('code');
      var text=code?code.textContent:pre.textContent;
      navigator.clipboard.writeText(text).then(function(){btn.textContent='Copied!';setTimeout(function(){btn.textContent='Copy';},2000);});
    });
    pre.appendChild(btn);
  });
  // Back to top
  var btt=document.getElementById('back-to-top');
  if(btt){
    window.addEventListener('scroll',function(){btt.style.display=window.scrollY>300?'flex':'none';});
    btt.addEventListener('click',function(){window.scrollTo({top:0,behavior:'smooth'});});
  }
  // TOC active scroll tracking
  var tocLinks=document.querySelectorAll('.toc-aside a[data-anchor]');
  if(tocLinks.length>0){
    var headingEls=[];
    tocLinks.forEach(function(l){var el=document.getElementById(l.dataset.anchor);if(el)headingEls.push({el:el,link:l});});
    var tocAside=document.querySelector('.toc-aside');
    var onScroll=function(){
      var scrollPos=window.scrollY+80;
      var active=null;
      for(var i=0;i<headingEls.length;i++){if(headingEls[i].el.offsetTop<=scrollPos)active=headingEls[i];}
      tocLinks.forEach(function(l){l.classList.remove('toc-active');});
      if(active){
        active.link.classList.add('toc-active');
        // Scroll active link into view within the TOC panel, not the page
        if(tocAside){
          var linkTop=active.link.offsetTop-tocAside.offsetTop;
          var visibleTop=tocAside.scrollTop;
          var visibleBottom=visibleTop+tocAside.clientHeight;
          if(linkTop<visibleTop+40||linkTop>visibleBottom-40){
            tocAside.scrollTop=linkTop-tocAside.clientHeight/2;
          }
        }
      }
    };
    window.addEventListener('scroll',onScroll);
    onScroll();
    // Prevent TOC links from scrolling the TOC panel to top on click
    tocLinks.forEach(function(l){
      l.addEventListener('click',function(e){
        e.preventDefault();
        var anchor=l.dataset.anchor;
        var target=document.getElementById(anchor);
        if(target){target.scrollIntoView({behavior:'smooth',block:'start'});}
      });
    });
  }
  // Persist sidebar scroll position across page navigations
  var sidebarEl=document.querySelector('nav.sidebar');
  if(sidebarEl){
    var sidebarKey='sasva-sidebar-scroll';
    // Restore scroll position on page load
    var savedScroll=sessionStorage.getItem(sidebarKey);
    if(savedScroll){sidebarEl.scrollTop=parseInt(savedScroll,10);}
    // Save scroll position before navigating away
    document.querySelectorAll('#sidebar-nav-links a').forEach(function(a){
      a.addEventListener('click',function(){
        sessionStorage.setItem(sidebarKey,String(sidebarEl.scrollTop));
      });
    });
    // Also scroll active item into view on load
    var activeLink=sidebarEl.querySelector('a.active');
    if(activeLink&&!savedScroll){
      var linkOffset=activeLink.offsetTop-sidebarEl.offsetTop;
      sidebarEl.scrollTop=Math.max(0,linkOffset-sidebarEl.clientHeight/2);
    }
  }
})();
