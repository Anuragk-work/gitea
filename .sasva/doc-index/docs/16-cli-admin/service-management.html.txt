<h1>Running Gitea as a System Service</h1>
<h1 id="running-gitea-as-a-system-service">Running Gitea as a System Service</h1>
<p>Gitea itself has no daemonization logic — <code>gitea web</code> runs in the foreground,
logs to stdout/stderr (or files, per <code>app.ini</code>), and relies on the OS's
process supervisor for start-on-boot, automatic restart on crash, and clean
shutdown signal delivery. The upstream repository ships ready-to-adapt unit
files/init scripts for every major init system under
<a href="../../contrib/service"><code>contrib/service/</code></a>, covering Linux (systemd,
legacy SysV init, OpenRC/Gentoo), the BSDs (FreeBSD <code>rc.d</code>, OpenBSD <code>rc.d</code>),
OpenWrt (<code>procd</code>), Solaris/illumos (SMF), macOS (<code>launchd</code>), and the
process-manager-agnostic <strong>Supervisor</strong> as a fallback for any platform.</p>
<p>All of these scripts converge on the same invocation as their actual
workload:</p>
<pre class="highlight"><code class="language-sh">gitea web --config /etc/gitea/app.ini</code></pre>
<p>run as a dedicated, unprivileged <code>git</code> OS user, with the working directory
set to Gitea's data directory (<code>GITEA_WORK_DIR</code>) so that relative paths in
<code>app.ini</code> (repositories, LFS objects, logs, etc.) resolve correctly. See
<a href="../03-getting-started/running-gitea.html">Getting Started — Running Gitea</a> for
the underlying <code>web</code> command flags and
<a href="../03-getting-started/configuration-app-ini.html">Configuration (<code>app.ini</code>)</a>
for <code>WORK_PATH</code>/<code>GITEA_WORK_DIR</code> semantics.</p>

<td>Binary path</td>

</tr>
<tr>

</tr>

</tr>
<tr>
<td>Restart policy</td>
<td>"always"/"automatic"</td>
<td>The service manager restarts Gitea if it crashes</td>
</tr>
</tbody>
</table>
<p>Every script sets <strong><code>GITEA_WORK_DIR</code></strong> (and usually <code>USER</code>/<code>HOME</code>) as
environment variables rather than relying on <code>gitea</code>'s <code>--work-path</code> flag —
this mirrors how <code>cmd/main.go</code>'s <code>prepareWorkPathAndCustomConf</code> resolves the
work path from flags, environment variables, or discovery, in that priority
order (see <a href="cli-commands.html#entry-point--app-assembly">CLI &amp; Admin Operations</a>).
Because none of these scripts pass <code>--work-path</code> explicitly, the environment
variable is what ultimately determines <code>setting.AppWorkPath</code> at process
start.</p>
<blockquote>
<p>Regardless of init system, <code>gitea</code> should <strong>never</strong> be run directly as
<code>root</code> in production — do a privileged one-time <code>chown -R git:git</code> of the
data directories, and let the unprivileged <code>git</code> account own the running
process. The only common exception is binding to a port below 1024
(<code>80</code>/<code>443</code>), for which several scripts show a commented-out
<code>setcap cap_net_bind_service=+ep</code> line rather than suggesting running as
root.</p>
</blockquote>
<h2 id="systemd-contribservicesystemdgiteaservice">systemd (<code>contrib/service/systemd/gitea.service</code>)<a href="#systemd-contribservicesystemdgiteaservice" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The most common production deployment target on modern Linux distributions
(Debian, Ubuntu, RHEL/Fedora, Arch, etc.).</p>
<pre class="highlight"><code class="language-ini">[Unit]
Description=Gitea (Git with a cup of tea)
After=network.target

[Service]
RestartSec=2s
Type=simple
User=git
Group=git
WorkingDirectory=/var/lib/gitea/
ExecStart=/usr/local/bin/gitea web --config /etc/gitea/app.ini
Restart=always
Environment=USER=git HOME=/home/git GITEA_WORK_DIR=/var/lib/gitea

[Install]
WantedBy=multi-user.target</code></pre>
<p>Notable commented-out extension points in the shipped unit file:</p>
<ul>
<li><strong>Database ordering</strong> — <code>Wants=</code>/<code>After=</code> blocks for <code>mysql.service</code>,
  <code>mariadb.service</code>, <code>postgresql.service</code>, <code>memcached.service</code>, and
  <code>redis.service</code>, so systemd starts the DB/cache before Gitea when they run
  on the same host.</li>
<li><strong>Socket activation</strong> — an <code>After=gitea.main.socket</code> /
  <code>Requires=gitea.main.socket</code> pairing plus an example companion
  <code>gitea.main.socket</code> unit (<code>ListenStream=&lt;port&gt;</code>), letting systemd own the
  listening socket and hand it to Gitea on first connection (reduces
  systemd-startup-order races and permits binding to privileged ports without
  capabilities).</li>
<li><strong><code>LimitNOFILE=524288:524288</code></strong> — raises the open-file-descriptor limit for
  repositories with very large numbers of files (avoids spurious HTTP 500s).</li>
<li><strong><code>RuntimeDirectory=gitea</code></strong> — when using a Unix socket for the HTTP
  listener, this tells systemd to create <code>/run/gitea</code> (which persists across
  reboots, unlike a manually created directory).</li>
<li><strong>Non-default git PATH</strong> — <code>Environment=PATH=/path/to/git/bin:...</code>, needed
  when a side-installed Git version (with <code>git-lfs</code> alongside it) should take
  precedence over the distro's Git.</li>
<li><strong>Binding to privileged ports</strong> — <code>CapabilityBoundingSet=CAP_NET_BIND_SERVICE</code></li>
<li><code>AmbientCapabilities=CAP_NET_BIND_SERVICE</code> grant the capability without
  running as root; <code>PrivateUsers=false</code> is documented as a companion setting
  when capabilities need to reach the Gitea process despite the unit's
  sandboxing.</li>
</ul>

<p>Because <code>RestartSec</code>/<code>Restart=always</code> already gives systemd ownership of
process supervision, deployments that let systemd manage restarts should
generally <strong>turn off</strong> Gitea's own <code>SIGHUP</code>-based fork-and-hand-off by
setting <code>[server] ALLOW_GRACEFUL_RESTARTS = false</code> in <code>app.ini</code> (the setting
defaults to <code>true</code>, i.e. <code>SIGHUP</code>-triggered forking is enabled unless
explicitly disabled) — sending <code>SIGHUP</code> to a process that then forks a
<em>second</em>, systemd-untracked process would confuse systemd's cgroup/PID
tracking for the unit. When <code>ALLOW_GRACEFUL_RESTARTS</code> is <code>false</code>,
<code>graceful.Manager.DoGracefulRestart()</code> skips forking entirely and simply
performs a normal <code>doShutdown()</code> — systemd's <code>Restart=always</code> then starts a
fresh, properly tracked process. See
<a href="cli-commands.html#restart-mechanics-modulesgracefulrestart_unixgo">Restart mechanics</a>.</p>
<p>Gitea's graceful manager also participates in the <strong>systemd notify
protocol</strong> (<code>Type=notify</code> is not set in the shipped unit, but the manager
code supports it): it reports <code>READY=1</code> and <code>MAINPID=&lt;pid&gt;</code> once startup
completes, <code>STOPPING=1</code> during shutdown, and pings the systemd watchdog if
<code>WATCHDOG_USEC</code> is present in the environment. To opt into this tighter
integration, change <code>Type=simple</code> to <code>Type=notify</code> in a local override.</p>
<p>Standard operational commands:</p>
<pre class="highlight"><code class="language-sh">sudo systemctl daemon-reload         # after editing the unit file
sudo systemctl enable --now gitea    # enable at boot + start now
sudo systemctl status gitea
sudo journalctl -u gitea -f          # follow logs (if logging to stdout/journal)</code></pre>
<h2 id="sysv-init-contribservicesysvinitgitea">SysV Init (<code>contrib/service/sysvinit/gitea</code>)<a href="#sysv-init-contribservicesysvinitgitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A traditional <code>/etc/init.d/gitea</code> LSB-style script for older/legacy
distributions without systemd. Declares LSB header metadata
(<code>Required-Start: $syslog $network</code>, <code>Default-Start: 2 3 4 5</code>) and implements
<code>start</code>/<code>stop</code>/<code>status</code>/<code>restart</code> using <strong><code>start-stop-daemon</code></strong>:</p>
<pre class="highlight"><code class="language-sh">DAEMON=/usr/local/bin/gitea
DAEMON_ARGS="web -c /etc/gitea/app.ini"
PIDFILE=/run/gitea.pid
WORKINGDIR=/var/lib/gitea
USER=git
STOP_SCHEDULE="${STOP_SCHEDULE:-QUIT/5/TERM/1/KILL/5}"</code></pre>
<ul>
<li><strong><code>do_start</code></strong> backgrounds the process via <code>start-stop-daemon --start
  --background --make-pidfile --chdir $WORKINGDIR --chuid $USER</code>, wrapping
  the actual invocation in <code>/bin/bash -c '/usr/bin/env USER=... GITEA_WORK_DIR=... HOME=... gitea -- web -c ...'</code>
  so the environment variables are set before <code>gitea</code> executes.</li>
<li><strong><code>do_stop</code></strong> uses <code>start-stop-daemon --stop --retry=$STOP_SCHEDULE</code>, where
  <code>STOP_SCHEDULE=QUIT/5/TERM/1/KILL/5</code> means: send <code>SIGQUIT</code>, wait up to 5s,
  send <code>SIGTERM</code>, wait up to 1s, then <code>SIGKILL</code> as a last resort — a
  deliberately graduated escalation so a hung process still gets forcibly
  terminated within a bounded time, while giving Gitea's normal
  <code>SIGTERM</code>-triggered graceful shutdown a fair chance first.</li>
<li><strong><code>do_status</code></strong> checks <code>kill -0 $(cat $PIDFILE)</code> to report whether the
  recorded PID is actually alive (handles the classic "stale pidfile" case).</li>
<li>Configuration overrides live in <code>/etc/default/gitea</code> (sourced if present,
  standard Debian/Ubuntu convention), letting deployments override <code>USER</code>,
  <code>WORKINGDIR</code>, <code>DAEMON_ARGS</code>, or <code>STOP_SCHEDULE</code> without editing the script
  itself.</li>
</ul>
<p>Install by copying to <code>/etc/init.d/gitea</code>, <code>chmod +x</code>, then register with
<code>update-rc.d gitea defaults</code> (Debian family) or <code>chkconfig --add gitea</code>
(RHEL family).</p>
<h2 id="openrc-gentoo-contribservicegentoogitea">OpenRC / Gentoo (<code>contrib/service/gentoo/gitea</code>)<a href="#openrc-gentoo-contribservicegentoogitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>An <code>openrc-run</code> script (Gentoo, Alpine when using OpenRC instead of its
default <code>/etc/init.d</code> scripts, and other OpenRC-based distributions):</p>
<pre class="highlight"><code class="language-sh">#!/sbin/openrc-run
command="/usr/local/bin/gitea"
command_user="git"
command_args="web -c /etc/$RC_SVCNAME/app.ini"
command_background="yes"
pidfile="/run/$RC_SVCNAME/$RC_SVCNAME.pid"
start_stop_daemon_args="--user git --chdir /var/lib/gitea"</code></pre>
<ul>
<li><strong><code>depend()</code></strong> declares <code>need net</code> and comments out optional <code>after</code>
  dependencies on <code>postgresql</code>/<code>mysql</code>/<code>mariadb</code>/<code>memcached</code>/<code>redis</code> — the
  same "start the DB first" pattern as the systemd unit, expressed in
  OpenRC's dependency DSL.</li>
<li><strong><code>start_pre()</code></strong> calls <code>checkpath --directory --owner git:git --mode 0750</code>
  to ensure <code>/run/gitea</code> and <code>/var/log/gitea</code> exist with correct ownership
  before the daemon starts (OpenRC's <code>/run</code> is often tmpfs and needs
  recreating on every boot) — this replaces the systemd unit's
  <code>RuntimeDirectory=</code> equivalent. It also documents the same
  <code>setcap cap_net_bind_service=+ep</code> option for privileged ports.</li>
<li><code>command_background="yes"</code> tells <code>start-stop-daemon</code> (which OpenRC uses
  internally) to fork Gitea into the background itself, since <code>gitea web</code>
  does not daemonize on its own.</li>
</ul>
<p>Enable and control with:</p>
<pre class="highlight"><code class="language-sh">rc-update add gitea default
rc-service gitea start</code></pre>
<h2 id="openwrt-contribserviceopenwrtgitea">OpenWrt (<code>contrib/service/openwrt/gitea</code>)<a href="#openwrt-contribserviceopenwrtgitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>An <code>/etc/rc.common</code>-based <strong>procd</strong> service definition for OpenWrt routers/
embedded Linux, appropriate for small/ARM deployments:</p>
<pre class="highlight"><code class="language-sh">#!/bin/sh /etc/rc.common
USE_PROCD=1
START=90
STOP=10

start_service(){
    procd_open_instance gitea
    procd_set_param env GITEA_WORK_DIR=$GITEA_WORK_DIR
    procd_set_param env HOME=$GITEA_WORK_DIR
    procd_set_param command $PROG web -c $CONF_FILE
    procd_set_param file $CONF_FILE
    procd_set_param user git
    procd_set_param respawn ${respawn_threshold:-3600} ${respawn_timeout:-5} ${respawn_retry:-5}
    procd_close_instance
}</code></pre>
<ul>
<li><code>START=90</code>/<code>STOP=10</code> set this service to start late (after most other
  system services) and stop early during shutdown.</li>
<li><code>procd_set_param file $CONF_FILE</code> tells <code>procd</code> to <strong>watch the config file</strong>
  and automatically restart the <code>gitea</code> instance if <code>app.ini</code> changes on
  disk — a convenience not present in any of the other init systems.</li>
<li><code>procd_set_param respawn &lt;threshold&gt; &lt;timeout&gt; &lt;retry&gt;</code> configures
  automatic respawn-on-crash with rate limiting, to avoid crash-looping
  forever if Gitea fails to start repeatedly.</li>
<li>Exposes standard <code>start</code>/<code>stop</code>/<code>reload</code> shell functions delegating to
  <code>service_start</code>/<code>service_stop</code>/<code>service_reload $PROG</code>.</li>
</ul>
<h2 id="freebsd-rcd-contribservicefreebsdgitea">FreeBSD <code>rc.d</code> (<code>contrib/service/freebsd/gitea</code>)<a href="#freebsd-rcd-contribservicefreebsdgitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A standard FreeBSD <code>/usr/local/etc/rc.d/gitea</code> script using the <code>rc.subr</code>
framework:</p>
<pre class="highlight"><code class="language-sh">name="gitea"
rcvar="gitea_enable"
: ${gitea_user:="git"}
: ${gitea_directory:="/var/lib/gitea"}
command="/usr/local/bin/gitea web -c /etc/gitea/app.ini"
pidfile="${gitea_directory}/${name}.pid"</code></pre>
<ul>
<li>Controlled entirely through <code>/etc/rc.conf</code> variables — set
  <code>gitea_enable="YES"</code> to enable at boot, and optionally override
  <code>gitea_user</code>/<code>gitea_directory</code>.</li>
<li><code>gitea_start()</code> exports <code>USER</code>/<code>HOME</code>/<code>GITEA_WORK_DIR</code>, <code>cd</code>s into the work
  directory, then daemonizes via <strong><code>/usr/sbin/daemon -f -u &lt;user&gt; -p
  &lt;pidfile&gt; &lt;command&gt;</code></strong> — FreeBSD's built-in daemonizer, analogous to
  <code>start-stop-daemon</code> on Linux.</li>
<li><code>gitea_stop()</code> reads the PID file directly and sends a default <code>kill</code>
  (<code>SIGTERM</code>), relying on Gitea's own graceful-shutdown handling rather than
  any escalation schedule.</li>
<li>Enable/manage via <code>service gitea start</code>/<code>stop</code>/<code>status</code> once
  <code>gitea_enable="YES"</code> is in <code>/etc/rc.conf</code>.</li>
</ul>
<h2 id="openbsd-rcd-contribserviceopenbsdgitea">OpenBSD <code>rc.d</code> (<code>contrib/service/openbsd/gitea</code>)<a href="#openbsd-rcd-contribserviceopenbsdgitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>OpenBSD's minimal <code>rc.d</code>/<code>rc.subr</code> convention, one of the shortest scripts in
the set:</p>
<pre class="highlight"><code class="language-sh">daemon="/usr/local/bin/gitea"
daemon_user="git"
daemon_flags="web -c /etc/gitea/app.ini"
gitea_directory="/var/lib/gitea"
rc_bg=YES

rc_start() {
    ${rcexec} "cd ${gitea_directory}; ${daemon} ${daemon_flags} ${_bg}"
}
rc_cmd $1</code></pre>
<ul>
<li><code>rc_bg=YES</code> tells OpenBSD's <code>rc.subr</code> to background the daemon
  automatically (again compensating for <code>gitea web</code> not self-daemonizing).</li>
<li><code>rc_start()</code> overrides only the start behavior (to <code>cd</code> into the working
  directory first); stop/restart/status/check fall back to <code>rc.subr</code>'s
  built-in generic implementations, which track the PID via
  <code>pkill</code>/<code>pgrep</code>-style matching against <code>${daemon}</code>.</li>
<li>Install to <code>/etc/rc.d/gitea</code>, then enable via <code>rcctl enable gitea</code> and
  control via <code>rcctl start|stop|restart gitea</code>.</li>
</ul>
<h2 id="solarisillumos-smf-contribservicesunosgiteaxml">Solaris/illumos SMF (<code>contrib/service/sunos/gitea.xml</code>)<a href="#solarisillumos-smf-contribservicesunosgiteaxml" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A Service Management Facility (SMF) manifest for Solaris/illumos-derived
systems (OmniOS, SmartOS), imported with <code>svccfg import gitea.xml</code>:</p>
<pre class="highlight"><code class="language-xml">&lt;service name="gitea" type="service" version="1"&gt;
  &lt;dependency name="network" .../&gt;
  &lt;dependency name="filesystem" .../&gt;
  &lt;exec_method type="method" name="start"
      exec="/opt/local/bin/gitea web" timeout_seconds="60"&gt;
    &lt;method_context&gt;
      &lt;method_credential user="git" group="git" /&gt;
      &lt;method_environment&gt;
        &lt;envvar name='GITEA_WORK_DIR' value='/opt/local/share/gitea'/&gt;
        &lt;envvar name='GITEA_CUSTOM' value='/opt/local/etc/gitea'/&gt;
        &lt;envvar name='HOME' value='/var/db/gitea'/&gt;
        ...
      &lt;/method_environment&gt;
    &lt;/method_context&gt;
  &lt;/exec_method&gt;
  &lt;exec_method type="method" name="stop" exec=":kill" timeout_seconds="60"/&gt;
  ...
&lt;/service&gt;</code></pre>
<p>Distinctive aspects of the SMF model compared to the Linux/BSD scripts:</p>
<ul>
<li><strong>Declarative dependencies</strong> — <code>network</code> and <code>filesystem/local</code> are
  declared as SMF service dependencies (not shell-script ordering hints),
  and SMF's fault-management daemon (<code>svc.startd</code>) automatically restarts
  the service if it exits unexpectedly, without any explicit "restart
  policy" configuration in the manifest.</li>
<li><strong><code>exec=":kill"</code> for stop</strong> — SMF's built-in <code>:kill</code> method sends
  <code>SIGTERM</code> (escalating to <code>SIGKILL</code> after <code>timeout_seconds</code>) rather than
  requiring a custom stop script.</li>
<li><strong><code>GITEA_CUSTOM</code></strong> is set explicitly (unlike the other scripts, which rely
  on <code>--config</code>/<code>-c</code>) — pointing to Gitea's <code>custom/</code> override directory
  directly via environment variable instead of a config-file flag.</li>
<li><strong><code>create_default_instance enabled="false"</code></strong> — the service is imported in
  a disabled state; an operator must explicitly <code>svcadm enable gitea</code> after
  import (a deliberate safety default so the service doesn't start
  unconfigured).</li>
</ul>
<p>Operate with <code>svcadm enable/disable/restart gitea</code> and inspect state with
<code>svcs gitea</code> / <code>svcs -xv gitea</code>.</p>
<h2 id="macos-launchd-contribservicelaunchdiogiteawebplist">macOS <code>launchd</code> (<code>contrib/service/launchd/io.gitea.web.plist</code>)<a href="#macos-launchd-contribservicelaunchdiogiteawebplist" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A per-machine (or per-user, if placed under <code>~/Library/LaunchAgents</code>)
<code>launchd</code> property list for running Gitea on macOS:</p>
<pre class="highlight"><code class="language-xml">&lt;key&gt;Label&lt;/key&gt;&lt;string&gt;io.gitea.web&lt;/string&gt;
&lt;key&gt;UserName&lt;/key&gt;&lt;string&gt;git&lt;/string&gt;
&lt;key&gt;GroupName&lt;/key&gt;&lt;string&gt;git&lt;/string&gt;
&lt;key&gt;ProgramArguments&lt;/key&gt;
&lt;array&gt;
  &lt;string&gt;/Users/git/gitea/gitea&lt;/string&gt;
  &lt;string&gt;web&lt;/string&gt;
&lt;/array&gt;
&lt;key&gt;RunAtLoad&lt;/key&gt;&lt;true/&gt;
&lt;key&gt;KeepAlive&lt;/key&gt;&lt;true/&gt;
&lt;key&gt;WorkingDirectory&lt;/key&gt;&lt;string&gt;/Users/git/gitea/&lt;/string&gt;
&lt;key&gt;StandardOutPath&lt;/key&gt;&lt;string&gt;/Users/git/gitea/log/stdout.log&lt;/string&gt;
&lt;key&gt;StandardErrorPath&lt;/key&gt;&lt;string&gt;/Users/git/gitea/log/stderr.log&lt;/string&gt;
&lt;key&gt;SoftResourceLimits&lt;/key&gt;
&lt;dict&gt;&lt;key&gt;NumberOfFiles&lt;/key&gt;&lt;integer&gt;8192&lt;/integer&gt;&lt;/dict&gt;</code></pre>
<ul>
<li><strong><code>RunAtLoad</code></strong> starts Gitea as soon as the plist is loaded (at boot for a
  <code>LaunchDaemon</code>, at login for a <code>LaunchAgent</code>); <strong><code>KeepAlive</code></strong> tells
  <code>launchd</code> to restart the process whenever it exits, regardless of exit
  code — the macOS equivalent of <code>Restart=always</code>.
  <code>SoftResourceLimits.NumberOfFiles=8192</code> raises the default open-file
  limit (macOS's default of 256 is documented as too low for Gitea's
  parallel-pipe usage patterns, e.g. concurrent git subprocess I/O).</li>
<li>No <code>--config</code> flag is passed — Gitea falls back to discovering
  <code>custom/conf/app.ini</code> relative to the binary/working directory. Adjust
  <code>ProgramArguments</code> to add <code>--config /path/to/app.ini</code> if a non-default
  location is needed.</li>
<li>Because paths are hardcoded to a specific user's home directory
  (<code>/Users/git/gitea/...</code>), every path in the plist <strong>must</strong> be edited to
  match the actual install location before use — the file is explicitly
  commented as a template.</li>
</ul>
<p>Install to <code>/Library/LaunchDaemons/io.gitea.web.plist</code> (system-wide,
requires <code>sudo launchctl load</code>) or <code>~/Library/LaunchAgents/io.gitea.web.plist</code>
(per-user), then:</p>
<pre class="highlight"><code class="language-sh">sudo launchctl load /Library/LaunchDaemons/io.gitea.web.plist
sudo launchctl start io.gitea.web</code></pre>
<h2 id="supervisor-contribservicesupervisorgitea">Supervisor (<code>contrib/service/supervisor/gitea</code>)<a href="#supervisor-contribservicesupervisorgitea" class="heading-anchor" aria-label="Link">#</a></h2>
<p>A platform-agnostic fallback for environments that use
<a href="http://supervisord.org/">Supervisor</a> as their process manager instead of
(or on top of) the OS's native init system — common in containerized or
PaaS-style deployments that already standardize on Supervisor for managing
multiple processes:</p>
<pre class="highlight"><code class="language-ini">[program:gitea]

environment = HOME="/home/git", USER="git"</code></pre>
<ul>
<li><code>autostart=true</code> + <code>autorestart=true</code> mirror the "start at boot, restart on
  crash" behavior of the native init systems.</li>
<li><code>startsecs=10</code> — Supervisor only considers the process "successfully
  started" if it stays up for 10 seconds, catching immediate crash-loops
  (e.g. a bad config) before marking the program healthy.</li>
<li>Built-in <strong>log rotation</strong> (<code>stdout_logfile_maxbytes</code>/<code>_backups</code>) is
  configured directly in the program stanza, since Supervisor manages log
  file rotation itself rather than delegating to <code>logrotate</code>.</li>
<li>Note the hardcoded example path assumes a source checkout under
  <code>$GOPATH/src/github.com/go-gitea/gitea/</code> — production deployments should
  point <code>directory</code>/<code>command</code> at wherever the release binary is actually
  installed, and typically pass <code>-c /etc/gitea/app.ini</code> explicitly rather
  than relying on binary-relative config discovery.</li>
<li>Reload after editing with <code>supervisorctl reread &amp;&amp; supervisorctl update</code>,
  then manage with <code>supervisorctl start|stop|restart gitea</code>.</li>
</ul>
<h2 id="choosing-between-init-managed-restart-and-giteas-own-graceful-restart">Choosing Between Init-Managed Restart and Gitea's Own Graceful Restart<a href="#choosing-between-init-managed-restart-and-giteas-own-graceful-restart" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Every script above gives the OS/process-manager ownership of "process
supervision" (start at boot, restart on crash). This is orthogonal to — and
by default takes precedence over — Gitea's <strong>own</strong> in-process graceful
restart mechanism (<code>SIGHUP</code> → fork-and-hand-off, gated by
<code>app.ini</code>'s <code>[server] ALLOW_GRACEFUL_RESTARTS</code> /
<code>setting.GracefulRestartable</code>), documented in depth in
<a href="cli-commands.html#graceful-restart--shutdown">CLI &amp; Admin Operations — Graceful Restart &amp; Shutdown</a>.</p>
<table>
<thead>
<tr>
<th>Scenario</th>
<th>Recommended approach</th>
</tr>
</thead>
<tbody>
<tr>
<td>Config change requiring a full reload, managed by systemd/OpenRC/etc.</td>
<td><code>systemctl restart gitea</code> / <code>rc-service gitea restart</code> (new PID, brief listener gap unless socket-activated)</td>
</tr>
<tr>
<td>Zero-downtime binary upgrade or config reload, self-managed</td>
<td>Ensure <code>ALLOW_GRACEFUL_RESTARTS</code> is <code>true</code> (the default), then signal <code>SIGHUP</code> directly (or via a process-manager "reload" hook if it forwards signals rather than restarting)</td>
</tr>
<tr>
<td>Runtime-only operations (flush queues, rotate logs, pause logging, cancel a stuck process)</td>
<td><code>gitea manager ...</code> subcommands over the internal API — see <a href="cli-commands.html#gitea-manager--controlling-a-running-process"><code>gitea manager</code></a> — these require <strong>no process restart at all</strong></td>
</tr>
<tr>
<td>External log rotation (<code>logrotate</code>, etc.)</td>
<td><code>gitea manager logging release-and-reopen</code>, triggered from the rotation tool's <code>postrotate</code> hook, regardless of which init system starts Gitea</td>
</tr>
</tbody>
</table>
<p>Container-based deployments (Docker/Kubernetes) use a different mechanism
entirely — the official image's <code>docker/root/etc/s6/</code> scripts run Gitea
under <strong>s6-svscan</strong>, with the container runtime itself (not one of the
scripts above) responsible for restart policy; see
<a href="../03-getting-started/installation-and-build.html">Getting Started — Installation &amp; Build</a>
for background on the various installation paths, including containers.</p>
