<h1>`web_src/` Directory Map</h1>
<h1 id="web_src-directory-map"><code>web_src/</code> Directory Map</h1>
<p>This page is a comprehensive, file-level reference for everything under <code>web_src/</code> — the source
tree that <a href="../09-core-modules/frontend-build.html">Vite compiles</a> into <code>public/assets/</code>. It
complements <a href="../09-core-modules/frontend-features.html">Frontend Features &amp; the "Islands of Interactivity" Pattern</a>
(which explains <em>how</em> these modules get wired up) by giving a directory-by-directory,
representative-file-by-file index of <em>what lives where</em>. See
<a href="go-templates.html">Go Templates &amp; Views</a> for the server-rendered HTML that these assets enhance.</p>
<h2 id="top-level-layout">Top-Level Layout<a href="#top-level-layout" class="heading-anchor" aria-label="Link">#</a></h2>
<pre class="highlight"><code class="language-text">web_src/
├── js/            TypeScript + Vue sources (this page's main focus)
├── css/           Plain CSS, consumed via Tailwind/PostCSS pipeline
├── fomantic/      Prebuilt Fomantic UI theme sources (Less-based, built separately from Vite)
└── svg/           Custom hand-authored SVG icon sources (merged with @primer/octicons)</code></pre>
<p>Only <code>js/</code> and <code>css/</code> are inputs to the Vite build declared in <code>vite.config.ts</code>
(<code>rolldownOptions.input</code>); <code>fomantic/</code> is compiled by Fomantic UI's own Gulp-based build tool
(configured by <code>web_src/fomantic/semantic.json</code>, which points <code>base</code> at
<code>node_modules/fomantic-ui</code> and restricts <code>components</code> to just the handful Gitea actually uses —
currently <code>api</code> and <code>tab</code>, since Gitea's own <code>modules/fomantic/*.ts</code> reimplements <code>dropdown</code>,
<code>modal</code>, <code>dimmer</code>, and <code>transition</code> natively) into <code>web_src/fomantic/build/</code>, whose output
(<code>fomantic.js</code>, theme CSS) is then imported by <code>index.ts</code>/<code>index.css</code> like any other pre-built
dependency; <code>svg/</code> is consumed by the <code>tools/generate-svg.ts</code> build script (see
<a href="#web_srcsvg-custom-icon-sources">SVG Icon System</a> below), not by Vite directly.</p>
<h2 id="web_srcjs-typescript-vue-source-tree"><code>web_src/js/</code> — TypeScript &amp; Vue Source Tree<a href="#web_srcjs-typescript-vue-source-tree" class="heading-anchor" aria-label="Link">#</a></h2>

<h2 id="web_srcsvg-custom-icon-sources"><code>web_src/svg/</code> — Custom Icon Sources<a href="#web_srcsvg-custom-icon-sources" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Custom, hand-authored SVG icon sources that are <strong>not</strong> part of the <code>@primer/octicons</code> package
(which supplies the bulk of Gitea's <code>octicon-*</code> icons via <code>node_modules</code>). <code>tools/generate-svg.ts</code>
(<code>make svg</code>) globs three separate source sets — <code>web_src/svg/*.svg</code> (this directory, no prefix),
<code>node_modules/@primer/octicons/build/svg/*-16.svg</code> (prefixed <code>octicon-</code>, with the <code>-16</code> size
suffix stripped from the name), and <code>public/assets/img/gitea.svg</code> (renamed to <code>gitea-gitea.svg</code>)
— and runs each through the same <code>svgo</code>-based optimization pass (strips default <code>preset-default</code>
noise, removes explicit width/height in favor of <code>viewBox</code>, injects <code>xmlns</code>, <code>aria-hidden="true"</code>,
a <code>class="svg &lt;name&gt;"</code> attribute, and prefixes internal element IDs with the icon name to avoid
collisions when multiple inline SVGs share a page), writing every result into the single flat
output directory <code>public/assets/img/svg/*.svg</code> — the directory that both <code>modules/svg</code> (Go,
server-side inline <code>svg</code> template func) and <code>web_src/js/svg.ts</code> (TypeScript, per-icon static
imports) read from. The same script also processes <code>node_modules/material-icon-theme/icons/*.svg</code>
into <code>options/fileicon/material-icon-svgs.json</code> (used by <code>modules/fileicon</code>) — a related but
separate output, kept as an inline JSON symbol map rather than individual files since file-icons
are looked up by filename/extension rules rather than by a fixed icon name. See
<a href="#svg-icon-system">SVG Icon System</a> below for the full pipeline.</p>

<h2 id="svg-icon-system">SVG Icon System<a href="#svg-icon-system" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The SVG pipeline spans build tooling, Go backend, and frontend, converging on one canonical
asset directory:</p>
<pre class="mermaid">flowchart LR
    subgraph Sources["Icon Sources"]
        OCT["node_modules/@primer/octicons<br/>(bulk of octicon-* icons)"]
        CUSTOM["web_src/svg/*.svg<br/>(gitea-*, material-*, fontawesome-*)"]
    end
    GEN["tools/generate-svg.ts<br/>(make svg / svg-check)"]
    OUT["public/assets/img/svg/*.svg<br/>(normalized: viewBox, width=16, height=16, class)"]
    OCT --> GEN
    CUSTOM --> GEN
    GEN --> OUT

    OUT -->|"AssetFS().ReadFile at startup"| GOSVG["modules/svg (Go)<br/>svg.Init() populates svgIcons map"]
    GOSVG -->|"{{svg \"octicon-check\" 16 \"class\"}}"| TMPL["templates/**/*.tmpl<br/>(server-rendered inline <svg>)"]

    OUT -->|"per-icon static import"| JSSVG["web_src/js/svg.ts<br/>(tree-shakeable, one import per icon)"]
    JSSVG -->|"svg(name, size, class) / <SvgIcon name=.../>"| VUEJS["Vue components & feature modules"]</pre>
<ul>
<li><strong>Build time</strong> — <code>tools/generate-svg.ts</code> (invoked by <code>make svg</code>; verified in CI/pre-commit by
  <code>make svg-check</code>, which regenerates, <code>git add</code>s, and diffs the result) combines <code>@primer/octicons</code>,
  the custom sources in <code>web_src/svg/</code>, and <code>public/assets/img/gitea.svg</code>, running each through
  <code>svgo</code> to normalize <code>viewBox</code>/<code>aria-hidden</code>/<code>class</code> attributes and strip redundant
  width/height so they all behave predictably regardless of source, then writes every result
  into the single flat <code>public/assets/img/svg/</code> directory. The same script separately converts
  <code>material-icon-theme</code>'s file-type icons into <code>options/fileicon/material-icon-svgs.json</code> and
  <code>options/fileicon/material-icon-rules.json</code> (name/extension → icon lookup rules), consumed by
  <code>modules/fileicon</code> rather than by <code>modules/svg</code>/<code>svg.ts</code>.</li>
<li><strong>Go/server side</strong> (<code>modules/svg/svg.go</code>) — <code>svg.Init()</code> runs at startup, lists every <code>.svg</code>
  file under <code>assets/img/svg</code> via the layered <code>public.AssetFS()</code>, reads and <code>Normalize()</code>s each
  one into an in-memory <code>svgIcons map[string]svgIconItem</code>. <code>svg.RenderHTML(icon, size, class)</code>
  (exposed to templates as the <code>svg</code> func, see <a href="go-templates.html">Go Templates</a>) looks up the
  icon, does a string-replace for non-default size/class combinations, and caches up to 10,000
  distinct <code>(icon, size, class)</code> render results in a <code>sync.Map</code> to avoid repeated string
  manipulation on hot template paths. <code>MockIcon()</code> lets Go tests substitute a dummy icon without
  needing the real asset files present. A missing icon renders a visible <code>&lt;span&gt;name(size/class)&lt;/span&gt;</code>
  placeholder instead of failing, so a typo'd icon name degrades gracefully rather than 500ing.</li>
<li><strong>Frontend/TypeScript side</strong> (<code>web_src/js/svg.ts</code>) — rather than a runtime lookup table, every
  icon actually used in <code>.vue</code>/<code>.ts</code> code is a <strong>named static import</strong> from the same
  <code>public/assets/img/svg/*.svg</code> output directory. This lets Vite's bundler tree-shake unused
  icons out of the final JS bundle entirely (only icons an entry point actually imports end up
  in that entry's chunk) at the cost of needing an explicit <code>import</code> line per icon used from JS —
  this is the rationale behind the <code>frontend-features.md</code> note that small components must "not
  import the non-tree-shakeable <code>svg.ts</code>" module wholesale if they only need one or two icons.
  <code>svg(name, size, classNames)</code> returns a plain HTML string (for use in non-Vue contexts like
  <code>markup/*.ts</code> or <code>modules/*.ts</code>), <code>svgRaw()</code> returns the raw markup for direct injection, and
  the <code>SvgIcon</code> Vue component (<code>defineComponent({name: 'SvgIcon', props: {name, size, className}})</code>)
  is the idiomatic way to render an icon inside a <code>.vue</code> template.</li>
<li>Both the Go and TypeScript consumers read from the <strong>same</strong> generated <code>public/assets/img/svg/</code>
  directory, so an icon added to <code>web_src/svg/</code> (or upgraded in <code>@primer/octicons</code>) becomes
  available to both server-rendered templates and client-side Vue components after a single
  <code>make svg</code> regeneration — there is no separate icon set to keep in sync.</li>
</ul>
<h2 id="frontend-build-pipeline-tsvue-viteesbuild-assets-go">Frontend Build Pipeline (TS/Vue → Vite/esbuild → Assets → Go)<a href="#frontend-build-pipeline-tsvue-viteesbuild-assets-go" class="heading-anchor" aria-label="Link">#</a></h2>
<p>The end-to-end path from source files in this directory to what a browser actually loads is
fully documented in <a href="../09-core-modules/frontend-build.html">Frontend Build Pipeline</a>; the diagram
below is a <code>web_src/</code>-centric summary of that same pipeline, showing exactly which subdirectory
feeds which build step.</p>
<pre class="mermaid">flowchart LR

<p>Key points this diagram makes explicit that the more detailed
<a href="../09-core-modules/frontend-build.html">Frontend Build Pipeline</a> page covers in prose:</p>
<ol>
<li><strong>Two independent build tools feed the same output directory.</strong> <code>tools/generate-svg.ts</code>
   (icon normalization) and the main Vite build both write into <code>public/assets/</code>, but on
   different schedules — SVGs are regenerated by <code>make svg</code> (occasionally, when icons change),
   while the JS/CSS bundle is rebuilt by <code>make frontend</code>/<code>make watch-frontend</code> on every source
   change. <code>svg-check</code> in CI ensures the checked-in <code>public/assets/img/svg/</code> output stays in
   sync with <code>web_src/svg/</code> + the pinned <code>@primer/octicons</code> version.</li>
<li><strong>Fomantic UI is a separate, pre-built dependency</strong>, not compiled by Vite — <code>web_src/fomantic/</code>
   sources are built by Fomantic's own Gulp toolchain into <code>web_src/fomantic/build/</code>, and only
   the <em>result</em> is <code>@import</code>ed/imported by <code>index.css</code>/<code>index.ts</code> like any other npm package.</li>
<li><strong>The Go template layer is the only consumer that ties JS/CSS and SVG output back together</strong>:
   <code>modules/templates</code> resolves hashed asset filenames via <code>manifest.json</code> for <code>&lt;script&gt;</code>/<code>&lt;link&gt;</code>
   tags, while <code>modules/svg</code> independently reads the same <code>public/assets/img/svg/</code> directory to
   inline icons directly into the HTML response — two separate consumption paths into one shared
   output directory.</li>
</ol>
