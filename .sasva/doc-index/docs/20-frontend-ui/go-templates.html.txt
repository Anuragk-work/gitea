<h1>Go Templates & Views</h1>
<h1 id="go-templates-views">Go Templates &amp; Views</h1>
<p>Gitea's server-rendered HTML pages are built with Go's standard <a href="https://pkg.go.dev/html/template"><code>html/template</code></a> package. This page documents the template engine setup, the helper-function ecosystem in <code>modules/templates/</code> and <code>modules/htmlutil/</code>, how the <code>templates/</code> directory mirrors the router package structure, and how site administrators can override any template via a <code>custom/</code> overlay directory.</p>
<h2 id="overview">Overview<a href="#overview" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Every HTML response served by the web routers (<code>routers/web/...</code>) is rendered by calling <code>ctx.HTML(status, tplName)</code>, where <code>tplName</code> is a <code>templates.TplName</code> — effectively the template's file path (without the <code>.tmpl</code> extension) relative to the <code>templates/</code> directory. The rendering pipeline is:</p>
<pre class="mermaid">flowchart LR
    A["Router handler<br/>routers/web/*.go"] --> B["ctx.HTML(status, tplName)"]
    B --> C["services/context<br/>Context.HTML()"]
    C --> D["templates.PageRenderer()<br/>modules/templates/page.go"]
    D --> E["scopedtmpl.ScopedTemplate<br/>modules/templates/scopedtmpl"]
    E --> F["Layered asset FS<br/>custom/templates → templates/"]
    F --> G[".tmpl file parsed<br/>with FuncMap injected"]
    G --> H["Rendered HTML response"]</pre>
<p>The same core machinery (with a different <code>FuncMap</code> and a separate template set) is reused for transactional e-mails, see <a href="#mail-templates"><code>modules/templates/mail.go</code></a> below.</p>
<h2 id="template-rendering-pipeline">Template Rendering Pipeline<a href="#template-rendering-pipeline" class="heading-anchor" aria-label="Link">#</a></h2>
<h3 id="templatespagerenderer"><code>templates.PageRenderer()</code><a href="#templatespagerenderer" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/templates/page.go</code> defines a lazily-initialized singleton (<code>sync.OnceValue</code>) that builds a <code>pageRenderer</code>:</p>
<pre class="highlight"><code class="language-go">var PageRenderer = sync.OnceValue(func() *pageRenderer {
    rendererType := util.Iif(setting.IsProd, "static", "auto-reloading")
    assetFS := AssetFS()
    tr := &amp;tmplRender{
        collectTemplateNames: func() ([]string, error) { /* lists all *.tmpl under templates/, excluding mail/ */ },
        readTemplateContent:  func(name string) ([]byte, error) { return assetFS.ReadFile(name + ".tmpl") },
    }
    pr := &amp;pageRenderer{tmplRenderer: tr}
    if err := tr.recompileTemplates(pr.funcMapDummy()); err != nil {
        processStartupTemplateError(err)
    }
    if !setting.IsProd {
        go AssetFS().WatchLocalChanges(graceful.GetManager().ShutdownContext(), func() {
            _ = tr.recompileTemplates(pr.funcMapDummy())
        })
    }
    return pr
})</code></pre>
<p>Key behaviors:</p>
<ul>
<li>In <strong>production</strong> (<code>setting.IsProd</code>), templates are compiled once at startup and any template error is fatal (<code>log.Fatal</code>).</li>
<li>In <strong>development</strong>, a filesystem watcher (<code>AssetFS().WatchLocalChanges</code>) triggers <code>PageRendererReload()</code> whenever a <code>.tmpl</code> file changes on disk, so edits are picked up without restarting the server.</li>
<li><code>ReloadAllTemplates()</code> (in <code>modules/templates/htmlrenderer.go</code>) reloads both the page renderer and the mail renderer together — this is also exposed through the admin "Reload Templates" action.</li>
</ul>
<h3 id="scoped-templates-modulestemplatesscopedtmpl">Scoped templates (<code>modules/templates/scopedtmpl</code>)<a href="#scoped-templates-modulestemplatesscopedtmpl" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Go's <code>html/template</code> package normally shares one global namespace: defining <code>{{define "x"}}</code> in one file makes <code>x</code> visible (and overridable) from every other file in the same <code>*template.Template</code>. Gitea's <code>templates/</code> tree defines many small <code>{{define}}</code> blocks with generic names (e.g. <code>list</code>, <code>content</code>) across dozens of files, which would collide in a flat namespace.</p>
<p><code>scopedtmpl.ScopedTemplate</code> (in <code>modules/templates/scopedtmpl/scopedtmpl.go</code>) solves this by building, for each <strong>top-level</strong> template name requested (e.g. <code>repo/view</code>), an isolated <code>scopedTemplateSet</code> that only contains that file's <code>{{define}}</code> blocks plus whatever it explicitly <code>{{template ...}}</code>-includes — following Go template's parse-tree dependency graph. This means a <code>{{define "list"}}</code> in <code>templates/repo/issue/list.tmpl</code> cannot accidentally leak into or be shadowed by one in <code>templates/org/list.tmpl</code>.</p>
<pre class="highlight"><code class="language-go">type ScopedTemplate struct {
    all        *template.Template // superset containing every parsed .tmpl file
    scopedTemplateSets map[string]*scopedTemplateSet // lazily built per top-level template
}

func (t *ScopedTemplate) Executor(name string, funcMap template.FuncMap) (TemplateExecutor, error) {
    // looks up (or builds) the scoped set for `name`, then returns
    // an executor bound to the caller-supplied FuncMap (which carries the request `ctx`)
}</code></pre>
<p>Because Go templates freeze their <code>FuncMap</code> at parse time, <code>ScopedTemplate.Freeze()</code> swaps in no-op stub functions before HTML-escaping analysis runs, and the <em>real</em> functions (which need the live per-request <code>context.Context</code>) are injected later, per-request, via <code>Executor(name, funcMap)</code>. This is why every rendered template funcmap always contains a <code>"ctx"</code> entry (see below).</p>
<h3 id="layered-asset-filesystem-custom-overrides">Layered asset filesystem &amp; custom overrides<a href="#layered-asset-filesystem-custom-overrides" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/templates/base.go</code> builds the effective template filesystem as two (or three) stacked layers using <code>modules/assetfs</code>:</p>
<pre class="highlight"><code class="language-go">func AssetFS() *assetfs.LayeredFS {
    return assetfs.Layered(CustomAssets(), BuiltinAssets())
}

func CustomAssets() *assetfs.Layer {
    return assetfs.Local("custom", setting.CustomPath, "templates")
}</code></pre>
<ul>
<li><strong><code>BuiltinAssets()</code></strong> — the templates shipped with Gitea. Depending on the build tag, this is either the local <code>templates/</code> directory on disk (<code>templates_dynamic.go</code>, tag <code>!bindata</code>) or embedded bindata compiled into the binary (<code>templates_bindata.go</code>, tag <code>bindata</code>, generated via <code>go run build/generate-bindata.go</code>).</li>
<li><strong><code>CustomAssets()</code></strong> — files under <code>&lt;CustomPath&gt;/templates/</code> (by default <code>custom/templates/</code> relative to the working directory, or <code>CustomPath</code> from <code>app.ini</code>).</li>
</ul>
<p><code>assetfs.LayeredFS.ReadLayeredFile()</code> (in <code>modules/assetfs/layered.go</code>) walks the layers <strong>top layer first</strong> — so a file present in <code>custom/templates/repo/view.tmpl</code> completely replaces the built-in <code>templates/repo/view.tmpl</code> for that path. This is Gitea's supported mechanism for site-specific template customization; see <a href="#custom-template-overrides">Custom Template Overrides</a> below.</p>
<blockquote>
<p>Note: <code>Local()</code> resolves the layer's root as an absolute <code>os.DirFS</code>, and <code>WatchLocalChanges</code> uses <code>fsnotify</code> to detect changes in dev mode across <strong>all</strong> layers, so custom template edits are also hot-reloaded when <code>setting.IsProd</code> is false.</p>
</blockquote>
<h3 id="error-reporting">Error reporting<a href="#error-reporting" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/templates/htmlrenderer.go</code> contains a small suite of regex-based "pretty" error formatters (<code>templateErrorPrettier</code>) that convert Go's terse <code>template: name:line: message</code> errors into a detailed, source-line-annotated message (with a <code>^^^</code> indicator under the offending token), including which asset <strong>layer</strong> (<code>custom</code> vs <code>builtin</code>) the broken file came from. This is surfaced via <code>templates.HandleTemplateRenderingError(err)</code>, used both at startup and by <code>Context.HTML()</code> when rendering fails at request time (falling back to the <code>status/500</code> template).</p>

<h2 id="template-naming-composition-conventions">Template Naming &amp; Composition Conventions<a href="#template-naming-composition-conventions" class="heading-anchor" aria-label="Link">#</a></h2>
<ul>
<li>Template names passed to <code>ctx.HTML()</code> never include the <code>.tmpl</code> suffix, and always use forward slashes (<code>filepath.ToSlash</code>) regardless of OS.</li>
<li>Layout partials are composed explicitly with <code>{{template "name" .}}</code>. A typical repo page looks like:</li>
</ul>
<p><pre class="highlight"><code class="language-gotemplate">{{template "base/head" .}}
&lt;div role="main" aria-label="{{.Title}}" class="page-content repository file list ..."&gt;
    {{template "repo/header" .}}
    &lt;div class="ui container ..."&gt;
        {{template "base/alert" .}}
        ...
        &lt;div class="repo-view-container"&gt;
            {{template "repo/view_file_tree" .}}
            &lt;div class="repo-view-content"&gt;
                {{template "repo/view_content" .}}
            &lt;/div&gt;
        &lt;/div&gt;
    &lt;/div&gt;
&lt;/div&gt;
{{template "base/footer" .}}</code></pre>
(from <code>templates/repo/view.tmpl</code>)</p>
<ul>
<li><code>base/head.tmpl</code> and <code>base/footer.tmpl</code> are the top/bottom of virtually every authenticated page. <code>base/head.tmpl</code> renders <code>&lt;html&gt;</code>/<code>&lt;head&gt;</code>, the CSP meta tag (<code>ctx.HeadMetaContentSecurityPolicy</code>), OpenGraph tags, page styles/scripts, and — crucially — the <code>custom/header</code>, <code>custom/body_outer_pre</code>, and <code>custom/body_inner_pre</code> extension points. <code>base/footer.tmpl</code> closes the body and includes <code>custom/body_inner_post</code>, <code>custom/body_outer_post</code>, and <code>custom/footer</code>.</li>
<li>Sub-templates that render a fragment of a page (e.g. AJAX partial updates) are often named <code>*_content.tmpl</code>, <code>*_list.tmpl</code>, or <code>*_div.tmpl</code> and can be rendered standalone via <code>ctx.HTML</code> or <code>ctx.RenderToHTML()</code>.</li>
<li><code>Context.JSONTemplate(tmpl)</code> (in <code>services/context/context_response.go</code>) executes a <code>.tmpl</code> file but sets <code>Content-Type: application/json</code> — used for endpoints whose payload is easier to template than to build with <code>structs</code>/<code>json.Marshal</code> (still HTML-escaped by <code>html/template</code>, so JSON-unsafe characters must be escaped with care, e.g. <code>JSEscape</code>).</li>
</ul>
<h2 id="the-templatestplname-type-ctxhtml">The <code>templates.TplName</code> Type &amp; <code>ctx.HTML()</code><a href="#the-templatestplname-type-ctxhtml" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Router handlers declare template identifiers as typed constants to avoid stringly-typed typos:</p>
<pre class="highlight"><code class="language-go">// routers/web/home.go
var (
    tplHome templates.TplName = "home"
)
...
ctx.HTML(http.StatusOK, tplHome)</code></pre>
<p><code>Context.HTML()</code> (in <code>services/context/context_response.go</code>) is the single entry point used by nearly all web handlers:</p>
<pre class="highlight"><code class="language-go">func (ctx *Context) HTML(status int, name templates.TplName) {
    ...
    err := ctx.Render.HTML(ctx.Resp, status, name, ctx.Data, ctx.TemplateContext)
    if err == nil || errors.Is(err, syscall.EPIPE) {
        return
    }
    if name != tplStatus500 {
        err = fmt.Errorf("failed to render template: %s, error: %s", name, templates.HandleTemplateRenderingError(err))
        ctx.ServerError("Render failed", err) // shows the 500 page
    } else {
        ctx.PlainText(http.StatusInternalServerError, "Unable to render status/500 page...")
    }
}</code></pre>
<p><code>ctx.Data</code> (a <code>reqctx.ContextData</code>, effectively <code>map[string]any</code>) is the "view model" passed as the template's dot (<code>.</code>); <code>ctx.TemplateContext</code> (see next section) is passed separately and is what backs the <code>ctx</code> function inside templates.</p>
<p><code>Context.RenderToHTML(name, data)</code> renders a template to a <code>template.HTML</code> string in memory (e.g. to embed one rendered fragment inside another value, or return via JSON), and <code>Context.RenderWithErrDeprecated(...)</code> is a <strong>deprecated</strong> legacy path for showing validation errors that new code should avoid (replaced by JSON responses + client-side form handling).</p>
<h2 id="ctx-the-template-request-context"><code>ctx</code> — the Template Request Context<a href="#ctx-the-template-request-context" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Nearly every non-trivial template calls functions on <code>ctx</code>, e.g. <code>ctx.Locale.Tr "..."</code>, <code>ctx.RenderUtils.MarkdownToHtml</code>, <code>ctx.CurrentWebTheme.InternalName</code>. This <code>ctx</code> is not Go's <code>context.Context</code> interface directly exposed — it's <code>services/context.TemplateContext</code> (<code>type TemplateContext map[string]any</code>, defined in <code>services/context/context_template.go</code>), which <strong>implements</strong> <code>context.Context</code> (so it can still be passed to context-aware functions) while also exposing template-friendly methods:</p>
<pre class="highlight"><code class="language-go">func NewTemplateContextForWeb(ctx reqctx.RequestContext, req *http.Request, locale translation.Locale) TemplateContext {
    tmplCtx := NewTemplateContext(ctx, req)
    tmplCtx["Locale"] = locale
    tmplCtx["AvatarUtils"] = templates.NewAvatarUtils(ctx)
    tmplCtx["RenderUtils"] = templates.NewRenderUtils(ctx)
    tmplCtx["MiscUtils"] = templates.NewMiscUtils(ctx)
    tmplCtx["ActionsUtils"] = templates.NewActionsUtils(ctx)
    tmplCtx["RootData"] = ctx.GetData()
    tmplCtx["Consts"] = map[string]any{ /* unit.Type* constants for use in templates */ }

<h3 id="moduleshtmlutil-low-level-html-safety-primitives"><code>modules/htmlutil</code> — low-level HTML-safety primitives<a href="#moduleshtmlutil-low-level-html-safety-primitives" class="heading-anchor" aria-label="Link">#</a></h3>
<p><code>modules/htmlutil/html.go</code> provides the building blocks that the template FuncMap and Go code (outside of templates) both rely on to safely construct <code>template.HTML</code> values without introducing XSS:</p>
<pre class="highlight"><code class="language-go">func HTMLFormat(s template.HTML, rawArgs ...any) template.HTML {
    return template.HTML(fmt.Sprintf(string(s), htmlFormatArgs(s, rawArgs)...))
}</code></pre>
<p><code>htmlFormatArgs</code> escapes every argument passed to a format string unless it is already a "safe" type (<code>template.HTML</code>, numeric, bool) — strings, <code>template.URL</code>, and <code>fmt.Stringer</code> values are all passed through <code>template.HTMLEscapeString</code>. This is the mechanism behind the <code>HTMLFormat</code> FuncMap entry.</p>
<p>Other utilities in this package:</p>
<ul>
<li><code>ParseSizeAndClass(defaultSize, defaultClass, others...)</code> — the shared convention used by <code>AvatarUtils.Avatar(item, others...)</code> and similar variadic helpers to accept optional <code>(size int, class string)</code> overrides.</li>
<li><code>HTMLWriter</code> / <code>HTMLBuilder</code> — streaming/builder wrappers (<code>WriteString</code> escapes, <code>WriteHTML</code> does not, <code>WriteFormat</code> calls <code>HTMLPrintf</code>) used when constructing HTML fragments from Go code (e.g. inside <code>RenderUtils</code> methods) rather than from <code>.tmpl</code> files.</li>
<li><code>EscapeString(s) template.HTML</code> — one-shot HTML-escape returning a safe <code>template.HTML</code>.</li>
</ul>
<blockquote>
<p><strong>Security note:</strong> Because <code>html/template</code> auto-escapes by default, most <code>.tmpl</code> files never need to call these functions directly — they exist for the (comparatively few) Go-code paths that build <code>template.HTML</code> values programmatically, and for the <code>HTMLFormat</code>/<code>SanitizeHTML</code> FuncMap entries used when a template needs to interpolate already-safe-but-dynamic markup (e.g. inserting an <code>&lt;a&gt;</code> link into a translated string). <code>HTMLFormat</code> panics if invoked without arguments specifically to prevent a common mistake — passing raw, unescaped user input directly as the format string.</p>
</blockquote>
<h2 id="mail-templates">Mail Templates<a href="#mail-templates" class="heading-anchor" aria-label="Link">#</a></h2>
<p><code>modules/templates/mail.go</code> defines a <strong>separate</strong> <code>MailRender</code> pipeline for transactional e-mail. It reuses the same <code>tmplRender</code>/<code>recompileTemplates</code> machinery from <code>htmlrenderer.go</code> but:</p>
<ul>
<li>Uses a distinct FuncMap, <code>mailBodyFuncMap()</code>, which intentionally exposes a <em>smaller</em> surface than the page FuncMap (no <code>ctx</code>, no DB-backed <code>RenderUtils</code>/<code>AvatarUtils</code> — mail is rendered outside of an HTTP request) plus mail-only helpers like <code>DotEscape</code> (wraps dots in <code>ZWJ</code> characters to defeat auto-linkers).</li>
<li>Supports an optional <strong>subject</strong> template embedded in the same <code>.tmpl</code> file, separated from the body by a line of three or more dashes, parsed via <code>mailSubjectSplit = regexp.MustCompile(</code>(?m)^-{3,}\s*$<code>)</code>. The subject half is parsed as a <code>text/template</code> (not <code>html/template</code>, since it's plain text) with <code>mailSubjectTextFuncMap()</code>.</li>
<li>Template files live under <code>templates/mail/&lt;user|repo|org&gt;/...</code>, e.g. <code>templates/mail/user/auth/activate.tmpl</code>, <code>templates/mail/repo/issue/default.tmpl</code>. Each <code>.tmpl</code> typically has a sibling <code>*.devtest.yml</code> fixture used by the <code>templates/devtest</code> preview tooling to render sample e-mails during development.</li>
<li><code>ReloadAllTemplates()</code> calls both <code>PageRendererReload()</code> and <code>MailRendererReload()</code>.</li>
</ul>
<p>Example (<code>templates/mail/user/auth/activate.tmpl</code>):</p>

<h2 id="custom-template-overrides">Custom Template Overrides<a href="#custom-template-overrides" class="heading-anchor" aria-label="Link">#</a></h2>
<p>Gitea ships two distinct mechanisms for site-specific template customization, both rooted at the <code>custom/</code> directory (<code>setting.CustomPath</code>, default <code>&lt;work-path&gt;/custom</code>, overridable via the <code>CustomPath</code> build-time <code>-X</code> flag or <code>GITEA_CUSTOM</code> env var — see <code>docs/build-source.md</code>):</p>
<h3 id="1-full-template-override-any-file">1. Full template override (any file)<a href="#1-full-template-override-any-file" class="heading-anchor" aria-label="Link">#</a></h3>
<p>Any file under <code>custom/templates/&lt;same-relative-path&gt;.tmpl</code> completely replaces the corresponding built-in file, because <code>CustomAssets()</code> is layered <strong>above</strong> <code>BuiltinAssets()</code> in <code>AssetFS()</code>. For example, to customize the repository home page, an administrator creates <code>custom/templates/repo/home.tmpl</code> with the full desired markup — Gitea will use that file instead of the built-in <code>templates/repo/home.tmpl</code> for every request, without needing to touch the built-in copy or recompile Gitea.</p>
<pre class="mermaid">flowchart LR
    Req["Template lookup: repo/home"] --> L1{"custom/templates/repo/home.tmpl<br/>exists?"}
    L1 -->|yes| Use1["Use custom override"]
    L1 -->|no| L2["templates/repo/home.tmpl<br/>(builtin, dynamic or bindata)"]</pre>
<p>This is a "replace the whole file" strategy — the override completely supersedes the original, so it must be kept in sync with upstream changes to avoid losing new functionality after a Gitea upgrade.</p>
<h3 id="2-extension-point-hooks-templatescustomtmpl">2. Extension-point hooks (<code>templates/custom/*.tmpl</code>)<a href="#2-extension-point-hooks-templatescustomtmpl" class="heading-anchor" aria-label="Link">#</a></h3>

<p>All of these files exist as <strong>zero-byte</strong> placeholders in <code>templates/custom/</code> (see <code>templates/custom/header.tmpl</code>, <code>templates/custom/footer.tmpl</code>, etc.) — they render nothing by default. To use one, an administrator creates the <strong>same relative path</strong> under <code>custom/templates/custom/&lt;name&gt;.tmpl</code> (e.g. <code>custom/templates/custom/header.tmpl</code>), and the layered filesystem serves that instead of the empty built-in stub. This is the recommended, upgrade-safe way to inject small custom markup, since it doesn't require replacing an entire (potentially large, frequently-changing) built-in template file.</p>
<blockquote>
<p><strong>Tip:</strong> Because the dev-mode file watcher (<code>AssetFS().WatchLocalChanges</code>) watches all layers, custom overrides placed under <code>custom/templates/</code> are hot-reloaded just like built-in templates when running with <code>RUN_MODE = dev</code>. In production, a full server restart (or the admin "Reload Templates" action, which calls <code>templates.ReloadAllTemplates()</code>) is required to pick up changes.</p>
</blockquote>

        delete clone.dataset.expandAdded;
        clone.removeAttribute('data-expand-added');
        clone.style.cssText='background:none;border:none;padding:0;margin:0;text-align:center;min-width:70vw;max-width:90vw;';
        // Clear overlay content safely, keep close button
        overlayInner.innerHTML='';
        var closeBtn=document.createElement('button');
        closeBtn.className='mermaid-overlay-close';closeBtn.textContent='×';closeBtn.title='Close';
        closeBtn.addEventListener('click',function(){overlay.classList.remove('open');});
        overlayInner.appendChild(clone);
        overlayInner.appendChild(closeBtn);
        overlay.classList.add('open');
        // Re-run mermaid on the clone after it's in the DOM
        setTimeout(function(){
          if(window.mermaid){
            try{mermaid.run({nodes:[clone]});}catch(err){}
          }
        },50);
      });
      wrapper.appendChild(btn);
    });
  }
  // Wait for mermaid to finish rendering before adding buttons (mermaid init runs above)
  setTimeout(_addMermaidButtons,800);
  if(overlay){
    overlay.addEventListener('click',function(e){if(e.target===overlay)overlay.classList.remove('open');});
    document.addEventListener('keydown',function(e){if(e.key==='Escape')overlay.classList.remove('open');});
  }
  // Code copy buttons
  document.querySelectorAll('pre').forEach(function(pre){
    if(pre.classList.contains('mermaid'))return;
    var btn=document.createElement('button');
    btn.className='code-copy';btn.textContent='Copy';
    btn.addEventListener('click',function(){
      var code=pre.querySelector('code');
      var text=code?code.textContent:pre.textContent;
      navigator.clipboard.writeText(text).then(function(){btn.textContent='Copied!';setTimeout(function(){btn.textContent='Copy';},2000);});
    });
    pre.appendChild(btn);
  });
  // Back to top
  var btt=document.getElementById('back-to-top');
  if(btt){
    window.addEventListener('scroll',function(){btt.style.display=window.scrollY>300?'flex':'none';});
    btt.addEventListener('click',function(){window.scrollTo({top:0,behavior:'smooth'});});
  }
  // TOC active scroll tracking
  var tocLinks=document.querySelectorAll('.toc-aside a[data-anchor]');
  if(tocLinks.length>0){
    var headingEls=[];
    tocLinks.forEach(function(l){var el=document.getElementById(l.dataset.anchor);if(el)headingEls.push({el:el,link:l});});
    var tocAside=document.querySelector('.toc-aside');
    var onScroll=function(){
      var scrollPos=window.scrollY+80;
      var active=null;
      for(var i=0;i<headingEls.length;i++){if(headingEls[i].el.offsetTop<=scrollPos)active=headingEls[i];}
      tocLinks.forEach(function(l){l.classList.remove('toc-active');});
      if(active){
        active.link.classList.add('toc-active');
        // Scroll active link into view within the TOC panel, not the page
        if(tocAside){
          var linkTop=active.link.offsetTop-tocAside.offsetTop;
          var visibleTop=tocAside.scrollTop;
          var visibleBottom=visibleTop+tocAside.clientHeight;
          if(linkTop<visibleTop+40||linkTop>visibleBottom-40){
            tocAside.scrollTop=linkTop-tocAside.clientHeight/2;
          }
        }
      }
    };
    window.addEventListener('scroll',onScroll);
    onScroll();
    // Prevent TOC links from scrolling the TOC panel to top on click
    tocLinks.forEach(function(l){
      l.addEventListener('click',function(e){
        e.preventDefault();
        var anchor=l.dataset.anchor;
        var target=document.getElementById(anchor);
        if(target){target.scrollIntoView({behavior:'smooth',block:'start'});}
      });
    });
  }
  // Persist sidebar scroll position across page navigations
  var sidebarEl=document.querySelector('nav.sidebar');
  if(sidebarEl){
    var sidebarKey='sasva-sidebar-scroll';
    // Restore scroll position on page load
    var savedScroll=sessionStorage.getItem(sidebarKey);
    if(savedScroll){sidebarEl.scrollTop=parseInt(savedScroll,10);}
    // Save scroll position before navigating away
    document.querySelectorAll('#sidebar-nav-links a').forEach(function(a){
      a.addEventListener('click',function(){
        sessionStorage.setItem(sidebarKey,String(sidebarEl.scrollTop));
      });
    });
    // Also scroll active item into view on load
    var activeLink=sidebarEl.querySelector('a.active');
    if(activeLink&&!savedScroll){
      var linkOffset=activeLink.offsetTop-sidebarEl.offsetTop;
      sidebarEl.scrollTop=Math.max(0,linkOffset-sidebarEl.clientHeight/2);
    }
  }
})();
</script>
