Security Issues: Trivy & Opengrep Scanning Guide for Gitea

This documentation set is a derived, focused reorganization of Gitea's existing Markdown documentation, built specifically to help a security engineer or scanner operator run security scanning tools — such as Trivy (dependency / container / vulnerability scanning) and opengrep-class static analysis tools (SAST / secret-detection / CI-config linting) — against this codebase, and to understand what Gitea already does for security before layering more tooling on top.

Source material note: no literal security-issues/ documentation directory exists in this workspace. Every page in this set is instead synthesized from Gitea's general Markdown documentation tree — primarily root-level SECURITY.md, CONTRIBUTING.md, WORKSPACE_ANALYSIS.md, and the structured docs/**/*.md tree (architecture, services, database models, core modules, configuration, and build/CI/CD docs). See STYLE_GUIDE.md for the full source-provenance table and the authoring conventions used throughout this set.

Quick Start for Scanner Operators#

If you just want to point Trivy/opengrep at this repository right now and know what to expect:

  1. Read the Security Posture Overview for the threat-model summary and the "what's covered vs. what's not" gap table.
  2. Skim Existing Security Tooling in CI so new scanning is additive, not duplicative, of govulncheck, zizmor, actionlint, golangci-lint/depguard, license scanning, and Renovate.
  3. Go straight to Running Trivy and Opengrep for concrete integration points in the existing pipeline and a consolidated opengrep rule-target backlog (with source-code pointers, not fabricated examples).
  4. If a scan turns up something real and exploitable, route it through the Vulnerability Disclosure Process instead of a public issue.

What This Set Covers, Section by Section#

  1. Security Posture Overview — a threat-model-at-a- glance summary and an annotated architecture diagram showing where security controls sit in Gitea's layered-monolith backend (routers/ → services/ → models/ → xorm, plus a shared modules/ layer, and a Vue 3/TypeScript frontend). Also includes a "what Trivy/opengrep would add vs. what's already covered" gap table and suggested reading paths.
  2. Existing Security Tooling in CI — what's already automated (govulncheck, zizmor, actionlint, golangci-lint/depguard, license scanning via go-licenses/rolldown-license-plugin, Renovate) so new scans don't duplicate coverage, and explicitly flags the govulncheck non-fatal gap.
  3. Attack surface, in four pages:
  4. Authentication & Session Security — the auth chain, session/token handling, 2FA, LDAP secret encryption.
  5. Authorization / Permission Model — AccessMode/Access/Permission, org/team roles, restricted users.
  6. Input Handling & XSS Defense — HTML sanitization (bluemonday), URL scheme blocklist, iframe sandboxing.
  7. SSRF, Webhooks & Outbound Requests — ALLOWED_HOST_LIST, webhook signing, LFS JWT auth.
  8. Security-Relevant Settings — the [security]/[cors] settings catalog and other security-relevant app.ini configuration, including secret-supply mechanics and HTTP security headers.
  9. Build, Release & Container Posture — release signing, Docker/rootless container posture, dependency pinning, and license compliance.
  10. Running Trivy and Opengrep — concrete guidance for slotting Trivy and opengrep into this repository's existing pipeline, and mapping findings back to the attack-surface pages above, plus a consolidated rule-target backlog.
  11. Vulnerability Disclosure Process — the official process (per SECURITY.md) for routing any real, exploitable finding responsibly instead of filing a public issue.
